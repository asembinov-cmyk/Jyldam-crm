# Jyldam Logistics CRM — контекст проекта для разработки

Сводка всего, что нужно знать о проекте, прежде чем вносить изменения в код. Написана после
длительной сессии разработки — чтобы новый исполнитель (человек или ИИ) не наступал на те же
грабли повторно.

## 1. О компании и бизнесе

**Jyldam Logistics** — курьерская и логистическая компания, работает по Казахстану (в первую
очередь Астана и Алматы, плюс региональные города).

Компания тесно связана / фактически является частью **ТОО «QP Service»** — эта же организация
оказывает услуги фулфилмента для продавцов маркетплейсов (в первую очередь Wildberries): приём
товара от продавцов, хранение, маркировка, упаковка и доставка на склад маркетплейса.

Есть партнёрская компания **KET Logistic** — с ней есть интеграция (заказы можно отправлять в KET
прямо из CRM).

### Бизнес-модель в двух словах

1. **Партнёры** (магазины/продавцы) создают **заявки на забор** — «у меня N заказов, заберите».
   Заявка привязана к конкретному партнёру и городу.
2. Из заявки автоматически создаются N **заказов** (пустые «болванки» — без ФИО, адреса и т.д.) —
   их нужно наполнить данными.
3. **Менеджеры заказов («забивальщики»)** открывают заявку, фотографируют накладные/бланки на
   каждый заказ, вносят ФИО получателя, адрес, телефон, тип доставки (курьерская или почтовая —
   это принципиально разные ветки логики дальше).
4. Дальше заказ либо:
   - **Курьерская доставка** — развозится курьером внутри города, ИЛИ уезжает межгородним рейсом
     в другой город (см. раздел 5).
   - **Почтовая доставка** — отправляется через Казпочту (см. раздел 7).
5. Параллельно на складе **кладовщики** сортируют физические посылки по городам — для этого есть
   отдельный модуль «Сортировка» (раздел 6), который позволяет начинать сортировку сразу, не
   дожидаясь, пока все заказы в заявке будут «забиты».

## 2. Технологии и архитектура

- **Фронтенд:** чистый HTML/CSS/JS без фреймворка и без сборки. До 18.09.2026 всё лежало в одном
  `index.html` на 11 838 строк; теперь разрезано на `index.html` + `css/app.css` + 15 файлов в
  `js/` — см. раздел 4. Это по-прежнему **обычные скрипты с общей глобальной областью**, а не
  ES-модули: переписывание на `import`/`export` затронуло бы 604 глобальных имени и остаётся
  отдельной большой задачей, **не делать её походя**.
- **Бэкенд:** Supabase (Postgres + Auth + Realtime + Edge Functions + Storage).
  - Project ref: `tdexhspesodslwgbxojw`
  - Организация в Supabase: «Jyldam CRM», тариф Pro.
  - Проект в Supabase называется Jyldam-logistics.
- **Хостинг фронтенда:** GitHub Pages.
  - Репозиторий: `github.com/asembinov-cmyk/Jyldam-crm`
  - Домен: `jyldam-crm.kz` (подключён через файл `CNAME` в репозитории)
  - Деплой автоматический: любой `git push` в ветку `main` → сайт пересобирается и публикуется.
    Никакого отдельного шага деплоя не нужно.
  - Раньше (до перехода на git/Claude Code) правки заливались вручную через GitHub веб-интерфейс:
    «Add file» → «Upload files» → выбрать `index.html` → «Commit changes». Это было медленно и
    ненадёжно (несколько раз файл заливался не полностью / не тот). Через git это больше не проблема.
- **ИИ-функции внутри самой CRM:** есть свой прокси к Anthropic API — функция
  `callAI({system, prompt, image, model, max_tokens})` в коде. Используется для:
  - распознавания данных с фото бланка при создании заказа;
  - распознавания данных с фото в модуле «Сортировка» (раздел 6).

  Модель по умолчанию — `claude-sonnet-5`.

### Второй, отдельный проект/сайт — не путать!

Существует отдельный сайт-панель `admin.jyldam-logistics.kz` — это **не** эта CRM, а отдельная,
более старая панель, которая занимается только интеграцией с Казпочтой (SOAP API). У неё свои
настройки (тот же ключ API, тот же номер договора, тот же БИН — но отдельный интерфейс). Если
разговор идёт про Казпочту и всплывает этот домен — это не баг в нашей CRM, это другая система.

## 3. Структура базы данных (основные таблицы)

- **`orders`** — заказы. Самая крупная и важная таблица (десятки тысяч строк, продолжает расти).
  Ключевые поля:
  - `code` — человекочитаемый номер заказа
  - `client`, `phone`, `address` — данные получателя
  - `delivery_id` — тип доставки (ссылка на `delivery_types`) — **обязательное** поле, без него
    заказ не считается «обработанным»
  - `courier_city_id` — город назначения ДЛЯ КУРЬЕРСКОЙ доставки
  - `city_id` — город назначения ДЛЯ ПОЧТОВОЙ доставки (**это два разных поля!** какое из них
    смотреть — зависит от `delivery_id`)
  - `pickup_city_id` — город, где посылку физически ЗАБРАЛИ (склад/партнёр) — это **НЕ** то же
    самое, что город назначения!
  - `pickup_id` — ссылка на заявку на забор, из которой создан заказ
  - `intercity_shipment_id`, `intercity_cost` — привязка к межгородней отправке (раздел 5)
  - `sorted_at`, `sorted_by_name` — отметка склада (модуль «Сортировка», раздел 6)
  - `track` — трек-номер (Казпочта или другой перевозчик)
  - `fizlico_pickup_address` — отдельный адрес забора, только для партнёров типа «Физ лицо
    Алматы/Астана» — не показывается в общем гриде, только в самой карточке заказа (этот столбец
    специально убирали из таблицы)
- **`pickups`** — заявки на забор от партнёров
- **`partners`** — партнёры/магазины (`tariff_post`, `tariff_courier` — тарифы)
- **`profiles`** — сотрудники CRM. У сотрудника может быть заполнено поле `city_id` — если
  заполнено, то в модуле «Сортировка» он видит только заказы своего города (раздел 6). У админа
  это поле обычно пустое → видит все города.
- **`shipments`** — межгородние отправки (раздел 5). Поля: `ship_date`, `warehouse_id`,
  `dest_city_id`, `box_cost` (стоимость всей отправки), `per_order` (стоимость на 1 заказ,
  `box_cost` делённая на кол-во заказов, округлённая), `order_ids` (jsonb-массив id заказов).
- **`deleted_items`** — «корзина». Перед любым `DELETE` из основной таблицы сначала сохраняется
  полный снимок строки сюда (функция `dbDelete` в коде) — на случай восстановления. Хранится
  30 дней. Смотреть в разделе CRM «Центр контроля» → «Корзина».
- **`delivery_types`** — справочник типов доставки. В нём могут быть лишние/старые записи — в
  форме заказа список специально отфильтрован регуляркой `/курьер|почт/i`, чтобы показывать только
  два актуальных варианта.
- **`courier_cities`** — отдельный, более узкий справочник городов именно для курьерской доставки
  (используется в межгороде и в форме заказа для поля «Город (курьерская)»). Это **НЕ** то же
  самое, что общий справочник `cities`! Если город не появляется в выпадающем списке межгорода —
  сначала проверить, есть ли он вообще в `courier_cities` (был случай с городом Капчагай — просто
  отсутствовал в справочнике).

### RLS (Row Level Security) — ОЧЕНЬ ВАЖНО, тут уже были проблемы

На таблицах `orders` и `pickups` в какой-то момент накопилось множество дублирующихся, избыточных
RLS-политик (по 9–11 штук на таблицу, некоторые — буквально копии друг друга). Это создавало
реальную нагрузку на Postgres при каждом запросе (каждая политика проверяется на каждой строке) и
приводило к таймаутам при загрузке большого объёма заказов.

Решение, которое уже применено: политики упрощены до 3 штук на таблицу — `orders_select`,
`orders_insert`, `orders_update` (аналогично для `pickups`) — каждая просто `using (true)` /
`with check (true)`, то есть разрешено всё (реальных ограничений по ролям в этой системе
фактически не было и раньше, просто было много избыточных копий одного и того же правила).

**ГРАБЛИ, на которые уже наступали:** при этом упрощении забыли политику на `DELETE` — из-за этого
удаление заказов молча не работало несколько часов (заказ «удалялся», но на самом деле нет — RLS
блокировал, PostgREST не считал это ошибкой на клиенте). Это добавлено отдельно:

```sql
create policy "orders_delete" on public.orders for delete using (true);
create policy "pickups_delete" on public.pickups for delete using (true);
```

Если в будущем снова будете трогать RLS у какой-то таблицы — **всегда проверяйте, что есть все
4 операции** (select/insert/update/delete), а не только 3.

### Закрытие анонимного доступа (18.09.2026) — текущее состояние

Описанное выше упрощение до `using (true)` имело побочный эффект: правила были выданы роли
`public`, а не `authenticated`. Роль `public` в Postgres включает анонимов — то есть таблицы были
открыты по анонимному ключу из `index.html` **без входа в систему**. Ключ этот публичен по
определению (статический фронтенд, спрятать его невозможно), и защищать данные должен был именно RLS.

Проверено практикой: запрос без авторизации отдавал `orders` целиком — 26 267 строк с ФИО,
телефонами и адресами получателей. Так же были открыты `pickups`, `deleted_items` (корзина с
полными копиями удалённых заказов), `wh_reservations`, на чтение — `partners` и справочники
(`cities`, `courier_cities`, `delivery_types`, `districts`, `statuses`, `order_statuses`).
У `calc_partners`, `calc_global_settings` и `kelesu_messages` не было ни одного правила вообще.

**Что сделано:** все эти правила переписаны с `public` на `to authenticated`, анонимные `SELECT`
сняты, на трёх таблицах без правил включён RLS с доступом для вошедших. Для сотрудников ничего не
изменилось — доступ у них по-прежнему полный. Заодно убраны дубли правил у `inbound_*` и `partners`
(по два одинаковых на таблицу — та самая лишняя нагрузка из предыдущего раздела).

Проверка после правки: тот же анонимный запрос к `orders`, `cities`, `deleted_items` и
`kelesu_messages` возвращает 0 строк.

**Как это выглядит при проверке:** PostgREST отвечает `HTTP 200` с пустым результатом, а НЕ ошибкой
доступа. Поэтому «закрыто» и «таблица пустая» снаружи выглядят одинаково — сверяйтесь со счётчиком
(`Prefer: count=exact`), а не с кодом ответа.

**Ловушка с именами правил:** правило на `deleted_items` называлось `allow all for authenticated`,
но выдано было роли `public`. Название врало, и в интерфейсе Supabase это выглядит нормально.
При проверке смотрите колонку `roles` в `pg_policies`, а не имя правила.

Готовые SQL для этой правки и для отката лежат локально в `db/` (папка в `.gitignore` — файлы
намеренно не выкладываются в публичный репозиторий).

### Производительность / таймауты при загрузке

При росте `orders` до ~25 000+ строк начались таймауты при загрузке списка на клиенте. Причины
были две, обе уже решены:

1. Функция `dbList()` раньше запускала слишком много параллельных запросов страниц одновременно
   (по числу страниц, без ограничения) — браузер физически не может держать больше ~6 одновременных
   соединений к одному хосту, остальные вставали в очередь и не укладывались в таймаут.
   Решение: `dbList()` теперь грузит страницы пачками по 6 (`CONCURRENCY=6`), с таймаутом на
   страницу 30 секунд.
2. У проекта Supabase на маленьком тарифе (Micro/Small compute) закончился Disk IO burst budget —
   реальное дисковое троттлинг на инфраструктурном уровне, не имеющее отношения к коду. Тариф был
   повышен (Large, потом вернули на Medium после того, как выяснилось, что дело было в основном в
   пункте 1 выше). Если увидите таймауты снова — сначала проверьте Supabase → Settings →
   Infrastructure → есть ли предупреждение «Disk IO budget is being consumed» — и учтите, что
   размер ДИСКА (не только compute) тоже можно увеличить отдельно (лимит: не чаще 4 раз в 24 часа).

## 4. Как устроен сам код

### Структура файлов (с 18.09.2026)

Раньше всё лежало в одном `index.html` на 11 838 строк. Файл разрезан на части:

```
index.html                  ~160 строк — только разметка и подключения
css/app.css                 1136 строк — все стили
js/01-yadro.js               463 — Supabase-клиент, обёртки БД, права, вход
js/02-ket.js                 901 — интеграция с KET Logistic
js/03-uvedomleniya.js        324 — уведомления, лента активности, корзина
js/04-sortirovka.js          444 — модуль «Сортировка»
js/05-sklad-finansy.js      1906 — Склад и Финансы (в исходнике идут вперемешку)
js/06-mezhgorod.js           445 — отправки межгород
js/07-kalkulyaciya.js        847 — калькуляция
js/08-kabinet-partnera.js    525 — кабинет партнёра (вход по QR ?p=КОД)
js/09-dashbord.js            346 — дашборд
js/10-zayavki.js             607 — заявки на забор
js/11-zakazy.js             1721 — заказы
js/12-spravochniki.js        533 — справочники
js/13-polzovateli-roli.js    294 — пользователи и роли
js/14-poisk-dublei.js        205 — поиск дублей заказов
js/15-ket-vhodyashchie.js    999 — заказы из KET (входящие)
tools/refresh-versions.py         — обновление меток версий (см. ниже)
```

**Это обычные скрипты, а НЕ модули.** Никаких `import`/`export`. Все 604 глобальных имени
(434 функции + 170 переменных) по-прежнему общие, файлы выполняются строго в порядке подключения
в `index.html`. Для браузера пятнадцать файлов подряд — ровно то же, что один склеенный.
Резали механически, ни одной строки кода не меняли.

**Порядок подключения менять нельзя.** Файлы ссылаются друг на друга по именам, и если, например,
`11-zakazy.js` подключить раньше `01-yadro.js`, получите `Cannot access 'X' before initialization`
(раздел 9, пункт 2). Новый файл добавляйте в `index.html` на его место по порядку.

**Грабли, на которые наступили при нарезке:** совпадение склеенного текста с оригиналом ещё НЕ
означает, что нарезка корректна. Каждый `<script>` браузер разбирает отдельно, поэтому граница не
может проходить внутри функции или блока — иначе файл невалиден сам по себе. С первого раза так
сломались 7 файлов из 15 при полностью совпавшей склейке. Проверять надо и то, и другое:
склейку — на идентичность оригиналу, каждый файл — на разбор по отдельности.

**Метки версий обязательны.** Подключения выглядят как `js/11-zakazy.js?v=d953c90e` — это отпечаток
содержимого. Без его обновления браузеры будут отдавать пользователям старую версию из кеша.
После любой правки в `js/` или `css/`, перед коммитом:

```
python3 tools/refresh-versions.py
```

Скрипт заодно ругается, если файл лежит на диске, но забыт в `index.html`.

**У самого `index.html` метки нет и быть не может** — его адрес фиксирован. GitHub Pages отдаёт его
с `cache-control: max-age=600`, то есть до 10 минут после деплоя браузер вправе показывать старую
копию, даже не спрашивая сервер. Проверено на практике: сразу после деплоя браузер отдал старый
`index.html` из кеша (передано 0 байт) со ссылкой на старую версию CSS, хотя сервер уже отдавал
новую. Обычное обновление страницы не помогает — нужен `Cmd+Shift+R` (Windows: `Ctrl+F5`) или
подождать до 10 минут. Учитывайте это, когда проверяете деплой: «не применилось» чаще означает
«кеш», а не «сломалось».

### Как устроен сам код

- Навигация — по функциям `render...()` (например
  `renderOrders()`, `renderPartnersPage()`, `renderSorting()`) — каждая отвечает за один раздел меню.
- Общий объект состояния `S` (глобальный) держит всё загруженное из базы: `S.orders`, `S.pickups`,
  `S.cities`, `S.courier_cities`, `S.me` (текущий пользователь) и т.д.
- `render()` — главный роутер, вызывается при переключении вкладки. Внутри — `if(S.tab==='...')render...()`.
  **Важно:** если добавляете новый раздел с плавающей панелью пагинации внизу (см. `.orders-pager`
  в CSS) — не забудьте добавить вызов её функции очистки (`removeXxxPager()`) в самое начало
  `render()`, иначе панель «уезжает» вместе со скроллом на других вкладках при переключении (были
  похожие баги — плавающая панель от «Сортировки» не убиралась при переходе в «Историю изменений»).
- `dbList`, `dbInsert`, `dbUpdate`, `dbDelete` — общие обёртки над Supabase клиентом (`sb`), с
  логированием действий в `activity_log` и (для delete) бэкапом в `deleted_items`.
- **Realtime уже подключён глобально** (`sb.channel('jyldam-live')`, подписка на `orders`,
  `pickups`, `inbound_orders`) — любое изменение в базе (от кого угодно) автоматически прилетает
  всем открытым сессиям и обновляет `S.orders` и текущий экран (`scheduleRtRender`). Не нужно
  вручную дёргать перезагрузку данных после сохранения — но полезно знать, что экран обновляется
  САМ, даже без вашего участия, если кто-то другой что-то поменял.
- `.resp-table` — общий CSS-класс адаптивных таблиц (на мобильном превращаются в карточки через
  `data-label` атрибуты). **Важная деталь:** есть отдельное CSS-правило
  `.resp-table tr:not(.open) td{display:none}` для ДРУГИХ таблиц с раскрытием строки по клику
  (показывает только избранные подписи вроде «ID», «Статус» и т.п., пока строка не раскрыта). Если
  делаете НОВУЮ простую таблицу на основе `.resp-table` и не собираетесь использовать раскрытие —
  **обязательно добавляйте класс `open` каждой строке** (`<tr class="open">`), иначе на мобильном
  будут видны только «избранные» подписи из чужого списка, а не все ваши столбцы (баг именно так и
  проявлялся в «Сортировке»).

## 5. Модуль «Отправки межгород» (Intercity)

Курьерские заказы, которые нужно физически перевезти между городами (например, забрали в Астане,
а получатель — в Алматы), объединяются в **отправки** (коробки/грузы) с общей стоимостью перевозки,
которая потом делится на все заказы в коробке.

### Особые правила маршрутизации (зашиты в константы в коде)

- `INTERCITY_ALMATY_ALLOWED_CITIES` — со склада Алматы отправка идёт напрямую только в эти
  5 городов: Астана, Шымкент, Тараз, Кызылорда, Талдыкорган. Все остальные города для склада Алматы
  не должны появляться в выборе вообще (едут транзитом через Астану).
- `INTERCITY_VIA_ASTANA_CITIES` — список городов (Усть-Каменогорск, Семей, Костанай, Павлодар,
  Петропавловск, Караганда, Кокшетау, Сатпаев, Жезказган, Актобе, Уральск, Актау, Атырау), в
  которые со склада Астана заказы едут, ПОДТЯГИВАЯ по пути заказы, забранные в Алматы днём раньше
  (транзит через Астану). Логика вычисления «вчерашней» даты забора — в `ordersForIntercity()`.
- `INTERCITY_LIMITED_SCHEDULE_CITIES` — города с ограниченным расписанием отправки (Тараз,
  Костанай, Петропавловск) — не каждый день, поэтому в отправку «подтягиваются» также заказы,
  забранные в предыдущие дни-«доноры» (`intercityRollupDates()`).
- **Талдыкорган** — отдельный особый случай: для целей склада/сортировки (не для межгородней
  логики выше!) считается «своим» для Алматы — заказы, забранные в Талдыкоргане, физически привозят
  на склад Алматы (там нет отдельного склада). См. функцию `sortingCityId()` в разделе 6.
- Список городов в выпадающем меню при создании отправки строится динамически функцией
  `destCitiesForDate(date, whId)` — показывает город только если для него реально нашлись
  неотправленные заказы (`ordersForIntercity()`) на выбранную дату. Если ожидаемый город не
  появляется — сначала проверить, что он вообще есть в `courier_cities`, и есть ли реально
  подходящие заказы.

### Расчёт стоимости на 1 заказ

`per_order = Math.round(box_cost / кол-во заказов)` — округление может создавать небольшую
погрешность на уровне отправки (сумма всех `per_order` не всегда равна точно `box_cost`), но это
признанная, некритичная погрешность (порядка единиц тенге на отправку), **не стоит переделывать без
явного запроса**.

### Связь с «Калькуляцией» (раздел финансов)

Итоговая сумма межгорода в сводке Калькуляции считается **по дате самой отправки** (`ship_date` у
`shipments`), а НЕ по дате забора заказа (`pickup_date` у `orders`) — специально сделано так, чтобы
сходилось с суммой, которую показывает сам модуль «Отправки межгород». Причина расхождения, которая
уже была найдена и исправлена: из-за «дня-донора» (см. выше) заказ может быть забран в одном
календарном месяце, а сама отправка уйти уже в следующем — раньше это создавало разницу в сотни
тысяч тенге между двумя экранами. Реализация — переменные `freightByShipDate` / `freightByOrderDate`
/ `freightAdjust` в функции `renderCalcSummary()`.

Раздел непривязанных заказов (модалка «Показать непривязанные») показывает только заказы текущего
месяца — старые (прошлых месяцев) не показываются, они больше не актуальны для повседневной работы.

## 6. Модуль «Сортировка»

### Зачем он нужен

Раньше склад ждал, пока все менеджеры («забивальщики») закончат вносить данные по всей заявке, и
только потом получал единый «реестр» (Excel-выгрузку) для сортировки посылок по городам. Это
значит, что сортировка не начиналась, хотя часть заказов уже была готова. Модуль «Сортировка»
позволяет сразу, по мере готовности каждого отдельного заказа, определить, в какой город его класть.

### Как это работает

1. Кладовщик фотографирует физическую накладную на посылке (на них нет штрих-кода — только
   рукописный/печатный текст: ФИО, адрес, телефон).
   - Фото сжимается на телефоне перед отправкой (canvas, до 1400px по длинной стороне, JPEG
     качество 0.75) — это специально сделано для скорости: полноразмерное фото с телефона
     (несколько МБ) сильно замедляло и отправку, и саму работу ИИ. Функция `resizeImageForAI()`.
2. ИИ (`callAI`, модель `claude-sonnet-5`) распознаёт с фото ФИО/адрес/телефон, возвращает строгий JSON.
3. Система ищет совпадение среди сегодняшних, уже обработанных, ещё не отсортированных заказов
   (`findSortMatches()`) — сравнивает по телефону (самый надёжный признак, вес 100), ФИО
   (полное/частичное совпадение слов) и частично по адресу. Если совпадений несколько — выбирается
   с максимальным «весом», остальные предлагаются как альтернативы при «Это не тот заказ».
4. Если совпадение найдено — крупно показывается город назначения (`orderDestCityId()` — берёт
   `courier_city_id` или `city_id` в зависимости от типа доставки) + тип доставки + ФИО/адрес для сверки.
5. Кладовщик подтверждает («✅ Принял») — заказу выставляется `sorted_at` + `sorted_by_name`.
   Отсортированные заказы больше не попадают в поиск.
6. Если авто-поиск не сработал — ручной поиск по ФИО/телефону/номеру среди необработанных заказов
   (`renderSortManualPick()`).

### «Обработан» ли заказ — важное понятие

`orderIsProcessed(o)` = у заказа заполнено ФИО получателя И определён тип доставки (`delivery_id`).
Пока это не так — заказ существует (создан по заявке), но данные ещё не внесены, и показывать его
кладовщику рано (тип доставки, а с ним и город, может ещё измениться в процессе заполнения).
Необработанные заказы исключены из пула поиска в «Сортировке» — если совпадение не найдено, но
необработанные заказы за этот день/город есть, кладовщику показывается подсказка «⏳ возможно,
заказ ещё не обработан», а не просто «не найден».

Из-за этого понятия в основной форме заказа (`orderModal`) поле «Тип доставки» обязательно для
сохранения (без него не даст сохранить — проверка `if(!val('o_delivery'))...return false`), и
список вариантов в нём специально ограничен только «курьерская»/«почтовая» (регулярка
`/курьер|почт/i` по названию из справочника `delivery_types`, у которого могли быть лишние старые записи).

### Привязка кладовщика к городу — по городу ЗАБОРА, не назначения!

Это принципиально отличается от логики курьера (у курьера — привязка к конкретным заказам через
`my_order_courier_ids()`, это НЕ трогали и не меняли).

У кладовщика в его карточке сотрудника (`profiles.city_id`) можно указать город — тогда в
«Сортировке» он видит только заказы, которые **забрали** в этом городе (`o.pickup_city_id`), а НЕ
те, что едут в этот город. Логика: кладовщик работает на конкретном физическом складе (например,
склад Алматы), и на этот склад привозят посылки, забранные в Алматы (и в Талдыкоргане — см. особый
случай) — а его задача — определить, в КАКОЙ ГОРОД каждая из этих посылок должна дальше уехать
(это и есть сортировка).

Функция `sortingCityId(o)` — как раз про это: возвращает `pickup_city_id` заказа, с одним особым
случаем — если это Талдыкорган, приравнивает к городу Алматы (потому что там нет отдельного склада,
все посылки физически идут через склад Алматы). Если у сотрудника `city_id` не заполнен (обычно у
админа) — фильтра нет, видно все города сразу — плюс для админа/общего доступа показывается
разбивка по городам сверху (сколько заказов/принято в каждом городе отдельно).

### UI-детали модуля (на будущее, если будете его расширять)

- Наверху — плашки статистики: Заказов [за день] / Принято / Осталось, плюс вторая строка:
  🚚 Курьерских / 📮 Почтовых / Не обработано.
- Фильтр по дате (`sortingDate`, по умолчанию сегодня, максимум — сегодня) — полноценный «архив»:
  можно посмотреть статус любого прошлого дня.
- Ниже — таблица «Список заказов»: ФИО, Телефон, Тип доставки, Адрес, № заказа, Статус. Строки
  подсвечены зелёным (принят) / красным (не принят). Класс `open` у `<tr>` обязателен (раздел 4).
- Фильтр по статусу (все/принятые/непринятые) + поиск по ФИО/телефону/номеру (`sortingListFilter`,
  `sortingListSearch`) — поиск обновляет только `<tbody>` (`renderSortListOnly()`), не всю страницу,
  чтобы не сбрасывать фокус в поле ввода при каждой напечатанной букве. **Грабли, которые уже
  были:** при поиске по буквам (без цифр) старая версия кода считала совпадением ЛЮБОЙ телефон
  (пустая строка после удаления нецифровых символов — подстрока чего угодно) — из-за этого поиск по
  имени казался «не работающим» (показывал почти всё). Исправлено — проверка по телефону теперь
  применяется только если в запросе реально есть цифры.
- По клику на строку — можно вручную переключить статус принят/не принят (с подтверждением через
  `confirm()`), не дожидаясь фото.
- Пагинация на компьютере — такая же плавающая панель, как везде в CRM (`.orders-pager`, выбор
  кол-ва на странице, кнопки листания). На мобильном — «Показать ещё» (батчами).
- Доступ к разделу регулируется как обычный модуль в «Роли и права» (ключ `sorting` в массиве
  `MODULES` и в карте `fb` внутри `canMod()`) — по умолчанию виден только админу, пока явно не
  выдано разрешение роли.

## 7. Интеграция с Казпочтой (SOAP API)

Курьер получает трек-номер для почтовых заказов через кнопку «📮 Получить трек» — вызывает Edge
Function `kazpost-get-barcode`, которая обращается к SOAP-сервису Казпочты (`GetAddrLetter`, боевой
URL `http://rates.kazpost.kz/postratesprod/endpoints`).

Важные детали, если снова будете трогать эту интеграцию:

- `ProductCode=P103` («Посылка РК», стандарт) — рабочая, проверенная комбинация, даёт трек-номера с
  префиксом AP. Пробовали разные другие коды (P145 → EW, P109, P126A → не сработали вовсе) в
  попытке получить префикс QS — не вышло. Причина: диапазон QS выделяется Казпочтой заранее, вручную,
  под конкретный номер договора/ключ, и никак не подбирается через параметры запроса. Это
  подтвердилось и с чужой, отдельной системой — та же проблема с тем же ключом и договором. Ждём
  ответа от техподдержки Казпочты по этому вопросу.
- `MailCtg` выбирается автоматически по каждому заказу (не хардкодится в секретах) — если у заказа
  есть сумма к оплате (`order_sum`), используется категория 4 («с объявленной ценностью и наложенным
  платежом» — покрывает и страховку, и наложенный платёж одновременно) с реальной суммой в полях
  `DeclaredValue`/`CashOnDelivery`; если суммы нет — категория 3 («Обыкновенная»).
- `SndrCtg=2` (юрлицо) — добавили после того, как обнаружили это поле в ДРУГОЙ, отдельной панели
  (`admin.jyldam-logistics.kz`), где были более полные настройки.
- Все секреты (Key, DEA_NUMBER, БИН и т.д.) читаются с `.trim()` — раньше случайный пробел в конце
  значения секрета (например, `"P109 "`) приводил к непонятной внутренней ошибке базы Казпочты
  (ORA-06512) без внятного сообщения.

## 8. Прочие известные особенности и грабли

- **Даты и часовые пояса:** используется `localToday()` — специальная функция для получения ТЕКУЩЕЙ
  ЛОКАЛЬНОЙ даты, корректно работающая независимо от часового пояса браузера (компенсирует
  `getTimezoneOffset()`). НЕ использовать голый `new Date().toISOString().slice(0,10)` для
  «сегодня» — это UTC, может отличаться от локальной даты на несколько часов ближе к границе суток.
- **Загрузка фото пачкой** (в карточке заявки на забор) — сопоставляет фото «по порядку» только с
  заказами, у которых ещё нет ни одного фото (защита от случайной перезаписи). Если фото больше,
  чем пустых заказов — лишние остаются нераспределёнными (есть тост-уведомление об этом, но легко
  упустить из внимания). Для быстрого поиска, каким заказам не хватило фото — есть кнопка-фильтр
  «🔍 Без фото (N)» в той же карточке.
- **Кнопка «Сохранить»** в карточке заявки на забор продублирована наверху (рядом с «Загрузить фото
  пачкой» / «Создать ещё заказ»), чтобы не листать длинную ленту заказов до самого низа — нижняя
  (стандартная) кнопка скрыта через CSS, но обе вызывают одну и ту же логику сохранения/проверки.
- **Партнёры типа «Физ лицо Алматы/Астана»** — особый тип партнёра (проверка
  `isFizlicoName()`/`isFizlicoPartner()`, сравнение без учёта разных видов кавычек). Для таких
  партнёров в карточке заказа появляется отдельное поле «Адрес откуда забрали (физ. лицо)»
  (`fizlico_pickup_address`), которое специально НЕ выводится в общую таблицу заказов (только
  внутри карточки).

## 9. Что делать, если что-то не работает после деплоя

1. Проверить консоль браузера (веб-инспектор → Консоль) на ошибки JS.
2. Если ошибка вида `Cannot access 'X' before initialization` — значит, какая-то
   переменная/константа используется РАНЬШЕ своего объявления в файле (JS temporal dead zone) —
   искать, где объявлена константа, и либо переместить объявление выше, либо не ссылаться на неё в
   коде, который выполняется немедленно при загрузке (вне функций).
3. Если что-то визуально не отображается, а в HTML (через инспектор → Copy outerHTML) видно, что
   данные там есть — значит, дело в CSS, не в генерации разметки. Проверить `getComputedStyle()`
   конкретного элемента через консоль (`display`, `visibility`, `opacity`) — вероятно, что-то
   пересекается с общим правилом для другой таблицы (см. про `.resp-table` и класс `open` выше).
4. Если действие (сохранение/удаление) как будто срабатывает, но результат не сохраняется после
   обновления страницы — проверить RLS-политики в Supabase для соответствующей таблицы
   (`select * from pg_policies where tablename='...'`) — возможно, отсутствует политика на нужную
   операцию.

## 10. Практические детали работы с репозиторием

Обнаружено при работе, в исходный документ не входило:

- `index.html` в репозитории хранится с **CRLF** переводами строк, а копия, скачанная с GitHub,
  приходит с LF. Если скопировать скачанный файл поверх репозиторного, git покажет изменение
  **всех** строк вместо реальной правки. Редактировать нужно файл из репозитория, сохраняя его
  переводы строк.
- Не редактировать копию в `~/Downloads`: она уже один раз была перезаписана новой загрузкой и
  молча потеряла применённую правку. Рабочая копия — клон репозитория.
- `gh` установлен в `/opt/homebrew/bin/gh`, но не всегда есть в `PATH` — вызывать по полному пути.
- Проверить, что деплой реально доехал:
  `gh api repos/asembinov-cmyk/Jyldam-crm/pages/builds/latest --jq '.status + " " + .commit[0:7]'`

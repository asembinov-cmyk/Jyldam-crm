# Jyldam Logistics CRM — контекст проекта для разработки

Сводка всего, что нужно знать о проекте, прежде чем вносить изменения в код. Написана после
длительной сессии разработки — чтобы новый исполнитель (человек или ИИ) не наступал на те же
грабли повторно.

## 1. О компании и бизнесе

**Jyldam Logistics** — курьерская и логистическая компания, работает по Казахстану (в первую
очередь Астана и Алматы, плюс региональные города).

Компания тесно связана / фактически является частью **ТОО «QP Service»** — эта же организация
оказывает услуги фулфилмента для продавцов маркетплейсов (в первую очередь Wildberries): приём
товара от продавцов, хранение, маркировка, упаковка и доставка на склад маркетплейса.

Есть партнёрская компания **KET Logistic** — с ней есть интеграция (заказы можно отправлять в KET
прямо из CRM).

### Бизнес-модель в двух словах

1. **Партнёры** (магазины/продавцы) создают **заявки на забор** — «у меня N заказов, заберите».
   Заявка привязана к конкретному партнёру и городу.
2. Из заявки автоматически создаются N **заказов** (пустые «болванки» — без ФИО, адреса и т.д.) —
   их нужно наполнить данными.
3. **Менеджеры заказов («забивальщики»)** открывают заявку, фотографируют накладные/бланки на
   каждый заказ, вносят ФИО получателя, адрес, телефон, тип доставки (курьерская или почтовая —
   это принципиально разные ветки логики дальше).
4. Дальше заказ либо:
   - **Курьерская доставка** — развозится курьером внутри города, ИЛИ уезжает межгородним рейсом
     в другой город (см. раздел 5).
   - **Почтовая доставка** — отправляется через Казпочту (см. раздел 7).
5. Параллельно на складе **кладовщики** сортируют физические посылки по городам — для этого есть
   отдельный модуль «Сортировка» (раздел 6), который позволяет начинать сортировку сразу, не
   дожидаясь, пока все заказы в заявке будут «забиты».

## 3. Структура базы данных (основные таблицы)

- **`orders`** — заказы. Самая крупная и важная таблица (десятки тысяч строк, продолжает расти).
  Ключевые поля:
  - `code` — человекочитаемый номер заказа
  - `client`, `phone`, `address` — данные получателя
  - `delivery_id` — тип доставки (ссылка на `delivery_types`) — **обязательное** поле, без него
    заказ не считается «обработанным»
  - `courier_city_id` — город назначения ДЛЯ КУРЬЕРСКОЙ доставки
  - `city_id` — город назначения ДЛЯ ПОЧТОВОЙ доставки (**это два разных поля!** какое из них
    смотреть — зависит от `delivery_id`)
  - `pickup_city_id` — город, где посылку физически ЗАБРАЛИ (склад/партнёр) — это **НЕ** то же
    самое, что город назначения!
  - `pickup_id` — ссылка на заявку на забор, из которой создан заказ
  - `intercity_shipment_id`, `intercity_cost` — привязка к межгородней отправке (раздел 5)
  - `sorted_at`, `sorted_by_name` — отметка склада (модуль «Сортировка», раздел 6)
  - `track` — трек-номер (Казпочта или другой перевозчик)
  - `fizlico_pickup_address` — отдельный адрес забора, только для партнёров типа «Физ лицо
    Алматы/Астана» — не показывается в общем гриде, только в самой карточке заказа (этот столбец
    специально убирали из таблицы)
- **`pickups`** — заявки на забор от партнёров
- **`partners`** — партнёры/магазины (`tariff_post`, `tariff_courier` — тарифы)
- **`profiles`** — сотрудники CRM. У сотрудника может быть заполнено поле `city_id` — если
  заполнено, то в модуле «Сортировка» он видит только заказы своего города (раздел 6). У админа
  это поле обычно пустое → видит все города.
- **`shipments`** — межгородние отправки (раздел 5). Поля: `ship_date`, `warehouse_id`,
  `dest_city_id`, `box_cost` (стоимость всей отправки), `per_order` (стоимость на 1 заказ,
  `box_cost` делённая на кол-во заказов, округлённая), `order_ids` (jsonb-массив id заказов).
- **`deleted_items`** — «корзина». Перед любым `DELETE` из основной таблицы сначала сохраняется
  полный снимок строки сюда (функция `dbDelete` в коде) — на случай восстановления. Хранится
  30 дней. Смотреть в разделе CRM «Центр контроля» → «Корзина».
- **`delivery_types`** — справочник типов доставки. В нём могут быть лишние/старые записи — в
  форме заказа список специально отфильтрован регуляркой `/курьер|почт/i`, чтобы показывать только
  два актуальных варианта.
- **`courier_cities`** — отдельный, более узкий справочник городов именно для курьерской доставки
  (используется в межгороде и в форме заказа для поля «Город (курьерская)»). Это **НЕ** то же
  самое, что общий справочник `cities`! Если город не появляется в выпадающем списке межгорода —
  сначала проверить, есть ли он вообще в `courier_cities` (был случай с городом Капчагай — просто
  отсутствовал в справочнике).

### RLS (Row Level Security) — ОЧЕНЬ ВАЖНО, тут уже были проблемы

На таблицах `orders` и `pickups` в какой-то момент накопилось множество дублирующихся, избыточных
RLS-политик (по 9–11 штук на таблицу, некоторые — буквально копии друг друга). Это создавало
реальную нагрузку на Postgres при каждом запросе (каждая политика проверяется на каждой строке) и
приводило к таймаутам при загрузке большого объёма заказов.

Решение, которое уже применено: политики упрощены до 3 штук на таблицу — `orders_select`,
`orders_insert`, `orders_update` (аналогично для `pickups`) — каждая просто `using (true)` /
`with check (true)`, то есть разрешено всё (реальных ограничений по ролям в этой системе
фактически не было и раньше, просто было много избыточных копий одного и того же правила).

**ГРАБЛИ, на которые уже наступали:** при этом упрощении забыли политику на `DELETE` — из-за этого
удаление заказов молча не работало несколько часов (заказ «удалялся», но на самом деле нет — RLS
блокировал, PostgREST не считал это ошибкой на клиенте). Это добавлено отдельно:

```sql
create policy "orders_delete" on public.orders for delete using (true);
create policy "pickups_delete" on public.pickups for delete using (true);
```

Если в будущем снова будете трогать RLS у какой-то таблицы — **всегда проверяйте, что есть все
4 операции** (select/insert/update/delete), а не только 3.

### Закрытие анонимного доступа (18.09.2026) — текущее состояние

Описанное выше упрощение до `using (true)` имело побочный эффект: правила были выданы роли
`public`, а не `authenticated`. Роль `public` в Postgres включает анонимов — то есть таблицы были
открыты по анонимному ключу из `index.html` **без входа в систему**. Ключ этот публичен по
определению (статический фронтенд, спрятать его невозможно), и защищать данные должен был именно RLS.

Проверено практикой: запрос без авторизации отдавал `orders` целиком — 26 267 строк с ФИО,
телефонами и адресами получателей. Так же были открыты `pickups`, `deleted_items` (корзина с
полными копиями удалённых заказов), `wh_reservations`, на чтение — `partners` и справочники
(`cities`, `courier_cities`, `delivery_types`, `districts`, `statuses`, `order_statuses`).
У `calc_partners`, `calc_global_settings` и `kelesu_messages` не было ни одного правила вообще.

**Что сделано:** все эти правила переписаны с `public` на `to authenticated`, анонимные `SELECT`
сняты, на трёх таблицах без правил включён RLS с доступом для вошедших. Для сотрудников ничего не
изменилось — доступ у них по-прежнему полный. Заодно убраны дубли правил у `inbound_*` и `partners`
(по два одинаковых на таблицу — та самая лишняя нагрузка из предыдущего раздела).

Проверка после правки: тот же анонимный запрос к `orders`, `cities`, `deleted_items` и
`kelesu_messages` возвращает 0 строк.

**Как это выглядит при проверке:** PostgREST отвечает `HTTP 200` с пустым результатом, а НЕ ошибкой
доступа. Поэтому «закрыто» и «таблица пустая» снаружи выглядят одинаково — сверяйтесь со счётчиком
(`Prefer: count=exact`), а не с кодом ответа.

**Ловушка с именами правил:** правило на `deleted_items` называлось `allow all for authenticated`,
но выдано было роли `public`. Название врало, и в интерфейсе Supabase это выглядит нормально.
При проверке смотрите колонку `roles` в `pg_policies`, а не имя правила.

Готовые SQL для этой правки лежат локально в `db/` (папка в `.gitignore` — файлы
намеренно не выкладываются в публичный репозиторий).

### Повышение прав через profiles (19.09.2026)

Edge Function `set-password` проверяет права **правильно**: читает роль вызывающего из `profiles`
и пропускает либо администратора, либо обладателя `users.edit` — и то лишь для смены пароля
курьеру. Дыра была не в функции, а в том, на что она опирается: `profiles` и `roles` стояли с
правилом `ALL / to authenticated / true / true`, то есть **любой вошедший мог переписать любую
карточку, включая свою**.

Цепочка: курьер входит под своим аккаунтом → прямым запросом ставит себе `role = 'admin'` →
вызывает `set-password` → функция честно читает его карточку, видит «admin» → меняет пароль
администратору. Причём шаг 2 сам по себе уже открывает весь интерфейс: проверки `can()`/`canMod()`
в браузере читают ту же роль.

**Что сделано:** чтение обеих таблиц оставлено всем вошедшим (нужно при каждом входе, чтобы
вычислить собственные права), запись ограничена по образцу интерфейса — `roles` только админу,
`profiles` админу целиком, а обладателю `users.edit` только карточки курьеров и только с условием,
что курьером она и останется (`using` проверяет строку до правки, `with check` — после).

**Почему понадобились функции `jyldam_is_admin()` и прочие:** правило на `profiles`, которое само
читает `profiles`, уходит в бесконечную рекурсию. Функции объявлены `security definer` и читают
таблицы в обход правил. Если будете писать похожие политики — делайте так же.

**Попутно замечено и закрыто 26.09.2026:** вкладка «Роли и права» показывалась любому с правом
«Сотрудники», хотя запись в `roles` в базе admin-only. Менеджер открывал роль, выдавал себе тип
«Админ» — и получал отказ уже при сохранении: экран есть, толку нет. Теперь вкладка видна только
администратору (`isAdmin()` в `renderUsers`), а сохранённый `usersSub` при отсутствии прав
сбрасывается на «Сотрудников» — иначе открылся бы пустой раздел.

### Финансы, калькуляция и корзина (19–20.09.2026)

**Финансы и калькуляция** (`finance_*`, `calc_*`, 11 таблиц) закрыты по правам роли: правило
вызывает `jyldam_can(модуль, действие)`, а та читает `roles.perms` — те самые права, что
выставлены в разделе «Роли и права». Ничего отдельно настраивать не нужно: выдали роли доступ
к «Финансам» в интерфейсе — он появился и в базе. Администратору доступно всё всегда.

**Корзина** (`deleted_items`) — здесь правило намеренно НЕсимметричное, не «упрощайте» его:

| Операция | Кому | Почему |
|---|---|---|
| SELECT / UPDATE / DELETE | только админ | там полные снимки удалённых заказов с ФИО, телефонами, адресами |
| INSERT | любому вошедшему | снимок кладёт `dbDelete` при ЛЮБОМ удалении от ЛЮБОГО сотрудника |

Если закрыть и INSERT, ломается страховка, причём молча: `dbDelete` оборачивает запись снимка
в `try/catch` и при неудаче всё равно удаляет запись. Менеджер удалил заказ → снимок не
сохранился → восстанавливать нечего → никто не заметил.

Логику интерфейса здесь повторять было нельзя: доступ к «Центру контроля» в нём привязан
к праву на заказы (`fb` карта, `notify:'orders'`), а оно есть у курьеров — корзина осталась бы
открытой. Решение владельца от 20.09.2026: смотрит только администратор.

### Отложено: построчные правила для заказов

Курьер по-прежнему получает из базы ВСЕ заказы, а «только свои» отбирает браузер:
`S.orders.filter(o => myOrderCourierIds().includes(o.order_courier_id))`. То есть чужие ФИО,
телефоны и адреса уже лежат у него в памяти телефона.

Правило в базе выглядело бы так: курьеру отдавать только заказы, где `order_courier_id` ведёт
на его карточку в `order_couriers` (там `account_id` = аккаунт входа); персоналу — всё.

**Главная опасность — скорость.** `orders` читается при каждом входе каждого сотрудника, и
правило проверяется на каждой строке. Наивный подзапрос в `order_couriers` для каждой из
26 тысяч строк — это ровно тот сценарий, из-за которого уже были таймауты (см. выше). Делать
через `stable`-функцию, которая один раз возвращает список «моих карточек», и сравнение
`order_courier_id = any(...)`, плюс проверить индекс на `order_courier_id`.

Работа отложена владельцем 20.09.2026. Открытый вопрос, без которого не начинать: **что именно
курьер вправе менять в своём заказе** — сейчас у него право «редактирование заказов» целиком,
то есть формально и сумму, и тариф, и назначение другому курьеру.

**Что остаётся открытым:** любой вошедший сотрудник по-прежнему может прямым запросом прочитать
`finance_entries`, `calc_*` (ставки и нормативы), всю клиентскую базу в `orders` и корзину
`deleted_items`, а также изменить или удалить любой заказ. Проверки прав на эти модули живут
только в браузере. Это отдельная, бо́льшая задача: построчные правила (курьер видит только свои
заказы) и разделение доступа к финансам.

### Производительность / таймауты при загрузке

При росте `orders` до ~25 000+ строк начались таймауты при загрузке списка на клиенте. Причины
были две, обе уже решены:

1. Функция `dbList()` раньше запускала слишком много параллельных запросов страниц одновременно
   (по числу страниц, без ограничения) — браузер физически не может держать больше ~6 одновременных
   соединений к одному хосту, остальные вставали в очередь и не укладывались в таймаут.
   Решение: `dbList()` теперь грузит страницы пачками по 6 (`CONCURRENCY=6`), с таймаутом на
   страницу 30 секунд.
2. У проекта Supabase на маленьком тарифе (Micro/Small compute) закончился Disk IO burst budget —
   реальное дисковое троттлинг на инфраструктурном уровне, не имеющее отношения к коду. Тариф был
   повышен (Large, потом вернули на Medium после того, как выяснилось, что дело было в основном в
   пункте 1 выше). Если увидите таймауты снова — сначала проверьте Supabase → Settings →
   Infrastructure → есть ли предупреждение «Disk IO budget is being consumed» — и учтите, что
   размер ДИСКА (не только compute) тоже можно увеличить отдельно (лимит: не чаще 4 раз в 24 часа).

Раньше всё лежало в одном `index.html` на 11 838 строк. Файл разрезан на части:


**Это обычные скрипты, а НЕ модули.** Никаких `import`/`export`. Все 604 глобальных имени
(434 функции + 170 переменных) по-прежнему общие, файлы выполняются строго в порядке подключения
в `index.html`. Для браузера пятнадцать файлов подряд — ровно то же, что один склеенный.
Резали механически, ни одной строки кода не меняли.

**Порядок подключения менять нельзя.** Файлы ссылаются друг на друга по именам, и если, например,
`11-zakazy.js` подключить раньше `01-yadro.js`, получите `Cannot access 'X' before initialization`
(раздел 9, пункт 2). Новый файл добавляйте в `index.html` на его место по порядку.

**Грабли, на которые наступили при нарезке:** совпадение склеенного текста с оригиналом ещё НЕ
означает, что нарезка корректна. Каждый `<script>` браузер разбирает отдельно, поэтому граница не
может проходить внутри функции или блока — иначе файл невалиден сам по себе. С первого раза так
сломались 7 файлов из 15 при полностью совпавшей склейке. Проверять надо и то, и другое:
склейку — на идентичность оригиналу, каждый файл — на разбор по отдельности.

**Метки версий обязательны.** Подключения выглядят как `js/11-zakazy.js?v=d953c90e` — это отпечаток
содержимого. Без его обновления браузеры будут отдавать пользователям старую версию из кеша.
После любой правки в `js/` или `css/`, перед коммитом:

```
python3 tools/refresh-versions.py
```

Скрипт заодно ругается, если файл лежит на диске, но забыт в `index.html`.

**У самого `index.html` метки нет и быть не может** — его адрес фиксирован. GitHub Pages отдаёт его
с `cache-control: max-age=600`, то есть до 10 минут после деплоя браузер вправе показывать старую
копию, даже не спрашивая сервер.

**С 02.10.2026 CRM говорит об этом сама.** `checkAppVersion()` в `js/01-yadro.js` раз в десять
минут (и через 8 секунд после входа) запрашивает `index.html` с `cache:'no-store'`, сравнивает
отпечатки ВСЕХ подключённых файлов с теми, что реально загружены на странице, и при различии
показывает полосу «Вышла новая версия CRM» с кнопкой. Кнопка перезагружает с другим адресом
(`?r=<время>`), потому что обычная перезагрузка может снова взять `index.html` из кеша.

Сделано после третьего за ночь разбора «правка не применилась»: правка каждый раз была
выложена, а у человека на экране жил старый скрипт. По экрану это неотличимо от поломки,
и каждый раз это стоило получаса.

Сравниваются именно ВСЕ отпечатки сразу: если поменялся только один файл, отпечаток
остальных не меняется, и проверка по одному файлу ничего бы не заметила. Проверено на практике: сразу после деплоя браузер отдал старый
`index.html` из кеша (передано 0 байт) со ссылкой на старую версию CSS, хотя сервер уже отдавал
новую. Обычное обновление страницы не помогает — нужен `Cmd+Shift+R` (Windows: `Ctrl+F5`) или
подождать до 10 минут. Учитывайте это, когда проверяете деплой: «не применилось» чаще означает
«кеш», а не «сломалось».

### Как устроен сам код

- Навигация — по функциям `render...()` (например
  `renderOrders()`, `renderPartnersPage()`, `renderSorting()`) — каждая отвечает за один раздел меню.
- Общий объект состояния `S` (глобальный) держит всё загруженное из базы: `S.orders`, `S.pickups`,
  `S.cities`, `S.courier_cities`, `S.me` (текущий пользователь) и т.д.
- `render()` — главный роутер, вызывается при переключении вкладки. Внутри — `if(S.tab==='...')render...()`.
  **Важно:** если добавляете новый раздел с плавающей панелью пагинации внизу (см. `.orders-pager`
  в CSS) — не забудьте добавить вызов её функции очистки (`removeXxxPager()`) в самое начало
  `render()`, иначе панель «уезжает» вместе со скроллом на других вкладках при переключении (были
  похожие баги — плавающая панель от «Сортировки» не убиралась при переходе в «Историю изменений»).
- `dbList`, `dbInsert`, `dbUpdate`, `dbDelete` — общие обёртки над Supabase клиентом (`sb`), с
  логированием действий в `activity_log` и (для delete) бэкапом в `deleted_items`.
- **Realtime уже подключён глобально** (`sb.channel('jyldam-live')`, подписка на `orders`,
  `pickups`, `inbound_orders`) — любое изменение в базе (от кого угодно) автоматически прилетает
  всем открытым сессиям и обновляет `S.orders` и текущий экран (`scheduleRtRender`). Не нужно
  вручную дёргать перезагрузку данных после сохранения — но полезно знать, что экран обновляется
  САМ, даже без вашего участия, если кто-то другой что-то поменял.
- `.resp-table` — общий CSS-класс адаптивных таблиц (на мобильном превращаются в карточки через
  `data-label` атрибуты). **Исправлено 20.09.2026:** раньше правило
  `.resp-table tr:not(.open) td{display:none}` действовало на ВСЕ такие таблицы, хотя раскрытие
  строки по клику есть ровно в двух — «Заказы» и «Заявки на забор». Любая другая таблица на
  мобильном превращалась в пустые полоски: ячейки скрывались, а показывались лишь те, чьи
  подписи перечислены в правиле («ID», «Статус», «Город»…), а у чужих таблиц таких подписей нет.
  Так ломались «История изменений» и «Непривязанные заказы»; раньше это же ловили в «Сортировке»
  и лечили добавлением `open` каждой строке — лечение симптома, а не причины.

  Теперь правила сворачивания привязаны к отдельному классу **`.resp-collapse`**, он стоит только
  на таблицах заказов и заявок. **Обычной таблице ничего добавлять не нужно** — она по умолчанию
  показывает все ячейки. Делаете таблицу со сворачиванием — ставьте `resp-collapse` рядом с
  `resp-table`.

## 5. Модуль «Отправки межгород» (Intercity)

Курьерские заказы, которые нужно физически перевезти между городами (например, забрали в Астане,
а получатель — в Алматы), объединяются в **отправки** (коробки/грузы) с общей стоимостью перевозки,
которая потом делится на все заказы в коробке.

### Особые правила маршрутизации (зашиты в константы в коде)

- `INTERCITY_ALMATY_ALLOWED_CITIES` — со склада Алматы отправка идёт напрямую только в эти
  5 городов: Астана, Шымкент, Тараз, Кызылорда, Талдыкорган. Все остальные города для склада Алматы
  не должны появляться в выборе вообще (едут транзитом через Астану).
- `INTERCITY_VIA_ASTANA_CITIES` — список городов (Усть-Каменогорск, Семей, Костанай, Павлодар,
  Петропавловск, Караганда, Кокшетау, Сатпаев, Жезказган, Актобе, Уральск, Актау, Атырау), в
  которые со склада Астана заказы едут, ПОДТЯГИВАЯ по пути заказы, забранные в Алматы днём раньше
  (транзит через Астану). Логика вычисления «вчерашней» даты забора — в `ordersForIntercity()`.
- `INTERCITY_LIMITED_SCHEDULE_CITIES` — города с ограниченным расписанием отправки (Тараз,
  Костанай, Петропавловск) — не каждый день, поэтому в отправку «подтягиваются» также заказы,
  забранные в предыдущие дни-«доноры» (`intercityRollupDates()`).
- **Талдыкорган** — отдельный особый случай: для целей склада/сортировки (не для межгородней
  логики выше!) считается «своим» для Алматы — заказы, забранные в Талдыкоргане, физически привозят
  на склад Алматы (там нет отдельного склада). См. функцию `sortingCityId()` в разделе 6.
- Список городов в выпадающем меню при создании отправки строится динамически функцией
  `destCitiesForDate(date, whId)` — показывает город только если для него реально нашлись
  неотправленные заказы (`ordersForIntercity()`) на выбранную дату. Если ожидаемый город не
  появляется — сначала проверить, что он вообще есть в `courier_cities`, и есть ли реально
  подходящие заказы.

### Кто видит «Отправки межгород»

**Раздел по умолчанию только для администратора.** В карте `fb` внутри `canMod()` у него
стоит `intercity:null`, а это значит «только админ, пока право не выдано явно». Сотруднику,
который реально собирает коробки, право нужно выдать в «Роли и права» — иначе он не увидит
ни пункта меню, ни отправок. То же касается `cash`, `sorting`, `filling`, `finance`, `calc`,
`history`.

**У роли с базовым типом «Курьер» меню собиралось из жёсткого списка** — «Мои заборы» и
«Мои заказы», — и выданные права в нём не участвовали вовсе. Выдали заборщику «Межгород» —
в меню он не появлялся, и понять почему было нельзя. Исправлено 26.09.2026: курьеру теперь
показываются и модули, выданные его роли ЯВНО (`S.myPerms[ключ].view`).

Берётся именно явное право, без запасной карты `fb` из `canMod()`: та отдаёт закрытые
разделы администратору, и по ней курьер получил бы лишнее.

Разделение остаётся прежним: **базовый тип ограничивает ДАННЫЕ, права — НАБОР модулей.**
В «Заказах» курьер по-прежнему видит только свои (`visibleOrders`), а внутри «Межгорода»
видит все заказы — иначе коробку не собрать. `visibleOrders()` вызывается ровно в одном
месте, в гриде заказов, и на другие модули не влияет.

Список отправок **ничем по сотруднику не фильтруется** — видно либо всё, либо ничего.
Поэтому «у меня есть, а у него нет» — это всегда доступ, фильтры или незагруженные данные,
и с 26.09.2026 пустой экран говорит, что именно: нет права (с указанием, где выдать),
не загрузились отправки, или всё скрыто фильтрами (с кнопкой сброса и числом отправок).

Для различения «отправок нет» и «не смогли прочитать» `S.shipments` при ошибке ставится
в `null`, а не в `[]` — иначе обе беды выглядели одинаково.

### Два плеча одного заказа (26.09.2026)

**Транзитный заказ едет в ДВУХ коробках и платит ДВЕ доли.** Это главное в модуле, и в
первой версии этой записи было написано наоборот — владелец поправил.

Заказ забрали в Алматы 25-го, получатель в Актобе:

1. 25-го Нурлан отправляет коробку **Алматы → Астана**. В ней едут и заказы с назначением
   Астана, и все транзитные — этот в том числе. Он берёт долю этой коробки.
2. 26-го он уже в Астане. Ермек собирает **Астана → Актобе**: заказы забора Астаны за 26-е
   ПЛЮС алматинские за 25-е. Тот же заказ выходит второй раз и берёт долю второй коробки.

**Следствие первое: «уже отправлен» считается ПО ПЛЕЧУ.** Раньше стояла проверка
`if(o.intercity_shipment_id)return false` — и второе плечо не наступало никогда: после
первой же коробки заказ исчезал из выдачи навсегда. Ровно поэтому и копились непривязанные.
Теперь членство берётся из самих отправок (`shipments.order_ids`), функция
`orderShippedFrom(id, городОтправления)`: уехал из Алматы — не предлагаем в алматинские
отправки, но в астанинской обязан появиться.

**Следствие второе: `orders.intercity_cost` — это СУММА долей**, а не доля одной коробки.
Считает `orderFreightTotal()`, записывает `syncOrderFreight()`. Записать долю текущей
коробки напрямую нельзя: второе плечо затёрло бы первое, и половина перевозки исчезла бы
из расчёта. Калькуляция и ежедневный отчёт читают это одно поле — их менять не пришлось.
При удалении коробки поле тоже не обнуляется, а пересчитывается по оставшимся.

**Следствие третье: коробка Алматы → Астана везёт и транзитные заказы.** Раньше в неё
попадали только заказы с назначением «Астана», то есть первого плеча в системе не было
вовсе: Нурлан возил транзит даром, а вся стоимость ложилась на астанинские заказы.
Признак — `isFirstLeg` в `ordersForIntercity`.

**Окно — ровно сутки, и расширять его не надо.** Забор сегодня уезжает сегодня; транзитный
подтягивается ровно вчерашний. 26.09.2026 пробовали расширить до месяца — владелец отменил:
накопившееся разбирается отдельным инструментом, а не подмешиванием в свежие коробки.
Дни-доноры для городов с редким расписанием (`intercityRollupDates`) на месте.

**Транзитных маршрутов два, и они заданы таблицей `INTERCITY_TRANSIT_RULES`,**
а не зашиты под одну Астану:

| Забрали в | Пересадка | Куда |
|---|---|---|
| Алматы | Астана | всё, кроме разрешённых для Алматы: Актобе, Семей, Темиртау, Балхаш… |
| Астана | Алматы | Талдыкорган, Конаев, Каскелен, Капчагай |

Правило работает в обе стороны сразу: коробка до пересадки везёт и «свои» заказы, и
транзитные (`firstLegRule`), а коробка с пересадки подтягивает вчерашние заказы города
отправления (`secondLegRule`). Напрямую туда, куда положен транзит, склад отправить не
может — `intercityRuleFor(склад, город)` возвращает правило, и выдача пуста: из Астаны
больше нельзя создать коробку в Талдыкорган, как из Алматы нельзя в Актобе.

Новый транзитный маршрут добавляется одной строкой в таблицу правил. Всё остальное —
число плеч, сумма долей, разбор накопившегося, список непривязанных — считается от неё.

**Через Астану идёт ВСЁ, кроме городов из `INTERCITY_ALMATY_ALLOWED_CITIES`** — правило, а
не перечень (`intercityViaAstana()`). Перечень из тринадцати городов оставлен справкой:
город вне его попадал в мёртвую зону — с Алматы не отправить, из Астаны не подтянуть.
В список разрешённых кроме Астаны, Шымкента, Тараза, Кызылорды и Талдыкоргана добавлены
пригороды Алматы: Каскелен, Конаев и Капчагай — иначе они ехали бы крюком в 2400 км.

**Город склада ищется по названию** (`shipmentCityName`): сначала точным совпадением с
городом, потом вхождением. Склад «Склад Астана» при строгом равенстве городу не
соответствовал, и отправка молча выпадала из подбора.

### Список отправок: страницы и фильтры (02.10.2026)

**Пагинация** — `icPage` + `IC_PER_PAGE` (50), панель под таблицей, как в «Истории
изменений». Страница приводится в границы ПОСЛЕ фильтрации, и любая правка фильтра
возвращает на первую: иначе после сужения выборки человек остаётся на пятой странице, а
строк там уже нет, и таблица выглядит пустой.

**Фильтр по отправителю** (`sender_name`) — список собирается из самих отправок, по
алфавиту. **«Сегодня»** ставит обе границы дат на сегодняшний день, **«Все даты»** снимает
ТОЛЬКО даты: склад, город, транспорт и отправитель при этом остаются выбранными — иначе
кнопка работала бы как «сбросить всё», а она для этого не нужна, рядом есть «Сбросить».

**Полоса `ic-totals` убрана:** те же три числа теперь в синей плашке общей шапки, и держать
их на экране дважды незачем.

### Разбор накопившегося

Кнопка «Разложить по уже созданным отправкам» в модалке непривязанных. Для каждого
недостающего плеча ищется самая ранняя подходящая отправка; у транзитного заказа плеч два,
и он может добавиться сразу в две коробки.

**Период задаётся прямо в окне** — поле «Заказы забором с», по умолчанию первое число
текущего месяца; предпросмотр пересчитывается на месте, окно не закрывается. Отправка
ищется в пределах `INTERCITY_BACKLOG_MAX_DAYS` (45 дней) после забора — к ежедневной
работе это отношения не имеет, там окно ровно сутки.

**Дата по умолчанию считается ЛЕНИВО, а не при загрузке файла.** `localToday()` объявлена
в `js/10-zayavki.js`, то есть ПОЗЖЕ этого файла, и вызов на верхнем уровне роняет весь
скрипт: функции остаются (они всплывают), а переменные ниже — нет, и получается
«Cannot access before initialization». Наступали на это уже дважды, см. раздел 9, пункт 2.

**Запись идёт пачками, а не по заказу.** Сначала обновляются сами отправки (их немного),
потом одним проходом доли: заказы группируются по одинаковой паре «сумма + последняя
коробка» и правятся запросом `update ... in (id, id, …)` по сто штук. Поштучно было по два
обращения на заказ плюс запись в журнал на каждое — на трёхстах заказах больше тысячи
запросов подряд, и кнопка выглядела мёртвой. Замер на 300 заказах в двух плечах: стало
2 запроса по отправкам и 3 групповых по заказам. Пока идёт запись, в окне видно «Пересчитываю
доли: N из M», а кнопка заблокирована.

Это **меняет деньги задним числом** и по-другому не может: стоимость коробки делится на
число заказов. Поэтому сначала показывается, что именно изменится, и только потом
применяется. Пересчитываются ВСЕ заказы коробки, а не только добавленные.

Если не разложилось — модалка называет причину по пунктам: нет отправки в этот город, склад
не сопоставился, все отправки раньше дня забора, маршрут не тот.

### Расчёт стоимости на 1 заказ

`per_order = Math.round(box_cost / кол-во заказов)` — округление может создавать небольшую
погрешность на уровне отправки (сумма всех `per_order` не всегда равна точно `box_cost`), но это
признанная, некритичная погрешность (порядка единиц тенге на отправку), **не стоит переделывать без
явного запроса**.

### Связь с «Калькуляцией» (раздел финансов)

Итоговая сумма межгорода в сводке Калькуляции считается **по дате самой отправки** (`ship_date` у
`shipments`), а НЕ по дате забора заказа (`pickup_date` у `orders`) — специально сделано так, чтобы
сходилось с суммой, которую показывает сам модуль «Отправки межгород». Причина расхождения, которая
уже была найдена и исправлена: из-за «дня-донора» (см. выше) заказ может быть забран в одном
календарном месяце, а сама отправка уйти уже в следующем — раньше это создавало разницу в сотни
тысяч тенге между двумя экранами. Реализация — переменные `freightByShipDate` / `freightByOrderDate`
/ `freightAdjust` в функции `renderCalcSummary()`.

Раздел непривязанных заказов (модалка «Показать непривязанные») показывает только заказы текущего
месяца — старые (прошлых месяцев) не показываются, они больше не актуальны для повседневной работы.

## 5b. Базовый тариф компании и доля менеджера (26.09.2026)

Компания держит свою цену доставки, а менеджер по продажам договаривается с партнёром
выше. Разница — его заработок. Пример владельца: база 1690, партнёр платит 1800, 110 ₸
идут менеджеру.

**Базовый тариф** — два норматива в «Расходах компании»: `base_post` и `base_courier`.
Хранятся по месяцам, как всё остальное: подняли цену с октября — сентябрь считается
по-старому.

**Надбавка считается от ТАРИФА ПАРТНЁРА, а не от суммы заказа.** Сумма растёт от размера
пакета (M +500, L +1500) и от перевеса, а договорённость у менеджера — на базовую цену,
и с этих доплат его доля не идёт. Решение владельца, подтверждено явно.

**Надбавка — статья расхода, а выручка остаётся полной.** Прибыль выходит та же, что если
считать выручкой базовый тариф, но так видно и что партнёр платит, и сколько из этого ушло
менеджеру. Второй способ прячет обе цифры.

**Только если у заказа указан менеджер** (`orders.sales_id`). Без него разница остаётся
прибылью компании.

Функция — `salesMarginFor(o, period)` в `js/07-kalkulyaciya.js`. Партнёр заказа берётся
своим полем, а если пусто — по названию отправителя (`findPartnerByNameLoose`): у заказов,
созданных пачкой из заявки, `partner_id` часто не заполнен. Если базовый тариф не задан,
надбавка не считается вовсе — не с чем сравнивать.

В «Общей сводке» — блок **«Заработок менеджеров по продажам»**: по каждому заказов,
надбавка (и сколько это на заказ), ставка за заказ и оклад. Менеджеры с окладом показаны,
даже если заказов за месяц не было: оклад им всё равно начислен.

**Надбавка запоминается в самом заказе** — колонка `orders.sales_margin`. Разные партнёры
договариваются на разные суммы (один 1750, другой 1720), и тариф со временем поднимают —
без снимка подъём пересчитал бы задним числом уже закрытые месяцы. `salesMarginFor()`
сначала смотрит снимок и только при пустом считает от тарифа. У старых заказов снимка нет,
они считаются как раньше.

**Снимок берётся при СОХРАНЕНИИ карточки, а не при создании «болванки».** Болванки из заявки
рождаются курьерскими, тип доставки выбирают позже — снимок ушёл бы от курьерского тарифа
вместо почтового (проверено: 200 ₸ там, где верно 160). У существующего заказа снимок не
перезаписывается. При загрузке из Excel тип известен сразу, поэтому там снимок ставится
прямо при создании.

**Партнёр внутри карточки ищется через `cardPartner()`** — он объявлен на уровне всей
`orderModal`. Раньше такой поиск (`findPartner`) жил внутри блока `if(!ro)`, и сохранение
падало на нём с `ReferenceError`: `const` виден только в своём блоке. Нужен партнёр в
сохранении — берите `cardPartner()`.

**Формула продублирована в ежедневном отчёте** — как и весь расчёт, см. раздел 6d.
Совпадение проверено прогоном на одних данных: 17 заказов дали 175 864 ₸ расходов
и в Калькуляции, и в отчёте.

### Фиксированная доля менеджера у отдельных партнёров (01.10.2026)

Правило «всё, что партнёр платит сверх базового, — заработок менеджера» годится не для
всех. Есть партнёры с тарифом 2000 при базовых 1690, у которых менеджеру по договорённости
идут те же 110, а остальные 200 — цена, которую держит компания. По общей формуле менеджеру
уходила вся разница, и **прибыль по таким партнёрам занижалась на 200 ₸ с каждого заказа**.

В карточке партнёра появилось поле **«Доля менеджера по продажам с заказа»**
(`partners.sales_margin_fixed`, `db/22`):

| Поле | Что считается |
|---|---|
| пусто | как раньше: тариф партнёра − базовый тариф компании |
| заполнено | ровно эта сумма, остаток остаётся прибылью компании |

**Порядок в `salesMarginFor` важен:** снимок в заказе → фиксированная доля партнёра →
разница с базовым тарифом. Снимок первым, потому что он уже учёл всё это в момент
сохранения заказа.

**ПОЛЯ ДВА, ПО ОДНОМУ НА ТИП ДОСТАВКИ** — `sales_margin_fixed` (почта, `db/22`) и
`sales_margin_courier` (курьер, `db/23`). Сначала поле было одно и действовало на оба типа;
владелец поправил: доли по почте и по курьеру разные, и одно число платило бы по курьеру то,
чего там не было. Через полчаса он же попросил добавить курьерскую сразу, «чтобы потом не
делать дважды».

**Имя `sales_margin_fixed` историческое — это ПОЧТОВАЯ доля.** Переименовать её в
`sales_margin_post` задним числом нельзя: пока миграция не выполнена, сохранение карточки
партнёра сломалось бы целиком (поле ушло бы в запрос под именем, которого в базе нет).
Читать обе доли — через `partnerFixedMargin(pt, courier)`, а не по именам колонок.

**Проверки готовности РАЗДЕЛЬНЫЕ** — `salesFixedReady()` и `salesCourierReady()`: файлы
`db/22` и `db/23` выполняют в разное время, и поле шлётся в запрос, только когда колонка
есть. Вторая колонка без первой тоже работает.

**Зачем курьерская доля вообще нужна, если по курьеру «ничего»:** базовый курьерский тариф
3000 стоит ровно столько же, сколько курьерский тариф у 457 партнёров из 468. Разница
«тариф − базовый» по курьеру структурно нулевая — сколько бы менеджер ни договорился, она не
насчитает ничего. Фиксированная доля — единственный способ ему что-то начислить.

**Поле нужно трём группам партнёров, и доля у всех одна — 110 ₸** (данные на 01.10.2026):
тариф 2000 — 74 партнёра; тариф 1800 — 16 (у них разница и так 110); **тариф 0** — такие
платят раз в месяц по счёту, по факту те же 1800–2000, и разница с базовым по ним никогда
не насчитает ничего. Последняя группа и есть главная причина, почему поле не выводится из
тарифа.

**Ноль — это «менеджеру ничего», а не «считай по разнице».** Проверка именно на пустоту
поля (`!=null && !==''`), а не на правдивость: партнёр, по которому менеджер не получает
ничего, иначе молча считался бы по общей формуле.

**Поле шлётся в запрос, только когда колонка в базе есть** (`salesFixedReady()`). Без
проверки PostgREST отклонил бы ВЕСЬ `update`, и карточка партнёра перестала бы сохраняться
целиком — те же грабли, что с новым нормативом в `calc_settings` (раздел 8).

**На уже созданные заказы поле само не действует** — доля записана снимком в
`orders.sales_margin`. Поэтому при изменении поля карточка СПРАШИВАЕТ, пересчитать ли её в
существующих заказах (`syncPartnerSalesMargin`), и пересчитывает **ТОЛЬКО ТЕКУЩИЙ МЕСЯЦ**:
«старые за прошлые месяцы не менять, считать с октября» — требование владельца. Прошлые
месяцы закрыты и по ним выплачено, а заказы текущего месяца, созданные ДО того как поле
заполнили, иначе остались бы со старым снимком, и месяц посчитался бы наполовину
по-старому. Месяц определяется по дате забора, а при её отсутствии по дате создания — как
в `ordersInOrderMonth`.

Поставили число — оно пишется в заказы партнёра за этот месяц с указанным менеджером;
очистили поле — снимок СТИРАЕТСЯ, и доля снова считается на лету: «правильное» число пачкой
не записать, оно у каждого заказа своё (тип доставки и базовый тариф того месяца).

**Пересчёт идёт ОТДЕЛЬНО по каждому типу доставки**, двумя запросами: доли разные, одним
числом их не записать. Типы перечисляются СПИСКОМ id (`.in('delivery_id', …)`), а не
отрицанием: заказ без типа доставки не должен попасть ни в ту, ни в другую пачку — снимок
ему проставят при сохранении карточки, когда тип наконец выберут. Правится только та
сторона, которую реально меняли: поправили курьерскую — почтовых заказов запрос не касается.

Берутся только заказы с заполненным `partner_id` — у созданных пачкой из заявки он часто
пуст, там партнёр определяется по названию отправителя (`orderPartnerObj`). То же
ограничение у соседнего пересчёта менеджера и обработчика.

**В ежедневном отчёте правило продублировано** (раздел 6d) — и там же вскрылось старое
расхождение: `salesMargin` в функции **не читал снимок `orders.sales_margin` вовсе**, поля
не было даже в списке запрашиваемых колонок. То есть после любого подъёма тарифа партнёру
отчёт считал долю по новому тарифу, а экран «Калькуляция» — по снимку, и они расходились по
всем прошлым заказам этого партнёра. Теперь снимок читается первым, как в CRM.

Партнёры в отчёте запрашиваются с `sales_margin_fixed` и запасным вариантом без неё: пока
`db/22` не выполнен, запрос с несуществующей колонкой уронил бы ВЕСЬ отчёт в 23:00.

В списке партнёров добавлена колонка «Доля менеджера» — видно, у кого зафиксировано, а у
кого «по разнице», не открывая карточек.

**ОТДЕЛЬНО: базовый тариф почты в нормативах за октябрь стоит 0**, то есть доля менеджера
по почте не начисляется вовсе — в `salesMarginFor` стоит `if(!base) return 0`, сравнивать не
с чем. Ноль здесь означает не «ноль тенге», а «норматив не заполнен». Пока три группы выше
закрыты фиксированной долей, базовый тариф на деньги почти не влияет: 375 партнёров платят
1500, то есть НИЖЕ любого разумного базового, и разница по ним всё равно ноль. Единственное,
что он меняет, — три партнёра с тарифом 1700 (при базовом 1690 это 10 ₸ с заказа).

**Справка в `db/22` сначала врала.** Блок «кому ставить» считал чистую арифметику
«тариф − базовый» и при незаполненном базовом показывал, будто менеджеру уходит ВЕСЬ тариф
(2000 ₸ с заказа). Правило «базовый не задан — не считаем» живёт только в коде. Блок
переписан: теперь он пишет «не считается — базовый тариф почты не задан», а перед ним стоит
блок, показывающий базовые тарифы по всем месяцам.

## 5c. Цены размеров пакета и перевеса (26.09.2026)

Надбавки за размер пакета и за перевес больше не зашиты в коде — правятся в CRM:
**«Калькуляция» → «Размеры пакетов и перевес»**. Размер S по-прежнему равен тарифу
партнёра из его карточки; M и L считаются от него с надбавкой.

**Лежат в ОТДЕЛЬНОЙ таблице `pricing_settings`, а не в `calc_settings` — это главное.
** `calc_settings` читают только по праву «Калькуляция» (db/4), а размер пакета выбирает
менеджер заказов, у которого этого права нет. Положи мы цены туда — у него надбавки молча
стали бы нулевыми, и заказ размера L ушёл бы по цене S. Поэтому читать `pricing_settings`
может любой вошедший, писать — только по праву «Калькуляция». Зарплаты и фонды остаются
закрытыми, как были.

**Без периода, в отличие от остальных нормативов.** Сумма заказа пишется в сам заказ при
сохранении, поэтому правка действует только на новые заказы, а прошлые месяцы не
пересчитываются в принципе — месячные версии тут не нужны.

**Пустое поле — это «как в коде», а не ноль.** Сохранение пишет `null`, и `priceNorm()`
(js/01-yadro.js) падает на `PRICING_DEFAULTS` — прежние 500/1500, 2000/4000, 2 кг и 100 ₸.
Ноль значил бы «надбавки нет», и пакет L стоил бы столько же, сколько S. По той же причине
панель не показывается, пока таблицы нет (`pricingReady()`): всё считается как раньше.

**У Барахолки надбавки за перевес НЕТ ВОВСЕ** (с 10.10.2026, подробности и грабли —
в 5f). Своя пара ставок там прожила два дня и убрана вместе с начислением.

**Ноль в поле «с какого веса» означает НЕ «не начислять», а «порог 0»** — то есть
надбавку получит любая посылка тяжелее нуля. «Не начислять» — это ноль в поле ставки
за килограмм. На этом уже обожглись (5f).

**Новое место, где нужна цена — берите `priceNorm(ключ)`,** а не число. Таблица грузится
при входе всем (`S.pricing`, js/02-ket.js) и обновляется при заходе в «Калькуляцию».

Под панелью — живой пример «S · M · L» по базовому тарифу: надбавки в уме не складываются,
а владелец и спросил ровно «L — там сколько, я уже забыл».

## 5d. Обработчики: персональные ставки (26.09.2026)

Обработчиков стало двое, и платят им по-разному. Раньше в калькуляции была одна общая
строка «Менеджер обработчик» — один оклад и одна ставка за заказ на всех. Теперь есть
таблица `calc_processor_norms`, устроенная ровно как `calc_sales_norms` у менеджеров
продаж: строка на человека и месяц, оклад в общий котёл, ставка за заказ — к заказам
этого обработчика (`orders.processor_id`).

**Состояний ровно два, промежуточных нет** — `calcProcessorPersonal(P)`. Пока не заполнено
ни одного персонального поля, действует прежняя общая строка «Менеджер обработчик»
(`salary_processor` + `perorder_processor`) и она видна в нормативах. Как только появилось
хоть одно персональное значение, общая строка перестаёт применяться целиком — и оклад, и
ставка — и уходит с экрана.

Так сделано после прямого вопроса владельца «зачем там дублировано». Убрать строку только
с экрана было нельзя: она продолжала бы влиять на прибыль, а найти её стало бы негде.
Промежуточное состояние (оклады персональные, ставка общая) тоже отпало — набранная ставка
молча не применялась, пока не задан оклад.

Следствия, о которых предупреждён владелец: заполнил одному — у второго ставка станет 0,
пока ему не впишут своё; и заказ без `processor_id` в персональном режиме ставку не несёт
вовсе. Обе цифры видны в сводке, молча ничего не пропадает.

Функции — `calcProcessorSalaryTotal(P)` и `calcProcessorPerOrder(o,P)`; **никогда не
читайте `salary_processor`/`perorder_processor` напрямую**, иначе новые места разойдутся
со старыми. В «Общей сводке» — блок «Заработок менеджеров обработчиков».

**Формула продублирована в ежедневном отчёте** (раздел 6d), там те же `procSalaryTotal`
и `procPerOrder`. Совпадение проверено прогоном настоящего кода функции на одних данных:
и с персональными ставками, и без них — до тенге.

## 5f. МОДУЛЬ «Барахолка» — отдельная ветка, а не фильтр (02.10.2026)

Раздел 5a описывает, как Барахолка считается в деньгах. Этот — как она отделена во всём
остальном. Формулировка владельца: «это другая ветка бизнеса, и нам надо её считать и
смотреть заказы отдельно», её заказы «никак не должны пересекаться с заказами заборов».

До этого отличал их только `calc_group`, и читала его ОДНА Калькуляция. Поэтому реестровые
заказы были видны везде: в «Заказах заборов» (не будучи привязаны ни к одной заявке), в
«Сортировке» (кладовщик искал посылку, которой на складе физически нет), в Статистике, в
поиске дублей, в Центре контроля и в ежедневном отчёте.

**ПРИЗНАК ОДИН НА ВСЮ СИСТЕМУ — `orders.calc_group='baraholka'`.** Им же фильтруется новый
модуль и им же эти заказы исключаются из остальных: один ключ на две задачи. Два разных
ключа (скажем, «загружен из Excel» для модуля и `calc_group` для денег) разошлись бы, и
мешанина вернулась бы на то же место. Отдельная таблица отпала по той же причине, что и у
партнёров Барахолки (раздел 5a): вторая ветка кода через всю систему, при том что
Калькуляция уже настроена на `calc_group`.

**Функции живут в `js/01-yadro.js`,** а не в Калькуляции: их спрашивают модули, которые
подключаются РАНЬШЕ (Сортировка, Центр контроля, меню).

| Функция | Что отдаёт |
|---|---|
| `isBaraholkaOrder(o)` | признак по одному заказу |
| `mainOrders(list?)` | заказы заборов — БЕЗ Барахолки |
| `barOnlyOrders(list?)` | только Барахолка |

**Поле может отсутствовать** (db/13 не выполнен) — тогда признак всегда ложный, все
исключения ничего не исключают, и система работает как до Барахолки.

### Где её теперь нет

`ordersScopedList()` («Заказы заборов», «Курьерская», «Почтовая», «Сегодня»), `sortingPool()`
и `sortingUnprocessedCount()` и список дня в «Сортировке», `renderDashboard` и
`aiBuildDataSummary`, `findDuplicateGroups`/`checkOrderDuplicate`, `notifyIssues` и
`notifyHighlights`, `fillNeedsWork`, ежедневный отчёт.

|---|---|
| Калькуляция | уже делит по `calc_group` (раздел 5a) |
| `js/18-blanki.js` | уникальность номера заказа по ВСЕМ заказам: на повторный `OrderNum` Казпочта вернёт чужой ШПИ |

| История изменений | общая |

### Модуль

Ключ `baraholka`, пункт меню сразу под «Заказами заборов». Рисует тот же `renderOrders`
новым режимом — фильтры, пагинация, выгрузка и карточка заказа общие, ничего не
дублируется. **Колонки «Фото» в этом режиме нет** (бланк никто не фотографирует), кнопки
«Создать заказ» нет (заказы приходят только реестром).

**Кнопка «⬆ Загрузить из Excel» теперь ЖИВЁТ ТОЛЬКО ЗДЕСЬ.** Пока она стояла в «Заказах
заборов», реестровые заказы наливали в общий список — из этого и выросла вся мешанина.

**РЕЖИМ ГРИДА ЗАДАЁТСЯ ВКЛАДКОЙ, а не только аргументом `renderOrders`.** Первая версия
теряла его на любом действии: перерисовок у грида много — сохранение карточки, удаление,
отправка в KET, массовые операции, загрузка из Excel, — и часть из них звала
`renderOrders()` БЕЗ аргумента, а `ordersMode=mode||''` на пустом аргументе означало
«Заказы заборов». Вкладка в меню оставалась на Барахолке, а содержимое подменялось чужим,
и выглядело это как перескок в другой раздел (жалоба владельца 02.10.2026: «что бы я там
ни сделал, перекидывает на заказы заборов»).

Теперь пустой вызов берёт режим из `S.tab` (`ORDERS_TAB_MODE` → `ordersModeForTab()`), а
не обнуляет его. Незнакомая вкладка оставляет режим как был: карточку заказа открывают и
из «Заполнения». **Новый режим грида — это строка в `ORDERS_TAB_MODE`**, иначе он будет
терять себя ровно так же.

**В карточке барахолочного заказа фото нет, и карточка становится ОДНОКОЛОНОЧНОЙ.** Бланк
этих заказов никто не фотографирует, а пустая колонка под фото забирала половину ширины.
Класс `order-split nophoto` ставит форму во всю ширину, а KET и переписку под неё — та же
перестановка, что в мобильных правилах. Признак берётся у ЗАКАЗА (`isBaraholkaOrder`), а
не у режима грида: карточку открывают и из других разделов, а фото там всё равно нет.

**Убрано с экрана по просьбе владельца 02.10.2026:**

| Что | Где | Было/стало |
|---|---|---|
| подпись под заголовком | только Барахолка | `subs.baraholka` удалена, `<p>` не рисуется вовсе |
| «🖨 Печать бланков» | только Барахолка | кнопка осталась в «Почтовой доставке» |

Подпись склеивается через `filter(Boolean).join(' · ')` — при пустой подписи иначе остался
бы висячий разделитель «· за период».

**Плашка «Оплачено» ушла СРАЗУ С ТРЁХ экранов** — блок из пяти плашек общий для «Заказов
заборов», «Заказов сегодня» и Барахолки. Владелец назвал два, третий тот же блок; разделять

**Право ОТДЕЛЬНОЕ** (`baraholka:null` в карте `fb`) — как у «Межгорода» и «Сортировки»:
сразу после выкладки модуль виден только администратору, пока право не выдано явно в «Роли
и права». Курьеру — только по явному праву, как остальным дополнительным модулям.

**Иконка `baraholka`** — прилавок с полосатым тентом и ящиком, в общем стиле набора

### Дубли при загрузке реестра

Просьба владельца: «пиши, какие заказы не загрузились, если есть дубли». Было три проблемы:

1. **Предпросмотр проверял дубли по памяти вкладки** (`S.orders`), а там после входа только
   сегодняшние заказы. Дубль за прошлую неделю не подсвечивался и молча отваливался уже при
   сохранении. Теперь — запросом к базе (`impExistingTracks`, чанками по 100), и если запрос
   не удался, об этом говорится вслух.
2. **Четыре причины складывались в одно число** «пропущено: 14».
3. **Сами строки нигде не перечислялись.**

Теперь после загрузки открывается `impResultModal`: сколько создано, и перечень не
загруженных — сгруппированный ПО ПРИЧИНЕ, со строкой файла, треком, ФИО и телефоном, плюс
кнопка «скопировать список», чтобы отправить партнёру. Туда же попадают строки, которые
отклонила сама база (например уникальный индекс трека), — иначе «создано 118 из 120»
осталось бы без объяснения.

**В списке партнёров — ТОЛЬКО партнёры Барахолки** (с 02.10.2026). Загрузка живёт в её
модуле, и заказы здесь создаются с её меткой; партнёр без галочки увёл бы их в «Заказы
заборов», то есть ровно в ту мешанину, из-за которой модуль и делали. По имени файла
партнёр тоже угадывается ТОЛЬКО среди них — иначе подставился бы тот, кого в списке нет.

**Если галочек нет ни у кого — показываем всех, как раньше.** Это значит, что `db/13` не
выполнен и раздела Барахолки в базе нет вовсе; пустой список был бы тупиком — ни загрузить,
ни понять почему. В этом случае остаётся и прежнее предупреждение «у партнёра не стоит
галочка, заказы уйдут в Заказы заборов».

**И второе предупреждение — про ДАТУ ЗАБОРА, она определяет МЕСЯЦ РАСЧЁТА.** Калькуляция
берёт месяц по `pickup_date`, а в окне загрузки дата подставляется сегодняшняя и меняется
руками. 02.10.2026 так уехали 51 заказ: реестры загрузили в октябре с сентябрьскими датами,
и они легли в сентябрь — месяц уже закрытый и выплаченный. Заметили только запросом к базе.

Теперь, если выбранная дата не из текущего месяца: в предпросмотре красным сказано, в какой
месяц уйдут заказы, а при нажатии «Создать заказы» спрашивается отдельное подтверждение с
названием месяца. **Жёстко не запрещаем** — бывает, что заказ правда нужно отнести к
прошлому месяцу.

Названия месяцев в `IMP_MONTHS` стоят в ИМЕНИТЕЛЬНОМ падеже: они подставляются в «попадут в
сентябрь 2026». С родительным («сентября») выходил подстрочник «попадут в сентября».

Те 51 заказ перенесены на 01.10.2026 (`db/29`): физического забора у Барахолки нет вовсе,
дата здесь означает день реестра, а реестр загрузили в октябре.

### Сентябрь НЕ пересчитывали — Барахолка считается с 1 октября

Проверка `db/28` нашла 364 заказа двух барахолочных партнёров (ИП Болаткан 295, Карлыгаш 69)
за 18–25.09 без метки `calc_group`: галочку у партнёров поставили позже, а метка ставится в
момент СОЗДАНИЯ заказа. Октябрьских среди них нет ни одного — с 26.09 всё помечается само.

**Решение владельца 02.10.2026: «сентябрь всё выплатил, как было в сентябре так и оставь».**
Метку этим 364 заказам НЕ ставили, и ставить не надо:

- сентябрь уже закрыт и выплачен, а метка меняет деньги задним числом — эти заказы ушли бы
  из общего котла в барахолочный, делитель общих фондов уменьшился бы на 364, и у
  обработчиков «за заказ» за сентябрь стало бы меньше на то же число;
- отчёт и Калькуляция перестали бы сходиться с тем, что реально выплатили, — это хуже
  неточной истории.

Да, по этим 364 заказам сентябрьские цифры формально неверны: на них навешаны курьер,
межгород и общие фонды, которых по ним не было (раздел 5a). **Это признанная погрешность
закрытого месяца, а не задача.** Не «исправляйте» её при следующем разборе.

Следствие: в модуле «Барахолка» сентябрьской истории этих двух партнёров нет — те 364
заказа остались в «Заказах заборов». Модуль показывает только помеченные.

**Единственный способ завести эту кашу заново** — снять у барахолочного партнёра галочку
«Барахолка»: его новые заказы перестанут получать метку и начнут утекать в «Заказы заборов».
Проверка на это — блок 3 в `db/28` (заказы С меткой, у которых у партнёра галочки НЕТ).

### KET: заказы Барахолки уходят на своего менеджера (02.10.2026)

Владелец дал id менеджера — **19987924**, заказы из модуля «Барахолка» должны идти на него.

**Второй аккаунт для этого НЕ понадобился.** В `callKet` уже есть выбор аккаунта
(`ketAccountForOrder`: Алматы → `almaty`, остальное → `astana`), но там нужен свой ключ API,
а владелец дал именно id, а не ключ. Значит это значение поля в самом заказе.

**⚠️ ИМЯ ПОЛЯ НЕ ПОДТВЕРЖДЕНО KET.** В их документации (`ketkz.com/api/doc.txt`) поля
«менеджер» нет вовсе. Ближайших два:

| Поле | Как описано у KET |
|---|---|
| `client_id` | «Служебное поле, его значение обсуждается отдельно **с менеджером**» |
| `web` | «id веба, который залил заявку» |

Сначала выбрали **`client_id`** — по описанию это ровно то поле, значение которого даёт
менеджер. **Проверено живым заказом 02.10.2026: НЕ РАБОТАЕТ.** Заказ ушёл под
**75747498**, то есть туда же, куда уходил всегда.

**РАЗГАДКА: KET смотрит на `uid` ЗАПРОСА, а не на поля заказа.** Владелец прислал исходник
`ket-proxy`, и там всё видно прямым текстом: **`75747498` — это `KET_UID_ALMATY`**, логин
аккаунта Алматы, прописанный в самой функции запасным значением. То есть барахолочный
тестовый заказ ушёл не «неизвестно куда», а под аккаунтом Алматы — потому что забор у него
алматинский, а `ketAccountForOrder` смотрел ТОЛЬКО на город.

Этот же номер KET называл «своей приёмкой» 21.09.2026, когда давал имя поля
`actual_weight` — то есть одно и то же, и сходится.

Никакое поле в `send_order.php` привязку не сдвинет, и `KET_BAR_MANAGER_FIELD` оставлен
пустым: пускать с каждым заказом значение, которое ничего не делает, — мусор в чужой
системе, где нет метода обновления. Id `19987924` оставлен в константе справкой, в запрос
он не уходит — он уходит как `uid`.

**`19987924` — это `uid`, а присланный ключ — его `secret`.** Девять знаков смутили меня
зря: у аккаунта Алматы секрет в том же исходнике тоже девятизначный. Короткий ключ здесь
норма, а не признак, что скопировалось не всё.

Второй кандидат `web` не проверялся и проверять его больше незачем. Если всё же придётся —
**отправлять только ОДНО поле, не оба**: по двум сразу потом не понять, какое сработало,
ровно на этом здесь уже обожглись с `kz_code`/`barcode` (раздел 6b).

**Менеджер выбирается ТРЕТЬИМ АККАУНТОМ** — тем же механизмом, которым уже разведены
Астана и Алматы. `ketAccountForOrder(o)` отдаёт имя аккаунта, CRM передаёт его в `ket-proxy`
полем `account`, а тот по имени достаёт свой секрет:

| Заказ | Аккаунт |
|---|---|
| **Барахолка — любой город забора** | **`baraholka`** |
| забор Алматы | `almaty` |
| всё остальное | `astana` |

**Барахолка проверяется ПЕРВОЙ, до города.** Это отдельная ветка бизнеса со своим
менеджером, и город забора к выбору ключа отношения не имеет: поставь проверку города
раньше — алматинская Барахолка утекла бы в общий поток.

**Ключи живут в `ket-proxy`** — исходник лежит локально в `functions/ket-proxy/index.ts`
(папка в `.gitignore`), а выкладывается через панель Supabase. В ЭТОТ файл ключи не писать:
репозиторий публичный (раздел 9a).

**Неизвестное имя аккаунта теперь ОТКАЗ, а не «возьмём основной».** Раньше `pickAccount`
на любое незнакомое значение молча отдавал астанинский аккаунт — то есть опечатка в имени
означала бы десятки заказов под чужим менеджером, и узнать об этом было бы негде: метода
обновления у KET нет. Пустое имя по-прежнему означает Астану — так функцию звали до
появления второго аккаунта. Функция возвращает ещё и `uid`, которым отправила.

**Попутно замечено в `ket-proxy`: логин и ключ аккаунта Алматы прописаны прямо в исходнике**
запасными значениями (`?? "<uid>"`, `?? "<ключ>"` — сами значения тут не приводятся), и
секретов на них, похоже, никто не заводил. Другой защиты у API KET нет вовсе: по паре `uid`+`secret` любой может создавать
заказы от имени этого аккаунта. Барахолочная пара добавлена так же — чтобы функция заработала
сразу, — но **обе пары стоит перенести в секреты**: `KET_UID_BARAHOLKA`,
`KET_SECRET_BARAHOLKA`, `KET_UID_ALMATY`, `KET_SECRET_ALMATY`. Это не срочно и не ломается,
но пока так, ключи видит каждый, у кого есть доступ к панели.

**В CRM видно ДВЕ вещи, и путать их нельзя:** какой аккаунт попросила CRM и каким прокси
РЕАЛЬНО отправил. Второе берётся из ответа `ket-proxy` (`account` и `uid`) и пишется в
сообщении об успехе и в окне «что ушло в KET» — `ketSentAs()`.

Это не украшение: пока в `ket-proxy` не выложен нужный аккаунт, СТАРАЯ версия функции на
незнакомое имя молча берёт аккаунт по умолчанию, и заказ уходит под прежним uid. Со стороны
это ровно то же самое, что «наша правка не сработала», и 02.10.2026 мы на это и наткнулись:
заказ снова ушёл под `75747498` уже ПОСЛЕ правки CRM. Теперь сообщение говорит прямо —
«просили baraholka, а ушло аккаунтом astana (uid 75747498)».

**Старый прокси узнаётся по отсутствию `uid` в ответе** — его там не было вовсе. Так что
«прокси не вернул uid» в сообщении означает «функция не выложена», а не ошибку KET.

Причина та же, по которой в сообщении о треке печатается контур Казпочты: без этого «ушло не
туда» видно только в чужой панели, а метода обновления у KET нет.

**ПРОВЕРЕНО ЖИВЫМ ЗАКАЗОМ 02.10.2026, 01:56 — работает.** Сообщение CRM:
«Заказ отправлен в KET (ID 9407627) · трек QS013822592KZ передан · **аккаунт baraholka ·
uid 19987924**». До выкладки функции тот же заказ уходил под `75747498`.

**Путь к этому занял две ложные остановки, обе про «правка не применилась»:**

1. `ket-proxy` ещё не был выложен, а СТАРАЯ его версия на незнакомое имя аккаунта молча
   брала аккаунт по умолчанию — заказ уходил под прежним uid, и выглядело это как «наша
   правка не сработала». В новой версии такое имя даёт честный отказ.
2. Браузер держал старый `index.html` из кеша (`max-age=600`, метки версии у него нет —
   раздел 4), поэтому работал код, загруженный ДО правки. Узнаётся по сообщению: в старом
   нет хвоста «· аккаунт …». Лечится `Cmd+Shift+R`.

Отсюда порядок проверки на будущее: **сначала Deploy функции, потом `Cmd+Shift+R`, потом
один заказ** — и читать хвост сообщения, а не гадать.

### Перевеса у Барахолки НЕТ — заведён 08.10.2026, убран 10.10.2026

Сначала владелец попросил «такую же надбавку за вес, как в заборах, чтобы накидывала
автоматом»: появилась своя пара ставок в `pricing_settings` (`bar_weight_free_kg`,
`bar_weight_step_fee`, `db/30`), панель на вкладке «Барахолка» и начисление прямо при
загрузке реестра. Через два дня он это отменил: «в барахолке убери функцию, которая
делала надбавку за вес».

**Как убрано.** `weightSurcharge(вес, курьер, барахолка)` возвращает ноль на третий
аргумент — правило живёт в ОДНОМ месте, а не вырезано по вызовам: карточка, «Сортировка»
(`repriceForWeight`) и список внутри заявки считают надбавку этой же функцией, и порознь
они разошлись бы. Загрузка реестра снова пишет в заказ ровно ту сумму, что стоит в
колонке файла; колонки `bar_weight_*` остались в базе, но их никто не читает.

**Следствие, шире просьбы:** надбавки нет у барахолочного заказа и в КАРТОЧКЕ, хотя до
08.10 она там начислялась по общей ставке заборов (заказы-то почтовые). Владельцу
сказано; вернуть — это снять `|| bar` в одной строке.

**ПОЧЕМУ НОЛЬ «НЕ РАБОТАЛ» — и это была настоящая ловушка в той конструкции.** Владелец
написал: «я вроде 0 поставил, а он всё равно делает надбавку». Воспроизведено: ноль в
поле **«Перевес · с какого веса (кг)»** при ПУСТОМ поле «за каждый кг» означал «порог 0,
ставка как в заборах» — то есть надбавка начислялась НА КАЖДУЮ посылку, включая
400-граммовую (+100 ₸), а трёхкилограммовая получала +400. Ноль в поле ставки работал
правильно, ноль в поле порога давал обратное тому, чего от него ждут.

Общий вывод на будущее: **в паре «порог + цена» ноль значит разное**, и пустое поле с
запасным значением из соседнего раздела это различие прячет. Если такая пара заводится
снова — обе ячейки должны быть либо заполнены, либо пусты вместе, и под ними должен
стоять живой пример («посылка 0,4 кг → +100 ₸»), по которому ошибку видно сразу.

**Та же ловушка есть и в заборах** (`priceNorm`, раздел 5c): поставить там «с какого
веса» = 0 при ставке 100 — и каждая почтовая посылка получит надбавку. Это не трогали,
но знать стоит.

**Уже созданные заказы не пересчитываются** — сумма записана в самом заказе. Те реестры,
что загрузили 08–10.10 с надбавкой, остались с ней; если владелец попросит, правится
отдельным запросом по дате загрузки.

### Сумма заказа при загрузке реестра: из файла, ноль — по тарифу партнёра (10.10.2026)

Владелец попросил «пусть CRM тянет информацию от партнёра в карточке, а не от экселя», и
я понял это как «сумма = тариф из карточки». **Это было неверно, и он поправил в тот же
час**, прежде чем правка успела что-то испортить:

> «Нияз грузит эксель, заказ уже с суммой с надбавкой веса: ставка партнёра 1400, заказ
> +2 кг — заходит 1520. Ты же этот заказ не поменяешь на 1400, верно? Надо именно: если у
> партнёра стоит 0 и заказ заходит с суммой — менять его на 0».

**В реестре стоит УЖЕ ПОСЧИТАННАЯ цена доставки** — тариф плюс надбавка за перевес, её
считает отправляющая сторона. Подставь мы тариф из карточки — потеряли бы 120 ₸ на каждой
тяжёлой посылке и выставили бы партнёру меньше, чем он должен. Это же объясняет, почему
двумя часами раньше была убрана надбавка за вес внутри CRM: её уже посчитали в файле, и
CRM начисляла бы её второй раз.

**Итоговое правило** (`impOrderSum` в `js/17-import-excel.js`):

| Тариф в карточке | Что попадёт в заказ |
|---|---|
| заполнен (1400, 1500…) | **сумма из файла как есть** — CRM её не пересчитывает |
| пусто | то же самое, сумма из файла |
| **ровно 0** | **0 ₸** + «Оплачено отправителем» + условная выручка из карточки |

**Из карточки берётся НЕ ЦЕНА, А ПРИЗНАК.** Тариф 0 означает, что партнёр платит за
доставку отдельно, по счёту раз в месяц (раздел 5b) — тогда сумма в файле к нашей выручке
отношения не имеет, и в заказе должен стоять ноль, что бы в файле ни стояло.

**Тариф 0 тянет за собой ещё два поля** — `paid_by_sender` и `order_sum_orig` (условная
сумма при прямой оплате из карточки). Ровно то же делают создание заказов по заявке
(`buildPickupOrderRows`, js/11) и кабинет партнёра (js/08): правило «тариф 0 = платит сам,
в Калькуляцию идёт условная выручка» в системе одно, и загрузка реестра была единственным
местом, которое его не знало. Без `direct_pay_amount` такие заказы в Калькуляции выглядят
чистым убытком — об этом сказано прямо в предпросмотре.

**Обнуление видно ДО создания заказов:** при тарифе 0 над таблицей стоит красная строка
«суммы из файла в заказы НЕ пойдут», а в колонке «Сумма» — «0 ₸» с подписью «в файле
1 520 ₸ · тариф 0». Молча обнулённая цена в чужом реестре — это счёт, который потом не
объяснить.

Проверено прогоном настоящего кода загрузки на примере владельца: тариф 1400 и 1520 в
файле → в заказ уходит 1520; тариф 0 → 0, «оплачено отправителем», условная 1800; тариф
не заполнен → 1520.

**Октябрьские заказы правятся запросом** `db/31-ОКТЯБРЬ-БАРАХОЛКА-суммы-по-тарифу.sql`:
обнуляет суммы ТОЛЬКО у партнёров с тарифом 0 и ставит им условную выручку; остальные не
трогает. Первая версия того файла переписывала суммы тарифом — она была неверной по той же
причине и переписана. Сентябрь не трогаем: закрыт и выплачен, месяц зашит строкой.

## 5a. «Барахолка» — отдельный учёт денег (26.09.2026)

Часть заказов приходит **готовым реестром Казпочты**: трек уже присвоен, посылки сданы,
курьер к партнёру не едет. Считать их по общим нормативам нельзя — на каждый повесился бы
курьер за забор, межгород и общие фонды, которых по ним не было. Прибыль по ним занижалась,
а по остальным завышалась.

**Раздел определяется партнёром, но записывается в заказ.** У партнёра галочка
`partners.is_baraholka`, на странице «Партнёры» — третья вкладка, которая показывает только
их. В момент СОЗДАНИЯ заказа из карточки партнёра берётся раздел и пишется в
`orders.calc_group` (`'baraholka'` или пусто).

Смотреть на партнёра каждый раз нельзя: партнёра могут перевести в Барахолку и обратно, и
тогда прибыль за прошлые месяцы пересчиталась бы задним числом молча — Калькуляция считает
на лету и ничего не хранит. Обратная сторона: галочка действует только на новые заказы,
старые переводятся отдельным запросом (он есть в конце `db/13`).

Партнёры Барахолки лежат в ОБЩЕЙ таблице `partners`, а не в своей. Заказ ссылается на
партнёра оттуда; отдельная таблица заставила бы тянуть вторую связь через всю систему и
каждый раз выяснять, «в какой он таблице».

**Свой набор статей** (`CALC_BAR_FIELDS` и `CALC_BAR_FUNDS` в `js/07-kalkulyaciya.js`):
пять за заказ (пакет, гофра, бланк, SMS, доставка почтой) и четыре месячных фонда
(ЗП обработчика, ЗП менеджера, аренда склада, ЗП доставки до почты). Курьера, межгорода,
общих фондов и зарплат из общего блока у этих заказов нет вовсе.

**Фонды делятся по разделам раздельно** — это главное в расчёте. `ordersInOrderMonth()`
считает заказы месяца ОТДЕЛЬНО для Барахолки и для остальных. Если делить общие фонды на
все заказы вместе, Барахолка разбавляет общий котёл, ничего из него не оплачивая, и прибыль
по обычным заказам растёт на пустом месте.

Следствие, о котором предупреждён владелец: после появления Барахолки прибыль по обычным
заказам меняется — делитель общих фондов стал меньше. Задним числом тоже.

**ВСЯ «Общая сводка» считается БЕЗ Барахолки** (решение владельца 28.09.2026). Пока оба
учёта лежали в одних карточках, «Итого расходы» наверху не сходились ни с одной таблицей
под ними, а прибыль двух разных бизнесов складывалась в одно число, по которому нельзя
понять ни один из них. Теперь:

**А с 02.10.2026 Барахолки в «Общей сводке» НЕТ ВООБЩЕ** — решение владельца: «оттуда всё,
что связано с барахолкой, убери, пусть будет только заказы заборов». Её деньги целиком
переехали в свою вкладку (`barSummaryHtml`), где и так была сводка под нормативами.

| Блок «Общей сводки» | Что показывает |
|---|---|
| Карточки наверху | выручка/расходы/прибыль/маржа/ROI по заказам заборов (`mainCalcs`) |
| Разбивка по статьям | только заборы, итог = `mainCost` — сходится с карточкой наверху |
| Заработок менеджеров и обработчиков | только заборы |
| Заработок курьеров | только заборы (за Барахолкой курьер не ездил) |
| Разбивка по типу доставки | две строки и «Всего» — курьерская плюс почтовая, без Барахолки |

Общих итогов «по компании» больше нет нигде: складывать две ветки в одно число незачем —
по такой сумме нельзя понять ни одну из них.

**Из таблиц по людям заказы Барахолки убраны не для красоты:** ставка за заказ на них
не начисляется вовсе (в `calcOrder` у ветки Барахолки нет ни `perorder_processor`, ни
ставки продавца — только свои пять статей, четыре фонда и надбавка менеджера). Пока они
считались вместе, «за заказ» у обработчиков было завышено на число барахолочных заказов.

**НО НАДБАВКА МЕНЕДЖЕРА ПО ПРОДАЖАМ К БАРАХОЛКЕ ПРИМЕНЯЕТСЯ** — это единственная общая
статья, которая к ней применяется, и деньги менеджер по этим заказам реально зарабатывает.
Её легко потерять: 01.10.2026 обнаружилось, что таблица «Заработок менеджеров по продажам»
строилась только по `mainCalcs`, то есть **«Итого» показывало МЕНЬШЕ, чем менеджеру
причитается**, и платить по той цифре значило недоплатить.

**Сводка Барахолки сделана теми же блоками, что «Общая сводка»** (02.10.2026, по просьбе
владельца «сделай нормальную, как в общей сводке»): те же пять карточек — выручка, итого
расходы, чистая прибыль, маржинальность, ROI — и та же «Разбивка по статьям расходов» с
долями и итогом 100 %. Было самодельное `calc-kpi` без ROI и с другим порядком колонок.

**И там же объяснено, почему в начале месяца прибыль выглядит страшной.** Месячные фонды
(`CALC_BAR_FUNDS`) считаются на ВЕСЬ месяц, а делятся на те заказы, что уже есть: 2 октября
при 120 заказах и фондах 400 000 ₸ на заказ ложится 3 333 ₸ — 81 % всей себестоимости, и
прибыль уходит в минус. К концу месяца заказов больше, доля фондов падает. Это свойство
расчёта, а не ошибка, и теперь оно написано прямо под карточками — иначе цифра выглядит
поломкой (владелец так и спросил: «как-то странно считает»).

**«Средняя сумма заказа» в шапке — диагностика, а не украшение.** Выручка Барахолки берётся
из `order_sum`, а при загрузке реестра туда ДО 10.10.2026 попадала колонка «сумма
наложенного платежа», то есть цена товара, и выручка раздувалась в разы. Видно это сразу:
средняя сумма заказа будет не 1500–2000, а десятки тысяч. Но имейте в виду: в реестрах,
которые грузят сейчас, в этой колонке стоит посчитанная цена доставки с перевесом, а не
цена товара (раздел 5f), поэтому сама по себе большая средняя — повод проверить файл, а
не доказательство ошибки.

Сейчас эта надбавка считается **на вкладке «Барахолка»** — блок «Надбавка менеджеров по
продажам» в `barSummaryHtml`: менеджер, заказов, надбавка, на заказ. **К выплате менеджеру —
сумма двух таблиц**, и об этом прямо написано в обеих: в «Общей сводке» и на вкладке.
Разносить одну выплату по двум экранам не идеально, но лучше, чем прятать Барахолку внутри
цифры «только по заборам».

У обработчиков такого блока нет и не нужно: их доля Барахолки идёт месячным фондом
(`CALC_BAR_FUNDS`), а не ставкой за заказ, и прибавлять им нечего.

**«Заказов» у человека меньше, чем в гриде «Заказы заборов» — это НЕ ошибка счёта**
(вопрос владельца 01.10.2026: у менеджера Айнур 5685 в Калькуляции против 5731 в гриде).
Причин ровно две, и обе законные:

1. **Барахолка в таблицы по людям не входит вовсе** — ставка за заказ на ней не
   начисляется, у неё свой месячный фонд. Грид показывает все заказы подряд.
2. **Месяц считается по-разному.** Калькуляция берёт месяц по дате ЗАБОРА, а если её нет —
   по дате создания (`(o.pickup_date||o.created_at).slice(0,7)`). Грид фильтрует строго по
   выбранному полю: при фильтре «забор с… по…» заказ с ПУСТОЙ датой забора выпадает совсем
   (`if(of.pickFrom&&(!pd||pd<of.pickFrom))return false`), а при фильтре по дате создания в
   выборку попадают заказы, которые Калькуляция отнесла к другому месяцу.

Приписки «+N Барахолки» в строках, которые добавлялись 01.10.2026, убраны 02.10 вместе со
всей Барахолкой: в «Общей сводке» её теперь нет вовсе, и сверять там нечего. Барахолочные
заказы человека видны на её вкладке.

Готовая сверка по конкретному человеку — `db/24` (только считает, ничего не меняет):
разбивает разницу на Барахолку, заказы без даты забора и расхождение «забор против
создания».

**В «Разбивку по статьям расходов» Барахолка не входит** (решение владельца 28.09.2026).
Статьи у неё свои, а названия частью совпадают с обычными: строка «Пакеты» складывала два
разных норматива, курьера и межгорода у Барахолки нет вовсе — смотреть на такую сумму
нельзя ни как на общую, ни как на чью-то конкретную. Итог и доли считаются от расходов БЕЗ
Барахолки (`expenseCost = totCost − barSum.cost`), иначе проценты не сошлись бы в 100.
Её расходы видны отдельной строкой в «Разбивке по типу доставки», и примечание под
таблицей на неё прямо ссылается — деньги не пропадают с экрана, а переезжают в свою строку.

**Формула продублирована в ежедневном отчёте** (`functions/daily-report/index.ts`), как и
весь остальной расчёт — см. раздел 6d. Ветка Барахолки добавлена в обоих местах, счётчики
месяца там тоже считаются по разделам двумя запросами вместо одного. Совпадение проверено
прогоном на одних данных: 12 заказов (8 обычных, 4 Барахолки) дали одинаковые итоги
в Калькуляции и в отчёте.

**Без `db/13` раздела не существует:** вкладка в Калькуляции и галочка у партнёра
не появляются, поле в заказ не пишется, всё работает как раньше. Проверка — `baraholkaReady()`,
смотрит, есть ли `calc_group` в загруженных заказах.

### Загрузка заказов из Excel (`js/17-import-excel.js`)

Реестр Казпочты приходит готовым файлом, и заказы создаются из него кнопкой
«⬆ Загрузить из Excel» в «Заказах заборов». Библиотека SheetJS уже подключена в
`index.html` и читает старый `.xls` (BIFF8) наравне с `.xlsx`.

**Колонки ищутся по названию, а не по номеру.** В выгрузке легко появится лишний столбец,
и жёсткие номера молча сдвинули бы все данные на графу. Строка заголовков тоже ищется —
та, где есть и «ФИО», и «ШПИ»; в реестре над ней семь строк шапки.

**Две поправки данных, обе обязательные:**

*Индекс.* Ведущий ноль в Excel превращается в латинскую «O» — `O14685` вместо `014685`.
Визуально неотличимо, для Казпочты это другой символ. Убираем букву в начале и дополняем
до шести знаков. В предпросмотре под исправленным индексом подписано, что было.

*Телефон.* Оставляем цифры, `8XXXXXXXXXX` и `XXXXXXXXXX` приводим к `7XXXXXXXXXX`.

**Строка пропускается**, если телефон короче десяти цифр, нет трека, нет индекса или такой
трек уже есть. Дубли проверяются ЗАПРОСОМ К БАЗЕ, а не по памяти вкладки: заказы мог
создать кто-то другой. Это и есть защита от повторной загрузки того же файла.

**Ничего не создаётся вслепую:** сначала таблица разбора — что создастся, что пропустим и
почему, — и только потом кнопка. Партнёр подставляется по имени файла, если совпал.

Заказы помечаются заполненными сразу (`filled_at`): ФИО, адрес и телефон в них уже есть,
менеджеру там делать нечего, и в очередь «Заполнения» они попадать не должны.

## 5e. Бланки Казпочты, выпущенные заранее (26.09.2026)

Партнёру отдают готовый бланк со штрих-кодом, а получателя он вписывает от руки. Трек
Казпочта выдаёт только на номер отправления, поэтому номера выпускаются заранее и лежат
в пуле, пока к ним не привяжется настоящий заказ. Код — `js/18-blanki.js`, таблицы
`track_batches` и `track_pool` (`db/17`).

**Живёт вкладкой в «Настройках» («Бланки заранее»), а не пунктом меню** — решение
владельца: пользуются редко и только свои, а модулей и так много. Отсюда и права: и в
интерфейсе (`canEditDir()`), и в правилах базы стоит `directories`, а не `orders`.
Рисует раздел в `#dirContent`, как остальные вкладки настроек.

**Почему НЕ в `orders`.** Десять тысяч пустышек среди заказов сломали бы тихо и сразу:
делитель фондов в Калькуляции (`ordersInOrderMonth`), очередь «Заполнения», «Сортировку»,
дашборд, счётчики меню, ежедневный отчёт и поиск дублей — плюс 40 % к самой большой
таблице, с которой уже были таймауты. Отдельная таблица не видна ни одному старому экрану.

**Ноль — допустимая сумма партии, а не «не заполнено».** Часть заказов идёт без
наложенного платежа, и у Казпочты это отдельная категория отправления: при сумме 0
уходит `MailCtg=3` («Обыкновенная») без `DeclaredValue`/`CashOnDelivery`, при сумме
больше нуля — `MailCtg=4` с наложенным платежом. Проверка в форме именно «введено
число», а не «больше нуля»: раньше ноль отвергался, и такую партию было не создать.

На бланке при нуле печатается «0 (ноль тенге 00 тиын)», а не пустая строка — ровно так,
как было напечатано в исходном шаблоне Казпочты. Это не украшение: у Казпочты по этому
номеру записано «без наложенного платежа», и пустая строка позволила бы вписать сумму
от руки, которую всё равно никто не соберёт.

**Партия — это «ИП + сумма + количество».** Сумма уходит наложенным платежом и печатается
на бланке прописью, а изменить её потом нечем: повторный запрос с тем же `OrderNum` новый
ШПИ не выдаёт — Казпочта возвращает прежний с кодом 20012. Разные номиналы — разные партии.

**Номер проверяется по двум источникам** — `orders.code` и `track_pool.code`, запросом к базе,
а не по памяти вкладки (там после входа лежат только сегодняшние заказы). Совпадение
недопустимо: на повторный `OrderNum` Казпочта вернёт ЧУЖОЙ, уже выданный ШПИ, и у двух
посылок окажется один трек.

**Получателя в запросе нет** — его ещё не существует. Вместо него уходят реквизиты
ОТПРАВИТЕЛЯ целиком: город, улица, дом И ИНДЕКС.

Индекс сначала не слали вовсе, и Казпочта отказала: «Не все значения переданы! (код 20000)»
(проверено 27.09.2026). Теперь уходит `KAZPOST_SNDR_INDEX` — тот же адрес, что и в остальных
полях: набор заглушек должен быть согласованным, наполовину заполненный адрес хуже целиком
подставленного.

Реальный адрес партнёр впишет на бланке от руки, и физически посылку сортируют по нему.
**Если окажется, что Казпочта маршрутизирует по электронному индексу и посылки возвращаются
к нам — здесь нужен индекс города назначения**, а для пула он неизвестен по определению;
это вопрос к самой Казпочте. Признак беды: посылка по такому бланку уехала в Астану.

В `track_pool` предусмотрено поле `index`: если оно заполнено, берётся оно, а не индекс
отправителя. Колонки в базе пока нет — добавлять, когда понадобится партия под конкретный
город.

**Повтор на строку с треком к Казпочте не идёт** (`processPool` выходит сразу): номер из
диапазона договора тратить нельзя. Поэтому «Получить треки» можно жать сколько угодно —
попытка повторится только для тех, у кого трека нет, а причина отказа лежит в `track_pool.error`
и видна в списке партии.

**Заказ садится на номер при загрузке реестра из Excel** (`js/17-import-excel.js`): трек из
файла ищется в пуле среди свободных, и заказ создаётся **с кодом из пула**, а не со своим.
Иначе у Казпочты остался бы один номер заказа, а у нас другой. ИП тоже берётся с бланка —
он уже напечатан, переиграть его нечем. Таблицы может не быть: тогда всё работает как раньше.

**Печать — тем же бланком, что и обычные заказы**: `printMailLabelsPdf` получает «заказ»,
которого ещё нет, — с кодом, треком, ИП и суммой партии, остальное пусто.

### Этикетка 100×150 мм

**Отдельного шаблона нет и не нужно.** Образец владельца оказался нашим же бланком A4,
повёрнутым на 90° и уменьшенным: в его потоке стоит `/TPL1 Do` и те же координаты текста,
что выдаёт наш код. Поэтому `a4LabelsToThermal()` берёт уже готовый A4-документ и
перекладывает каждую страницу на этикетку через `embedPages`/`drawPage`. Содержимое
гарантированно то же, что на A4, — расходиться между форматами ему нечем.

**Числа взяты из самого образца, а не подобраны:** масштаб `0.60834861`, сдвиг
`-9.7529932 / -32.4233243`, поворот `0 1 -1 0 283.464567 0`. Масштаб больше, чем «вписать
целиком» (0.476), то есть поля бланка обрезаются — так и было в образце, сама форма влезает.
`drawPage` у pdf-lib сначала сдвигает, потом поворачивает, поэтому сдвиг образца переносится
как `x = ширина − dy`, `y = dx`.

Проверено сверкой с образцом: «КОД ПЛАТЕЖА», код, индекс и телефон поддержки совпали по
координатам до 0,3 пункта. Номер ШПИ стоит на ~10 пунктов иначе — образец печатался до
того, как эти координаты правили; источником считается наш A4.

Кнопки — в партии: «Печать 100×150» и A4 рядом. У `printMailLabelsPdf` появился второй
аргумент `fmt`, так что включить этикетку где-то ещё — одна строка.

## 6. Модуль «Сортировка»

### Зачем он нужен

Раньше склад ждал, пока все менеджеры («забивальщики») закончат вносить данные по всей заявке, и
только потом получал единый «реестр» (Excel-выгрузку) для сортировки посылок по городам. Это
значит, что сортировка не начиналась, хотя часть заказов уже была готова. Модуль «Сортировка»
позволяет сразу, по мере готовности каждого отдельного заказа, определить, в какой город его класть.

### Как это работает

1. Кладовщик фотографирует физическую накладную на посылке (на них нет штрих-кода — только
   рукописный/печатный текст: ФИО, адрес, телефон).
   - Фото сжимается на телефоне перед отправкой (canvas, до 1400px по длинной стороне, JPEG
     качество 0.75) — это специально сделано для скорости: полноразмерное фото с телефона
     (несколько МБ) сильно замедляло и отправку, и саму работу ИИ. Функция `resizeImageForAI()`.
2. ИИ (`callAI`, модель `claude-sonnet-5`) распознаёт с фото ФИО/адрес/телефон, возвращает строгий JSON.
3. Система ищет совпадение среди сегодняшних, уже обработанных, ещё не отсортированных заказов
   (`findSortMatches()`) — сравнивает по телефону (самый надёжный признак, вес 100), ФИО
   (полное/частичное совпадение слов) и частично по адресу. Если совпадений несколько — выбирается
   с максимальным «весом», остальные предлагаются как альтернативы при «Это не тот заказ».
4. Если совпадение найдено — крупно показывается город назначения (`orderDestCityId()` — берёт
   `courier_city_id` или `city_id` в зависимости от типа доставки) + тип доставки + ФИО/адрес для сверки.
5. Кладовщик подтверждает («✅ Принял») — заказу выставляется `sorted_at` + `sorted_by_name`.
   Отсортированные заказы больше не попадают в поиск.
6. Если авто-поиск не сработал — ручной поиск по ФИО/телефону/номеру среди необработанных заказов
   (`renderSortManualPick()`).

### «Обработан» ли заказ — важное понятие

`orderIsProcessed(o)` = у заказа заполнено ФИО получателя И определён тип доставки (`delivery_id`).
Пока это не так — заказ существует (создан по заявке), но данные ещё не внесены, и показывать его
кладовщику рано (тип доставки, а с ним и город, может ещё измениться в процессе заполнения).
Необработанные заказы исключены из пула поиска в «Сортировке» — если совпадение не найдено, но
необработанные заказы за этот день/город есть, кладовщику показывается подсказка «⏳ возможно,
заказ ещё не обработан», а не просто «не найден».

Из-за этого понятия в основной форме заказа (`orderModal`) поле «Тип доставки» обязательно для
сохранения (без него не даст сохранить — проверка `if(!val('o_delivery'))...return false`), и
список вариантов в нём специально ограничен только «курьерская»/«почтовая» (регулярка
`/курьер|почт/i` по названию из справочника `delivery_types`, у которого могли быть лишние старые записи).

**Пустой пункт «—» в этом списке показывается ТОЛЬКО пока тип не выбран** (просьба
владельца 10.10.2026: «пусть будет только курьерская и почтовая»). У заказа с уже
выбранным типом он не нужен — выбрать «ничего» там нельзя, сохранение всё равно
потребует тип. **А у НОВОГО заказа он обязателен:** без него список молча показывает
первый вариант, и заказ сохранится почтовым, хотя тип никто не выбирал. Тип тянет за
собой всё остальное — город, сумму, трек у Казпочты, видимость на складе, — и молча
решать его за человека нельзя.

### Привязка кладовщика к городу — по городу ЗАБОРА, не назначения!

Это принципиально отличается от логики курьера (у курьера — привязка к конкретным заказам через
`my_order_courier_ids()`, это НЕ трогали и не меняли).

У кладовщика в его карточке сотрудника (`profiles.city_id`) можно указать город — тогда в
«Сортировке» он видит только заказы, которые **забрали** в этом городе (`o.pickup_city_id`), а НЕ
те, что едут в этот город. Логика: кладовщик работает на конкретном физическом складе (например,
склад Алматы), и на этот склад привозят посылки, забранные в Алматы (и в Талдыкоргане — см. особый
случай) — а его задача — определить, в КАКОЙ ГОРОД каждая из этих посылок должна дальше уехать
(это и есть сортировка).

Функция `sortingCityId(o)` — как раз про это: возвращает `pickup_city_id` заказа, с одним особым
случаем — если это Талдыкорган, приравнивает к городу Алматы (потому что там нет отдельного склада,
все посылки физически идут через склад Алматы). Если у сотрудника `city_id` не заполнен (обычно у
админа) — фильтра нет, видно все города сразу — плюс для админа/общего доступа показывается
разбивка по городам сверху (сколько заказов/принято в каждом городе отдельно).

- Фильтр по дате (`sortingDate`, по умолчанию сегодня, максимум — сегодня) — полноценный «архив»:
  можно посмотреть статус любого прошлого дня.
- Ниже — таблица «Список заказов»: ФИО, Телефон, Тип доставки, Адрес, № заказа, Статус. Строки
  подсвечены зелёным (принят) / красным (не принят). Класс `open` у `<tr>` обязателен (раздел 4).
- Фильтр по статусу (все/принятые/непринятые) + поиск по ФИО/телефону/номеру (`sortingListFilter`,
  `sortingListSearch`) — поиск обновляет только `<tbody>` (`renderSortListOnly()`), не всю страницу,
  чтобы не сбрасывать фокус в поле ввода при каждой напечатанной букве. **Грабли, которые уже
  были:** при поиске по буквам (без цифр) старая версия кода считала совпадением ЛЮБОЙ телефон
  (пустая строка после удаления нецифровых символов — подстрока чего угодно) — из-за этого поиск по
  имени казался «не работающим» (показывал почти всё). Исправлено — проверка по телефону теперь
  применяется только если в запросе реально есть цифры.
- По клику на строку — можно вручную переключить статус принят/не принят (с подтверждением через
  `confirm()`), не дожидаясь фото.
- Пагинация на компьютере — такая же плавающая панель, как везде в CRM (`.orders-pager`, выбор
  кол-ва на странице, кнопки листания). На мобильном — «Показать ещё» (батчами).
- Доступ к разделу регулируется как обычный модуль в «Роли и права» (ключ `sorting` в массиве
  `MODULES` и в карте `fb` внутри `canMod()`) — по умолчанию виден только админу, пока явно не
  выдано разрешение роли.

### «Курьер привёз» и фильтр по заборщикам (08.10.2026)

В списке заказов появилась колонка **«Курьер привёз»** и фильтр по курьерам-заборщикам
(`sortingListCourier`) рядом с фильтрами статуса и типа доставки.

**В самом заказе курьера-заборщика НЕТ.** Курьер назначается на ЗАЯВКУ
(`pickups.courier_id`), а заказ ссылается на заявку (`orders.pickup_id`) — отсюда
`sortingPickupCourierId(o)` идёт через заявку. **Не путать с `order_courier_id`:** это
курьер, который заказ РАЗВЕЗЁТ, а не тот, кто привёз его на склад.

Пусто бывает в двух случаях, и оба показываются как «не назначен»: у заявки курьер не выбран
или заказ создан не из заявки вовсе.

**Список курьеров в фильтре собирается ИЗ ЗАКАЗОВ ВЫБРАННОГО ДНЯ, а не из справочника по
городу сотрудника.** Так «Астана видит астанинских, Алматы — алматинских» получается само:
заказы кладовщику уже отфильтрованы по его складу (`cityFilter` в `renderSorting`).

**Фильтровать сам справочник по `couriers.city_id` было бы ОШИБКОЙ.** Заказы, забранные в
Талдыкоргане, физически привозят на склад Алматы (`sortingCityId`), а у того курьера в
карточке стоит Талдыкорган — он исчез бы из фильтра, хотя его заказы в списке есть. Тот же
приём, что в «Партнёрах по городам» (раздел 8яг): варианты берём из данных, а не из
справочника.

**Выбранный курьер сбрасывается, если в новом дне его заказов нет.** Иначе после смены даты
в списке его нет, выбор не виден, а таблица пуста — выглядит как поломка. То же для пункта
«— курьер не назначен —».

Пункт «— курьер не назначен —» имеет значение `-`: пустую строку в `<option value>` не
отличить от «все курьеры», а такие заказы спрашивают отдельно.

Проверено на подставных данных: все курьеры — 4 заказа, Нурлан — 1, Ермек — 1,
«не назначен» — 2; колонка показывает имя заборщика, а у заказа без заявки — «не назначен».

## 6a. Модуль «Заказы партнёров» (KET) — особенности загрузки

Самые большие таблицы в базе: `inbound_orders` (36 тыс. строк, 47 МБ) и `inbound_order_items`
(87 тыс. строк, 21 МБ). Поэтому модуль грузится лениво и постранично, и с ним связаны три вещи,
которые легко сломать.

**`S.inbound_orders` — признак «модуль ещё не открывали».** Модуль проверяет именно
`if(!S.inbound_orders)`, чтобы понять, нужна ли первая загрузка. Поэтому никакой другой код не
должен создавать этот массив «про запас». Так уже ломалось: обработчик Realtime делал
`if(!S[key])S[key]=[]`, и один заказ, прилетевший от KET до открытия модуля, делал массив
непустым — первая загрузка не срабатывала, и вместо списка показывалась пара случайных строк.
Исправлено 18.09.2026: для `inbound_orders` обработчик выходит, если массива ещё нет.

**Обновления от KET не должны перерисовывать чужие модули.** Данные KET видны только в своём
модуле — ни счётчика в меню, ни на дашборде у них нет. Поток заказов от KET может идти почти
непрерывно, и раньше он перерисовывал текущий экран каждые 4 секунды, какой бы модуль ни был
открыт: список дёргался, прокрутка сбрасывалась. Теперь перерисовка планируется только при
`S.tab==='ket_orders'`; в памяти данные обновляются всегда.

**Режим «вся история» залипает — помните об этом.** В `loadInbound` параметр `full` по умолчанию
наследуется от прошлого вызова (`_inboundFullHistory`). Стоит один раз применить фильтр — он
грузит всё, — и дальше любой вызов `loadInbound()` без явного `full` снова тянет всю историю.
Так фоновое обновление раз в 3 минуты заново качало 36 тысяч заказов со всеми позициями каждый
раз, когда пользователь возвращался в модуль. Исправлено 18.09.2026: фоновое обновление для
`ket_orders` больше не трогает данные вообще, а обновляет только счётчики (три запроса `head:true`,
ноль строк) — строки и так приходят через Realtime. Если добавляете новый вызов `loadInbound`,
**указывайте `full` явно**.

**Фильтрация идёт в базе, а не в браузере (с 20.09.2026).** Раньше любой фильтр включал полную
загрузку: 36 тыс. заказов и 87 тыс. позиций ради полусотни строк на экране. Теперь всё, что
выражается запросом, считает база: даты, статусы (`send_status`, `status_kz`, `call_status`),
тип доставки (курьерская — `index is null`, почтовая — заполнен), общий поиск по
`external_id`/`client`/`phone` и фильтры по колонкам из карты `INB_SERVER_COL`.

Что запросом НЕ выразить — партнёр (вычисляется через состав заказа), склад, звонки,
переведённые на русский статусы — по-прежнему требует полной загрузки: `inboundNeedsFullLoad()`
решает это честно, лучше подождать, чем показать неполный список. **Добавляете новый фильтр по
колонке — либо внесите поле в `INB_SERVER_COL`, либо он автоматически потянет полную загрузку.**

Замер на заглушке (поиск по номеру заказа): было 147 запросов и 108 381 строка, стало 5 запросов
и 100 строк. Фильтр по партнёру остался на полной загрузке — это и проверялось отдельно.

Тонкость с поиском по телефону: строка запроса режется по пробелам и запятым (чтобы можно было
вставить сразу много номеров заказов), поэтому `+7 701 234 56 78` распадается на куски. Отдельно
добавляется поиск по цифрам всей строки целиком — иначе телефон не находился бы вовсе.

**Позиции грузятся пачками параллельно.** `loadInbound({full:true})` тянет позиции запросами по
500 id. Раньше это был последовательный цикл с `await` внутри — на 36 тысячах заказов 73 запроса
строго один за другим, десятки секунд. Теперь пачки идут по 6 одновременно (как в `dbList`).
Полная загрузка включается при первом же вводе в любой фильтр — имейте в виду, она тяжёлая.

## 6b. Отправка заказов в KET — трек-номер

Документация KET: https://ketkz.com/api/doc.txt. У них **всего два метода**:
`send_order.php` (создать заказ) и `get_orders.php` (прочитать заказы). **Метода обновления
не существует** — это главное ограничение, из которого следует всё остальное.

**Трек-номер (штрихкод) отправляется ДВУМЯ полями сразу — `kz_code` И `barcode`.**
Не убирайте ни одно из них без проверки на живом заказе. По документации это узнать нельзя:
среди полей ОТПРАВКИ там нет ни `barcode`, ни `kz_code` (последний описан только как поле
ОТВЕТА `get_orders`: «kz_code - трекинг код - когда заказ идёт почтой»).

Что показали проверки на живых заказах (20–21.09.2026), по порядку:

| Что отправляли | Колонка Barcode в KET |
|---|---|
| только `kz_code` | пусто |
| `kz_code` + `barcode` | **заполнена** |
| только `barcode` | пусто (проверено дважды) |

То есть работает именно пара. Почему — неизвестно, и выяснять это можно только живыми
отправками: метода обновления у KET нет, каждая проверка — новый заказ у них в системе.

**Грабли, на которые уже наступили.** После удачного теста с двумя полями `kz_code` убрали,
решив, что сработал `barcode`. Тест этого не показывал: уходили оба поля, и какое из них
сработало, из него не следовало. Трек перестал доходить, и заметили это не сразу — заказы
уходили к KET без трека, а дослать его нечем. Вывод общий: **не удаляйте поле на основании
теста, в котором оно не проверялось отдельно.**

Прежде чем винить KET, проверяли свою сторону целиком — и правильно делали:
`orderToKet()` кладёт поле, `callKet()` шлёт объект в нашу функцию `ket-proxy`, а та собирает
`data` как `{...order, secret}`, то есть **передаёт все поля насквозь и ничего не фильтрует**.
Значит поле действительно доходило до KET.

Отправляем при ЛЮБОМ типе доставки, если `track` заполнен. Условия «только почтовые» быть не
должно — курьерский заказ с треком тогда уходит без него.

**Метода обновления у KET нет** (всего два: `send_order.php` и `get_orders.php`), поэтому трек
уходит только в момент создания заказа. Отправили раньше, чем получили трек у Казпочты —
дослать нечем. Отправку это НЕ блокирует (решение владельца): заказ уходит без трека, а
`ketSendWarnNoTrack` лишь предупреждает. Не превращайте предупреждение обратно в вопрос.

**Следствие отсутствия метода обновления:** трек уходит только в момент отправки. Если заказ
отправили в KET до получения трека у Казпочты — дослать нечем, только пересоздавать заказ.
Поэтому порядок действий важен: **сначала получить трек, потом отправлять в KET.**

**Вес заказа уходит в поле `actual_weight`**, в килограммах, ровно тем числом, что стоит в
карточке заказа. Имя поля дал KET 21.09.2026 (по их приёмке 75747498), в документации его нет.
Отправляем ТОЛЬКО когда вес заполнен: выдумывать его нельзя, метода обновления у KET нет, и
неверный вес останется у них навсегда. Этим же закрыта просьба «по Астане можно не делать» —
там заказы не взвешивают, поле пустое, и ничего не уходит само. Понадобится слать вес и по
Астане — достаточно начать его проставлять в заказах, код менять не нужно.

**Отправку это НЕ блокирует и блокировать не должно** (решение владельца от 20.09.2026):
заказ без трека уходит в KET как обычно, просто без полей трека. Пользователю показывается
уведомление `ketSendWarnNoTrack` — при массовой отправке в тексте подтверждения, при
одиночной тостом после успешной отправки. Если будете это трогать — не превращайте
уведомление обратно в вопрос, который мешает отправить заказ.

**Что видно при отправке.** `sendOrderToKet` пишет в консоль браузера то, что уходит
(`KET → отправляем`), и ответ KET (`KET ← ответ`), а в сообщении об успехе прямо говорит:
«трек AP… передан». Без этого «у KET колонка Barcode пустая» невозможно отличить от
«мы его и не передавали» — именно на этом и потеряли время.

**Как проверить, что трек реально доехал:** отправить почтовый заказ с треком, затем открыть
«Заказы партнёров» и посмотреть колонку «Трек номер» (это и есть `kz_code` из ответа KET).
Если там пусто — значит `send_order.php` поле не принимает, и надо запрашивать у KET отдельный
способ передачи; наша сторона при этом сделана верно.

## 6c. Бланк Казпочты — данные отправителя в настройках

Данные отправителя (от кого, откуда, телефон поддержки, индекс, договор, код платежа) были
**впечатаны в сам PDF-шаблон**: сменить ИП или номер договора можно было только пересобрав файл.
С 20.09.2026 они хранятся в таблице `mail_label_settings` и правятся в CRM:
**Настройки → «Бланк Казпочты»**.

**Два файла шаблона, не перепутайте:**

| Файл | Что это |
|---|---|
| `assets/mail-label-blank.pdf` | чистый бланк, из него печатаем |
| `assets/mail-label-template.pdf` | исходный, с впечатанными данными — оставлен как образец «как было» |

Чистый получен из исходного удалением шести надписей. Технически: их содержимое лежало
**отдельным слоем** — последний поток PDF, который сначала рисует саму форму (`/TPL1 Do`), а
потом кладёт текст поверх. В этом потоке у шести блоков `BT x y Td [...]TJ ET` содержимое
заменено на пустое, **дополненное пробелами до прежней длины** — чтобы не сдвинулись байтовые
смещения и не сломался xref. Размер файла совпадает с исходным до байта.

**Почему нельзя было просто закрасить белым:** казахские подписи правой колонки стоят
вплотную — «сумма наложенного платежа» на 9 пунктов выше строки «Откуда». Прямоугольник,
закрывающий адрес целиком, срезал бы им низ букв.

Координаты (базовая линия, отсчёт сверху, страница 842×595): от кого 96/156, откуда 96/190,
поддержка 96/204, индекс 196/220, договор 65/351, КОД ПЛАТЕЖА 264/126 и число 480/126.

**Данные берутся по ИП, выбранному в заказе.** Так же устроено у KET: там «Настройки
отправителей» — список ИП, и при выборе ИП данные бланка меняются. У нас выбор уже был:
в карточке ПОЧТОВОГО заказа поле «ИП для Почты» (`orders.post_ip_id`), просто бланк его не
использовал. Теперь `mailLabelCfgFor(order, common)` берёт поля выбранного ИП из справочника
`post_ips`, а чего у ИП не задано — подставляет из общих настроек. «От кого» складывается
как «приставка + название ИП» (`ТОО QP Service` + `ИП Жадыра`), как в KET.

Поля у ИП: `label_prefix`, `from_addr`, `support`, `index_code`, `contract`, `payment_code`.
Пустое поле означает «взять общее» — заполнять нужно только то, что у этого ИП своё.

**Номер ШПИ и штрих-код.** Печатаются в правой колонке: номер над подписью «№ ШПИ»,
штрих-код под штамп-квадратом — там же, где их ставит бланк, который печатает KET.
Координаты сняты из самого шаблона через pdf.js, а не подобраны на глаз: подпись «№ ШПИ»
стоит на 511/219, подписи штампа — на 273 и 283.

Код рисуется настоящим Code128 (библиотека JsBarcode, она уже подключена в index.html и
используется для кодов заказов), вставляется в PDF картинкой PNG и кэшируется по номеру —
в одной печати бывают десятки бланков. Проверено чтением обратно: сгенерированный PDF
рендерится и распознаётся сканером как исходный номер. Самодельные «полоски по цифрам»
для этого не годятся — такой рисунок не читается.

Если трека у заказа нет, номер и код просто не печатаются, бланк выходит как раньше.

**Суммы и индекс получателя.** Обе денежные строки бланка — «сумма объявленной ценности» и
«сумма наложенного платежа» — показывают ОДНУ И ТУ ЖЕ сумму заказа прописью:
«1 500 (одна тысяча пятьсот тенге 00 тиын)». Считает `amountForLabel`; склонения проверены
на 1500/2000/5000/21 («одна тысяча», «две тысячи», «пять тысяч», «двадцать один»).
Индекс внизу справа — это индекс ПОЛУЧАТЕЛЯ из карточки заказа (`orders.index`), не путать
с индексом отправителя вверху (он из настроек).

**У файлов в `assets/` тоже есть метка версии.** Шаблон грузится через `fetch` из кода, а не
тегом, и сначала метки не было — правка шаблона не доезжала, браузер отдавал старую копию
из кеша. Поймано на живом примере: в бланке оказались ОБЕ строки, старая «0 (ноль тенге)»
и новая сумма. `tools/refresh-versions.py` теперь проставляет версии и для `assets/`,
но правит файлы `js/` уже после того, как посчитал их отпечатки — **после правки шаблона
скрипт нужно прогнать дважды**, пока не скажет «менять нечего».

**Значения по умолчанию продублированы в коде** (`MAIL_LABEL_DEFAULTS`) — ровно те, что были
на старом бланке. Если таблицы нет или она недоступна, бланк печатается как раньше, а не пустым.

## 6d. Ежедневный отчёт в Телеграм

Бот «JYLDAM Logistics» присылает сводку по работе за день. Считает и отправляет Edge Function
`daily-report`, расписание — в планировщике базы (`pg_cron` + `pg_net`), SQL лежит в
`db/9-ТЕЛЕГРАМ-ежедневный-отчёт.sql`.

**Два отчёта:** вечерний (23:00 по Астане — итоги дня) и утренний (9:00 — что мешает работать:
без типа доставки, почтовые без веса, без трека, без индекса). Тело запроса выбирает какой:
`{"kind":"evening"}` или `{"kind":"morning"}`; утренний не обязателен.

**Что в вечернем:** заявок на забор; заказов всего и в разрезе курьерских/почтовых; по городам
забора; сколько принял склад (по городам, Талдыкорган относится к Алматы — как в «Сортировке»);
сколько заказов правили менеджеры и кто именно; проблемы; выручка, расходы и прибыль за день.

**«Кто сколько заполнил» берётся из модуля «Заполнение»** — отметки `filled_at` и
`filled_by_name` (решение владельца 30.09.2026), чтобы цифры в Телеграме и на экране
«Заполнения» совпадали.

До этого здесь стоял журнал действий — «кто правил заказы». Это другое и по смыслу, и по
числу: правка адреса в чужом заказе попадала в счёт, а заполнение вчерашнего заказа не
попадало вовсе.

Три тонкости, без которых цифры разойдутся:

1. **Запрос отдельный**, а не по массиву `orders`: тот собран по дате СОЗДАНИЯ, а сегодня
   заполняют и вчерашние заказы (раздел 8j) — они бы в счёт не попали. Поэтому итог по
   людям может быть БОЛЬШЕ числа заказов за день, и это правильно.
2. **Среднее время считается по правилу модуля** (`fillOrderSecs`): только если заказ
   заполнил тот же человек, который его брал, и только если уложился в десять минут
   (`FILL_MEASURE_MAX_MIN`). Дольше — человек отошёл, а не работал.
3. **Если колонок учёта в базе нет** (db/11 не выполнен), строка не исчезает: считается
   по-старому, по журналу правок. Проверка — `fillReady`.

**Совпадение проверено прогоном обеих реализаций на одних данных:** модуль и отчёт дали
одинаковые числа и одинаковое среднее, включая исключение двадцатиминутного заказа и
заказа, который брал один, а заполнил другой.

**Про `activity_log` и `processor_id` — почему не они.** `processor_id` подставляется от
партнёра автоматически при создании заказа и не говорит, кто сел и переписал бланк.
В журнале запись появляется только если поля реально изменились (`dbUpdate` пишет лог при
непустом `buildChanges`), и один заказ могли править несколько раз — там считаются заказы,
а не строки журнала.

**Заказ без типа доставки — не почтовый.** `delivery_id` пустой означает «ещё не заполнен»;
если отнести такие к почтовым, счётчик «почтовых без веса» раздувается пустышками. В отчёте
они отдельной строкой «без типа доставки» — это ровно те, которых не видит склад (раздел 6).

**«Не отправлено в KET» не считаем.** Отправка в KET — ручное решение по каждому заказу,
обязанности отправлять нет, поэтому такой счётчик был бы шумом. Вместо него: сколько ушло и
сколько из них ушло БЕЗ трека — вот это настоящая потеря, метода обновления у KET нет
(раздел 6b), дослать трек нечем.

**Проверка Казпочты идёт номером УЖЕ ВЫДАННОГО заказа.** Функция берёт почтовый заказ
сегодняшнего дня, у которого уже есть трек, и повторяет запрос с его `OrderNum`: Казпочта
отвечает кодом 20012 и прежним ШПИ, нового номера не тратит. **Не подставляйте свой номер
вроде `PING`** — первый же такой запрос израсходует настоящий ШПИ, а номер навсегда займётся
и потом столкнётся с реальным заказом (`genOrderCode()` выдаёт 7 цифр). Если за день нет ни
одного почтового заказа с треком, проверка просто пропускается.

**Если отчёт не собрался, приходит сообщение об ошибке.** Молчание в 23:00 легко принять за
«день без происшествий», поэтому сбор обёрнут в `try/catch`: текст ошибки уходит тем же
сообщением, а функция отвечает `500`, чтобы сбой был виден и в `cron.job_run_details`.

**ПРИБЫЛЬ СЧИТАЕТСЯ В ДВУХ МЕСТАХ — это единственное такое место в системе.** Формула в
функции (`orderFinance`) — построчная копия `calcOrder()` из `js/07-kalkulyaciya.js` вместе с
наследованием нормативов (`calc_settings` → предыдущий месяц → строка без периода), городскими
и персональными ставками, снимком `orders.calc` и правилом «оплачено отправителем». **Меняете
статьи расходов в CRM — поправьте и здесь**, иначе отчёт начнёт тихо расходиться с экраном
«Калькуляция». Совпадение проверялось прогоном обеих версий на одних данных.

Одно расхождение сознательное: в месячной сводке Калькуляции межгород пересчитывается по дате
ОТПРАВКИ (`freightByShipDate`, раздел 5), а в дневном отчёте берётся `intercity_cost` самого
заказа. Для одного дня пересчёт по отправкам смысла не имеет.

**Список полей заказа сверяется с базой на лету.** Функция сначала читает одну строку
`orders` целиком, смотрит набор колонок и запрашивает только те, что реально есть.
Так вышло не от хорошей жизни: запрос несуществующей колонки роняет ВЕСЬ отчёт, хотя без
неё считается всё остальное. Отсутствующие перечисляются в сообщении строкой «нет полей в
базе», чтобы потеря была видна, а не тиха.

**В базе нет `orders.ket_id` и `orders.calc`, хотя код CRM пишет в обе** (обнаружено
22.09.2026 как раз этим отчётом). Следствия разные: `calc` — это снимок расчёта по заказу,
без него Калькуляция просто всегда считает по текущим нормативам; а вот `ket_id` — отметка
«отправлен в KET», и она не сохраняется, то есть галочка «KET ✓» пропадает после
обновления страницы и заказ можно отправить в KET повторно, не заметив. Отчёт берёт
отправки в KET из `activity_log` (`action='ket'`) — там запись есть.

**Передать конкретный день:** `{"kind":"evening","date":"2026-09-21"}`. Нужно, чтобы
проверить отчёт на настоящих числах, не дожидаясь вечера. Неразобранная дата молча
откатывается на сегодня. Планировщик `date` не передаёт.

**В сообщение уходят ТОЛЬКО ЦИФРЫ** — ни ФИО, ни телефонов, ни адресов. Телеграм чужой
сервис, клиентской базе там не место. Понадобится список — он остаётся в CRM.

### Бот отвечает на команды (22.09.2026)

Телеграм при каждом сообщении дёргает **ту же функцию** `daily-report` — отдельной не
заводили. Команды: `/report`, `/report вчера`, `/report 21.09`, `/problems`, `/help`.
Дата разбирается `parseDayFromText` — понимает «21.09», «21.09.2026», «2026-09-21»,
«вчера», «позавчера», «сегодня».

**Два входа в одну функцию, и путать их нельзя.** Планировщик приходит с заголовком
`x-report-key` и секретом `REPORT_KEY`. Телеграм — с заголовком
`x-telegram-bot-api-secret-token` и секретом `TELEGRAM_WEBHOOK_SECRET`, который задаётся
один раз в `setWebhook`. Проверка вебхука идёт ПЕРВОЙ, `REPORT_KEY` для неё не нужен.

**Отвечаем сразу, работу доделываем в фоне.** Отчёт собирается ~10 секунд, а Телеграм,
не дождавшись ответа, шлёт то же сообщение снова — и отчёт приходит дважды. Поэтому
`200` отдаётся немедленно, а сбор уходит в `EdgeRuntime.waitUntil` (или просто без
`await`, если его нет). Плюс повтор отсекается по `update_id`.

**Накопившаяся очередь.** Пока вебхук не настроен, Телеграм хранит сообщения около суток
и вываливает их все разом при включении. Поэтому в `setWebhook` стоит
`drop_pending_updates: true`. Именно это и выглядело как «бот пишет по два раза».

**Вебхук включается запросом к самой функции** (`{"action":"setwebhook"}`), а не вручную
через `api.telegram.org`. Причина: вручную токен бота стоит прямо в адресе, и на любой
другой токен — например отозванный через `/revoke` — Телеграм отвечает глухим
`404 Not Found`, по которому не догадаться, в чём дело. Мы на это потратили полчаса.
У функции токен уже в секретах. Есть ещё `webhookinfo` и `deletewebhook`.

**Если меняете токен через `/revoke`, сразу замените и секрет `TELEGRAM_BOT_TOKEN`** —
иначе молча перестают приходить и отчёты, и ответы бота.

**Бота может найти посторонний.** Функция отвечает только в чат из `TELEGRAM_CHAT_ID`,
остальным молча ничего — но обязательно с кодом `200`, иначе Телеграм будет слать то же
сообщение снова.

**Защита.** У функции выключен «Verify JWT» (её зовёт планировщик, а не вошедший сотрудник),
поэтому вместо входа стоит собственный ключ `REPORT_KEY`: без заголовка `x-report-key`
функция не отвечает никому. Ключ лежит в секретах и в тексте задания планировщика.

**Часовой пояс — важно.** `pg_cron` считает по Гринвичу, а Казахстан круглый год UTC+5 и
часы не переводит. Поэтому 23:00 по Астане это `0 18 * * *`, а 9:00 — `0 4 * * *`. Границы
самого дня функция тоже считает по местному времени (`localDayBounds`), иначе вечерний отчёт
захватывал бы кусок вчерашнего дня — та же ловушка, что была с `localToday()` в CRM.

**Грабли при настройке — на них ушёл почти час.**

`net.http_post` возвращает НОМЕР ЗАПРОСА, а не результат. Ответ приходит позже и лежит в
`net._http_response`; смотреть надо по этому номеру (или `order by id desc limit 3`), иначе
кажется, что всё прошло. Коды: 404 — функция не выложена, 403 — ключ не совпал с секретом
`REPORT_KEY`, 500 «REPORT_KEY не задан» — секрет не создан.

`timeout_milliseconds := 60000` обязателен. По умолчанию `pg_net` ждёт 5 секунд, а отчёт
собирается дольше. Причём функция при этом ДОРАБАТЫВАЕТ и отчёт присылает — просто в
`net._http_response` остаётся «Timeout of 5000 ms reached», и выглядит это как провал.

Редактор SQL в Supabase выполняет ВСЁ содержимое окна, а показывает результат только
последнего запроса. Файл `db/9`, прогнанный целиком, создаёт задания с текстом-заглушкой
`СЮДА-КЛЮЧ` вместо ключа — они молча получают 403 в 23:00. Выполнять по одному блоку:
выделить мышкой и Run. Проверка в блоке 4 показывает колонку `ключ_не_подставлен`.

Три значения, которые легко перепутать: токен бота (`123:AA…`) → секрет `TELEGRAM_BOT_TOKEN`;
идентификатор чата (`812929478`) → `TELEGRAM_CHAT_ID`; придуманный нами ключ → секрет
`REPORT_KEY` И заголовок `x-report-key`. К Телеграму последний отношения не имеет.

**Деньги.** Ни Телеграм, ни планировщик отдельно не стоят: бот бесплатен, `pg_cron` и
`pg_net` входят в тариф Supabase.

## 7. Интеграция с Казпочтой (SOAP API)

Курьер получает трек-номер для почтовых заказов через кнопку «📮 Получить трек» — вызывает Edge
Function `kazpost-get-barcode`, которая обращается к SOAP-сервису Казпочты (`GetAddrLetter`, боевой
URL `http://rates.kazpost.kz/postratesprod/endpoints`).

### Два контура у Казпочты — и разные диапазоны номеров (21.09.2026)

На одном сервере `rates.kazpost.kz` у Казпочты **два адреса сервиса**, и они выдают номера из
РАЗНЫХ диапазонов. Один и тот же запрос, тот же ключ, тот же номер заказа:

| Адрес | Ответ |
|---|---|
| `…:80/postratesprod/endpoints` | `AP081985585KZ` |
| `…:80/postratesws/endpoints` | `QS000000014KZ` |

**Этим и объяснялась вся история с префиксом QS**, на которую ушло несколько дней. Перебирали
`ProductCode` (P103/P145/P109/P126A), `MailCtg`, `SendMethod`, `EnvelopeSize`, формат `OrderNum`,
формат телефона — ни одно из этого не было причиной. Казпочта успела «привязать QS к ключу», и
это было правдой: просто на другом контуре.

Как нашли: программист Казпочты прислал скриншот SoapUI со своим запросом — в адресной строке
стоял `postratesws`, а у нас в коде был `postratesprod`. Отправили ИХ ЖЕ запрос на оба адреса и
получили разные префиксы.

**Адрес теперь в секрете `KAZPOST_ENDPOINT`** (Supabase → Edge Functions → Secrets), чтобы
переключать контур за минуту без правки кода. Значение по умолчанию, если секрет не задан, —
`http://rates.kazpost.kz:80/postratesws/endpoints` (тот, что даёт QS). Вернуться на прежний:
задать секрет со значением `http://rates.kazpost.kz:80/postratesprod/endpoints`.

**27.09.2026: QS перестал приходить, номера идут с префиксом AP.** Проверено: контур тот
же (`postratesws`, секрет `KAZPOST_ENDPOINT` не задан вовсе), `ProductCode=P103`,
`MailCtg=4`, `SndrCtg=2`, договор прежний — запрос собирается ровно тот же, что давал QS.
Категория тоже ни при чём: бланки с суммой (категория 4) и с нулём (категория 3) одинаково
дали AP.

Скорее всего, выделенный диапазон исчерпан: первый QS был **QS000000014KZ**, то есть
диапазон только начинался и был, видимо, небольшим. Казпочта при этом не возвращает ошибку —
молча отдаёт номер из общего AP, и заметить можно только по префиксу. **Кодом не лечится,
вопрос к Казпочте.** AP-номера рабочие: на них жили до сентября.

Прежде чем снова искать причину в коде — посмотрите приписку «контур …» в сообщении о
полученном треке. Если там `postratesprod`, значит выложена не та версия функции либо
появился секрет `KAZPOST_ENDPOINT`.

### Диапазон QS привязан К КЛЮЧУ (владелец подтвердил 28.09.2026)

То есть префикс выбирает не контур и не `ProductCode`, а то, **какой ключ лежит в секрете
`KAZPOST_KEY`**. Эталонный запрос, давший `QS000000014KZ`, шёл с ключом, начинающимся на `bbfc50…` —
и это главный и, похоже, единственный подозреваемый: если в секрете другой ключ, всё
остальное не имеет значения.

**Сам ключ здесь НЕ ЗАПИСАН, и записывать его сюда нельзя** — репозиторий публичный
(GitHub Pages раздаёт сайт из него), и до 28.09.2026 ключ полностью лежал в этом файле,
то есть был опубликован в интернете. Ключ живёт ровно в одном месте: секрет `KAZPOST_KEY`
в Supabase → Edge Functions → Secrets. Сверять его с нужным — по первым шести знакам,
которые CRM теперь пишет в сообщении о треке.

**Осторожно с последними знаками при сверке на глаз.** Ключ читали со скриншота SoapUI, и
в этом файле он неделю стоял с ОШИБКОЙ в одном символе (`…4568 8f…` вместо `…4566 8f…`) —
6 и 8 на снимке различаются плохо. Если кто-то копировал ключ отсюда в секрет, он вводил
неверный — а это само по себе объясняет отказы и чужой диапазон. Источник ключа — владелец
и Казпочта, не этот файл.

**Ключ теперь виден в самой CRM** — рядом с номером и контуром: «Трек-номер получен:
AP… · контур postratesws · ключ bbfc50…(32 зн.)». Показываются ТОЛЬКО первые шесть знаков
и длина: сверить с нужным ключом этого достаточно, подобрать по ним нельзя. Та же подпись
стоит и в сообщении об ОШИБКЕ — отказ по ключу иначе не отличить от отказа по данным.

Причина ровно та же, по которой раньше добавили контур: какой ключ реально выложен, из
интерфейса было не видно, и каждый раз это выяснялось руками в панели Supabase.

**Ключ сверяется по ОТПЕЧАТКУ, а не по первым знакам.** Записанный в этом файле ключ
отличался от настоящего ровно одним символом в середине (`…4568 8f` против `…4566 8f`;
6 и 8 на скриншоте похожи), а первые шесть знаков у них одинаковые — `bbfc50`. То есть
подпись «ключ bbfc50…», добавленная сначала, эту ошибку не различала вовсе.

Теперь CRM пишет начало, конец и **отпечаток** — восемь знаков SHA-256 от ключа
(`keyHint()` в функции). Отпечаток меняется от любого различия, а ключ по нему не
восстановить, поэтому его можно держать здесь:

| Ключ | Отпечаток |
|---|---|
| правильный, от владельца (28.09.2026) | **`f57146d5`** |
| ошибочный, что лежал в этом файле | `ab917208` |

Совпал `f57146d5` — в секрете нужный ключ, причину AP надо искать не в нём.

**Проверить ключ на УЖЕ ИСПОЛЬЗОВАННОМ номере заказа нельзя** (проверено): Казпочта
сначала смотрит `OrderNum` и отвечает `20012` с прежним ШПИ ОБОИМ ключам — и верному, и
ошибочному. Бесплатной проверки ключа у них нет вовсе: ни один метод «только на чтение»
(`GetBarCodeFromOrderNum`, `GetBarcodeInfo`, `GetTrf`, `GetPostRate`) ключа не принимает.
Значит ключ проверяется ровно одним способом — новым бланком, и это стоит одного ШПИ.

**Порядок проверки теперь короткий:** получить трек на одном бланке → посмотреть в
сообщении, каким ключом спросили → если не `bbfc50…`, заменить секрет `KAZPOST_KEY` и
повторить. Менять по одному значению за раз и по одному бланку на проверку: каждый новый
бланк тратит настоящий ШПИ.

Оговорка к предыдущему разделу: раз диапазон привязан к ключу, «postratesws — тестовый
контур» остаётся догадкой, а не выводом. Факт же — что боевой контур не знает
`QS000000014KZ` — никуда не делся и объясняется проще: номер выдан на другом контуре,
базы у них разные.

### Секреты читаются ОДИН РАЗ, при запуске функции

Все `Deno.env.get(...)` в `kazpost-get-barcode` — верхнеуровневые `const`. Supabase держит
запущенный экземпляр функции тёплым и переиспользует его, поэтому **изменённый секрет
может не подействовать, пока экземпляр не перезапустят**. Надёжный способ — перевыложить
функцию.

Именно это спутало разбор 28.09.2026: владелец поменял номер договора, а в отправленном
запросе остался прежний — и первым делом возникло подозрение, что значение зашито в коде.
Проверено построчно: **не зашито**, читается только из секрета, а при пустом секрете
функция вообще отказывается работать («Не заданы секреты на сервере»).

**Единственное значение в этом запросе, у которого ЕСТЬ значение по умолчанию в коде** —
телефон отправителя: `KAZPOST_SNDR_PHONE || "77000000000"`. В эталоне Казпочты там
`777777777`. Остальные поля отправителя без секрета не работают вовсе, а константы
в шаблоне (`SndrCtg 2`, `RcpnCountry`/`SndrCountry` «Казахстан», пустой `Marks`)
совпадают с эталоном.

**Отсюда правило при любой сверке запроса:** сначала перевыложить функцию, потом смотреть
«Казпочта → отправили». Иначе сверяете не с тем, что в секретах.

### РАЗГАДКА: KET не спрашивает номер у Казпочты, а генерирует его сам (28.09.2026)

Владелец достал их скрипт `set_KzCode.php`. Никакого обращения к SOAP-сервису там нет
вообще. Что он делает:

1. берёт МАКСИМАЛЬНЫЙ уже использованный номер с префиксом QS — из своей же базы
   (`MAX(kz_code) … substring(kz_code,1,2)='QS'`), с кешем в Redis (`max_kz_code_ket`);
2. прибавляет единицу к восьмизначной серии (`substr($maxcodeStr, 2, 8)`);
3. считает контрольный разряд и складывает `QS` + 8 цифр + разряд + `KZ`;
4. пишет номер себе в заказ и отдаёт партнёру.

**Поэтому у них «QS в любое время и даже на пустой заказ»** — Казпочту они при этом не
трогают, и их не касаются ни ночное обслуживание, ни чужие диапазоны. Мы же просим
Казпочту ВЫДАТЬ номер, и она выдаёт из того диапазона, который у неё свободен, — отсюда
AP, AT и вся чехарда.

**Контрольный разряд — стандарт UPU S10, и он теперь известен точно:** веса
`8,6,4,2,3,5,9,7` по восьми цифрам серии, сумма произведений mod 11; остаток 0 → разряд 5,
остаток 1 → разряд 0, иначе `11 − остаток`.

Проверено на шести настоящих номерах Казпочты — **сходится на всех**:

| ШПИ | Серия | Разряд в номере / по алгоритму |
|---|---|---|
| `QS000000014KZ` | 00000001 | 4 / 4 |
| `AP082220677KZ` | 08222067 | 7 / 7 |
| `AP081985585KZ` | 08198558 | 5 / 5 |
| `AP082192300KZ` | 08219230 | 0 / 0 |
| `AT001251243KZ` | 00125124 | 3 / 3 |
| `AP082192295KZ` | 08219229 | 5 / 5 |

**Важное следствие про наш сентябрьский QS:** `QS000000014KZ` — это серия `00000001`,
то есть **порядковый номер ОДИН**. Не «диапазон почти исчерпан», а «диапазон только
что открыт и выдан самый первый номер». У KET счётчик стоит около `01000010`, то есть
их диапазон совсем другой — продолжать их нумерацию НЕЛЬЗЯ, это будут их номера.

**Что отсюда следует для нас.** Путь к QS не через параметры запроса, а такой же, как
у KET:

1. получить у Казпочты **свой диапазон QS** — начало и размер (наш `00000001`, похоже,
   именно его начало, но подтверждение нужно от них);
2. генерировать номера самим, с этим контрольным разрядом;
3. при регистрации отправления передавать свой номер в поле **`<sch:Barcode>`** — оно
   есть в `AddrInfo` как поле ЗАПРОСА (нашли в схеме 27.09), а не только в ответе.

Пункты 2 и 3 — работа на нашей стороне, и она несложная. **Пункт 1 без Казпочты
невозможен:** выдумывать диапазон нельзя, номера пересекутся с чужими, и посылки
потеряются. Поэтому вопрос к ним остаётся, но формулируется теперь точно: «подтвердите
начало и размер выделенного нам диапазона QS, дальше мы присваиваем номера сами».

### Разбор схемы 28.09.2026: методов восемнадцать, и контуры — РАЗНЫЕ БАЗЫ

Схему (`http://rates.kazpost.kz/postratesprod/postratesws.wsdl`) разобрали целиком, а не
только `GetAddrLetter`. Операций в ней **восемнадцать**, и три меняют картину:

| Метод | Что делает | Ключ нужен? |
|---|---|---|
| `GetBarCodeFromOrderNum(ordernum)` | какой ШПИ выдан по НАШЕМУ номеру заказа | **нет** |
| `GetBarcodeInfo(Barcode)` | что записано по самому ШПИ | **нет** |
| `GetStatus(Barcode…)` | статусы движения, списком | нет |
| `GetParcelBarcode(Key, AddrInfo…)` | ещё один способ получить номер, отвечает СПИСКОМ `Barcodes` | да |
| `GetAddrLetterUsingBarcode(barcode)` | бланк по уже существующему ШПИ | нет |
| `GetBarCodeNext(barCode, product, sendMethod, mailCategory, idCompany)` | «следующий номер», отвечает `Excell`+`Id` | нет |

Первые два — **бесплатная справка: ключ не нужен, номер из диапазона не тратится.**
Для проверок пользуйтесь ими, а не повторным `GetAddrLetter`. Готовый инструмент —
`tools/kazpost-lookup.py` (спрашивает оба контура сразу):

```
python3 tools/kazpost-lookup.py 2514200 AP081985585KZ
```

**ГЛАВНОЕ: у контуров РАЗНЫЕ базы, и боевой не знает номер QS.** Проверено 28.09.2026:

| Запрос | `postratesprod` | `postratesws` |
|---|---|---|
| номер заказа 2514200 (эталон Казпочты) | `AP081985585KZ`, success | код 1033, `SQLException` |
| ШПИ `QS000000014KZ` | **«ШПИ не найден!» (20001)** | ORA-01033 (ночное обслуживание) |

То есть единственный QS-номер, который у нас есть, в боевой базе Казпочты **не
существует**. А контур, который его выдал, на простую справку отвечает исключением базы.

**Отсюда вопрос, без ответа на который QS искать нельзя: настоящие ли это номера.**
Если `postratesws` — тестовый контур со своей базой (а всё на это указывает: своя
нумерация с единицы, своя Oracle, ошибки на простых запросах), то посылка с QS-номером
в боевой системе не числится, и гоняться за этим префиксом не надо вовсе — надо просить
Казпочту выделить QS-диапазон на БОЕВОМ контуре.

Проверку нужно закончить днём, когда ws поднимется: спросить оба контура про наш свежий
AP-номер. Знает только prod — контуры независимы, и вывод выше подтверждён.

**Замеченное попутно, до выяснения не трогать:**

- **`Marks` — ОБЯЗАТЕЛЬНОЕ поле, и убирать его нельзя ни в коем случае.** В опубликованном
  WSDL его в `AddrInfo` нет, и 28.09.2026 я записал здесь, что поле лишнее. **Это было
  неверно**, проверено живым запросом: боевой контур отвечает
  `SOAP-ENV:Fault · Validation error · Invalid content was found starting with element
  'SendMethod'. One of 'Marks' is expected.` — то есть сервер проверяет по СВОЕЙ схеме, где
  `Marks` обязателен и стоит ровно между `ProductCode`/`EnvelopeSize` и `SendMethod`.
  Наш боевой запрос собран верно; убрали бы — перестали бы выдаваться все треки сразу.
  **Вывод шире: опубликованный WSDL не совпадает с живой схемой**, сверять состав запроса
  по нему нельзя, только живым запросом с уже использованным `OrderNum`.
- `Barcode` в `AddrInfo` — поле ЗАПРОСА (подтверждено ещё 27.09): номер можно передать
  свой. Но свою нумерацию наугад не делать — у ШПИ контрольный разряд.
- `GetBarCodeFromOrderNum` **не требует ключа вообще** — по номеру заказа ШПИ узнает кто
  угодно. Наши номера семизначные и предсказуемые; для нас это не угроза (в ответе только

договору, то есть это ровно тот класс ошибки, который мог отдавать нас в общий диапазон AP.

вырезан** (`maskKey`): запрос попадает в консоль, светить там доступ-ключ незачем — для
сверки есть отпечаток.

**Три отличия от того, что слали мы:**

1. **`Key`** — у него начинается на `bbfc50…`. Диапазон QS, по словам Казпочты, привязан

2. **`EnvelopeSize` он не отправляет вовсе**, а мы всегда слали `M`. Поле необязательное —
   с 27.09.2026 не отправляем и мы, вернуть можно секретом `KAZPOST_ENVELOPE_SIZE`.
3. **`SndrIndex`** — у него `010000`, у нас `010009`.

У него `MailCtg=3` без сумм, то есть его запрос — это ровно наш **бланк с нулевой суммой**.
После правки набор и порядок полей у такого бланка совпадают с эталоном поле в поле.

**Схема сервиса: `http://rates.kazpost.kz/postratesprod/postratesws.wsdl`.** Разбор её
27.09.2026 дал то, чего нет в документации KET и Казпочты:

- **`Barcode` — поле ЗАПРОСА, а не только ответа.** Оно лежит в `AddrInfo`, то есть номер
  можно ПЕРЕДАТЬ свой, а не просить выдать. Похоже, так и работает KET: получает QS в любое
  время и даже на пустой заказ, потому что подставляет номер из выделенного ему диапазона.
  Мы это поле не отправляем вовсе — Казпочта берёт номер из того диапазона, который у неё
  свободен, отсюда и чехарда QS → AP → AT.
- **`PAY_CODE`** — в схеме есть, мы не отправляли. Добавлено секретом `KAZPOST_PAY_CODE`
  (тот самый «КОД ПЛАТЕЖА» с бланка). Не задан — не уходит.
- **`AddrLetPdf` в ответе** — Казпочта умеет возвращать готовый бланк в PDF. Пригодится,
  если к нашей отрисовке формы возникнут претензии на почте.
- Порядок полей у нас совпадает с `xs:sequence` схемы — здесь ошибки нет, проверено.

**Свою нумерацию НЕ делать наугад.** У ШПИ есть контрольный разряд, и номер, собранный без
знания выделенного диапазона и правила расчёта, будет нерабочим — бланки придётся
перепечатывать. Сначала подтверждение от Казпочты, потом код.

**Подтверждено 27.09.2026 по приписке «контур» в самом сообщении: `postratesws` выдаёт
AP.** То есть тот же контур, что в сентябре давал QS. Адрес правильный, секрета
`KAZPOST_ENDPOINT` нет, параметры запроса прежние — на нашей стороне менять нечего.
Номера за двое суток: QS…14 (сентябрь) → AP082192295KZ → AT001251243KZ → AP082192300KZ.

**27.09.2026, продолжение: пришёл номер с префиксом AT** (AT001251243KZ) — третий
диапазон за два дня, при неизменных полях запроса. Префикс выбирает Казпочта, мы им не
управляем: в запросе нет ничего, что его задаёт, кроме `ProductCode` и контура, а они те же.

Поэтому при ОДИНОЧНОМ запросе трека функция возвращает ответ Казпочты целиком
(`debug_raw_response`), а CRM пишет его в консоль браузера строкой «Казпочта ← ответ
целиком». В их XML встречаются поля, которых нет в документации, — по одному номеру
причину смены диапазона не понять, а по полному ответу шанс есть. В пачке ответ не
возвращается: полсотни XML никто читать не будет.

**Контур виден в ответе функции** (поле `contour`) и в сообщении CRM рядом с номером:
«Трек-номер получен: QS… · контур postratesws». Добавлено 27.09.2026, когда номера вдруг
пошли с префиксом AP и выяснять, откуда они, пришлось по секретам вручную. Префикс и
контур связаны жёстко: `postratesws` → QS, `postratesprod` → AP.

**Полезное следствие, пригодится при отладке.** Если отправить запрос с тем же `OrderNum`, что
уже использовался, Казпочта НЕ выдаёт новый номер: возвращает код `20012` и ранее выданный ШПИ.
Значит повторный запрос с известным номером заказа — бесплатный способ посмотреть, что этот
контур выдал в прошлый раз, не тратя номер из диапазона.

**И отсюда же риск, про который стоит помнить.** Номер заказа у нас — случайное семизначное
число (`genOrderCode`), а уникальность проверяется только среди заказов, загруженных в браузер.
Сразу после входа там лежат лишь сегодняшние. При 26 тысячах заказов в диапазоне 9 миллионов
совпадения статистически ожидаемы. Если два заказа получат один номер, второй не получит своего
ШПИ — Казпочта молча вернёт чужой, и у двух посылок будет один трек. Проверить:
`select code, count(*) from public.orders group by code having count(*) > 1;`

**Ночью треки не выдаются, днём выдаются — это НЕ про дату заказа.** Владелец заметил
закономерность и предположил, что Казпочта отказывает «старому» заказу (просим за 25-е,
а уже 26-е). Проверено по коду: **никакой даты в запросе нет вообще** — уходят получатель,
отправитель, вес, сумма, коды продукта и договора и `OrderNum`. Отличить «вчерашний» заказ
от сегодняшнего Казпочта не может. Закономерность сходится с другим: `ORA-01033` — это
оракловое «база запускается или останавливается», то есть их ночное обслуживание.

**Подтверждено на живом запросе** 26.09.2026 в 02:08: `ORA-01033: сейчас идет либо запуск,
либо останов ORACLE`, все три попытки подряд. Номер при этом НЕ тратится — ШПИ не выдан,
из диапазона договора ничего не уходит, повторять днём можно спокойно.

Перед большой партией бланков (раздел 5e) в часы до 07:00 система предупреждает об этом
отдельной строкой в подтверждении — но не запрещает: окно у них плавающее.

**Поэтому с 26.09.2026 запрос повторяется до трёх раз** (паузы 2 и 6 секунд) — на любые
`ORA-*`, HTTP 5xx и обрыв связи. Отказ по делу (неверный индекс, не тот договор) не
повторяется: ответ не изменится, а время уйдёт.

**Повтор с тем же `OrderNum` безопасен, и на этом всё держится:** если номер уже был выдан,
Казпочта не выдаёт новый, а возвращает прежний ШПИ с кодом 20012. Значит лишняя попытка не
может ни потратить номер из диапазона, ни развести один заказ на два трека. Если будете
менять эту логику — проверьте, что это свойство сохраняется.

Практическое следствие: **большую партию бланков (раздел 5e) ночью запускать не стоит** —
упрётесь в то же обслуживание, только на тысячах номеров.

Важные детали, если снова будете трогать эту интеграцию:

- `ProductCode=P103` («Посылка РК», стандарт) — рабочая, проверенная комбинация, даёт трек-номера с
  префиксом AP. Пробовали разные другие коды (P145 → EW, P109, P126A → не сработали вовсе) в
  попытке получить префикс QS — не вышло. Причина: диапазон QS выделяется Казпочтой заранее, вручную,
  под конкретный номер договора/ключ, и никак не подбирается через параметры запроса. Это
  подтвердилось и с чужой, отдельной системой — та же проблема с тем же ключом и договором. Ждём
  ответа от техподдержки Казпочты по этому вопросу.
- `MailCtg` выбирается автоматически по каждому заказу (не хардкодится в секретах) — если у заказа
  есть сумма к оплате (`order_sum`), используется категория 4 («с объявленной ценностью и наложенным
  платежом» — покрывает и страховку, и наложенный платёж одновременно) с реальной суммой в полях
  `DeclaredValue`/`CashOnDelivery`; если суммы нет — категория 3 («Обыкновенная»).
- `SndrCtg=2` (юрлицо) — добавили после того, как обнаружили это поле в ДРУГОЙ, отдельной панели
  (`admin.jyldam-logistics.kz`), где были более полные настройки.
- Все секреты (Key, DEA_NUMBER, БИН и т.д.) читаются с `.trim()` — раньше случайный пробел в конце
  значения секрета (например, `"P109 "`) приводил к непонятной внутренней ошибке базы Казпочты
  (ORA-06512) без внятного сообщения.

## 8. Прочие известные особенности и грабли

- **Вес заказа — всегда три знака после запятой.** Кладовщик списывает с весов и отбрасывает
  хвостовые нули: набирает «1,3» вместо «1,300», «0,97» вместо «0,970». Число от этого не
  меняется, но в списке рядом стоят «1,3», «0,97» и «2» — глазами не сравнить и не понять,
  записано ли до грамма. Везде показываем через **`fmtWeight(w)`** (js/01-yadro.js), читаем из
  полей через **`parseWeight(v)`**: он принимает и запятую, и точку и округляет до грамма.
  Поля ввода веса — `type="text"` с `inputmode="decimal"`, а НЕ `type="number"`: у числового
  поля запятая считается ошибкой ввода, значение молча становится пустым, и вес терялся.
  Формат не исправляет уже введённые неверные числа: 1,031 так и останется 1,031.

- **Сумма заказа: два поля, одно правило.** В базе исторически `order_sum` (то, что человек
  вводит в карточке) и `cost` (его копия). Сохранение давно пишет оба одинаково, но у старых
  заказов `order_sum` бывает пустым, а `cost` заполнен. Раньше это разъезжалось на экране:
  карточка и Калькуляция читали `order_sum`, а грид «Стоимость», плашка «Сумма доставки» и
  выгрузка Excel — `cost`; один заказ показывал разные числа, а в Калькуляцию заказы с пустым
  `order_sum` попадали с нулевой выручкой. Теперь везде **`orderSum(o)`** (js/01-yadro.js):
  берёт `order_sum`, а если он пуст — `cost`. **Новые места с деньгами по заказу делайте через
  него**, а не читайте поля напрямую.

- **«Сегодня» берётся по времени СЕРВЕРА, а не по часам компьютера.** 27.09.2026
  сотрудница видела пустую очередь «Заполнения» и ноль заполненных, пока у всех
  остальных было нормально: на её ноутбуке стояло 28 сентября. Заказы за 27-е
  переставали быть «сегодняшними», и разделы выглядели пустыми — по экрану понять это
  невозможно. Теперь при входе `syncServerTime()` спрашивает время у сервера
  **из токена сессии** и запоминает поправку, а `localToday()` считает от неё.

  Первая попытка читала заголовок `Date` ответа — и не работала молча: браузер не отдаёт
  его при запросе на другой домен (в списке видимых заголовков остаются только
  `content-length` и `content-type`). Поправка всегда выходила нулевой. Токен же выдаёт
  сам сервер и кладёт внутрь `iat` — момент выдачи по ЕГО часам.

  Берём `iat` свежеобновлённой сессии. Если обновить не удалось, старый токен принимаем
  только при расхождении больше шести часов: он мог пролежать почти час, и мелкую поправку
  из него считать нельзя, а вот разницу в сутки видно и так. Если ДАТА расходится, человеку показывается предупреждение с обеими датами.
  Не удалось спросить — работаем как раньше, по местным часам.

  **Новые места с «сейчас» делайте через `nowMs()`**, а не `Date.now()`: иначе они снова
  будут зависеть от часов конкретного ноутбука.

- **Даты и часовые пояса:** используется `localToday()` — специальная функция для получения ТЕКУЩЕЙ
  ЛОКАЛЬНОЙ даты, корректно работающая независимо от часового пояса браузера (компенсирует
  `getTimezoneOffset()`). НЕ использовать голый `new Date().toISOString().slice(0,10)` для
  «сегодня» — это UTC, может отличаться от локальной даты на несколько часов ближе к границе суток.
- **Загрузка фото пачкой** (в карточке заявки на забор) — сопоставляет фото «по порядку» только с
  заказами, у которых ещё нет ни одного фото (защита от случайной перезаписи). Если фото больше,
  чем пустых заказов — лишние остаются нераспределёнными (есть тост-уведомление об этом, но легко
  упустить из внимания). Для быстрого поиска, каким заказам не хватило фото — есть кнопка-фильтр
  «🔍 Без фото (N)» в той же карточке.
- **Кнопка «Сохранить»** в карточке заявки на забор продублирована наверху (рядом с «Загрузить фото
  пачкой» / «Создать ещё заказ»), чтобы не листать длинную ленту заказов до самого низа — нижняя
  (стандартная) кнопка скрыта через CSS, но обе вызывают одну и ту же логику сохранения/проверки.
- **Партнёры типа «Физ лицо Алматы/Астана»** — особый тип партнёра (проверка
  `isFizlicoName()`/`isFizlicoPartner()`, сравнение без учёта разных видов кавычек). Для таких
  партнёров в карточке заказа появляется отдельное поле «Адрес откуда забрали (физ. лицо)»
  (`fizlico_pickup_address`), которое специально НЕ выводится в общую таблицу заказов (только
  внутри карточки).
- **Новый норматив в «Калькуляции» — это ещё и колонка в базе.** Каждое поле из `CALC_FIELDS`
  сохраняется в ОДНОИМЁННУЮ колонку таблицы `calc_settings` (`saveCalcSettings` собирает строку
  по `data-calcnorm`). Добавили поле только в код — при сохранении вылетит
  «Could not find the 'X' column of 'calc_settings' in the schema cache», причём **не сохранится
  ничего**: ни новое поле, ни остальные значения, которые правили на этом экране. Ровно так
  вышло 20.09.2026 с `fund_smm` и `fund_other` — я заявил, что SQL не нужен, и ошибся.
  Добавляете поле — сразу добавляйте колонку (`db/7-ДОБАВИТЬ-расходы-в-калькуляцию.sql` как
  образец) и проверяйте сохранение, а не только отрисовку.

## 8c. «Заполнение» — поиск «кто заполнял заказ» (26.09.2026)

В шапке раздела стояла вторая кнопка «Взять следующий» — та же, что внизу страницы.
Дубль убран, на его месте поиск по номеру заказа, ФИО получателя, телефону и треку:
показывает, кто заказ заполнил и когда, а если ещё нет — кто держит его сейчас.

**Ищем ЗАПРОСОМ К БАЗЕ, а не по `S.orders`:** в памяти вкладки после входа лежат только
сегодняшние заказы, а спрашивают обычно про вчерашний. Условия собираются в `or(...)`.

**Условие по телефону добавляется, только если в запросе есть цифры** — пустая строка
после удаления нецифровых символов является подстрокой чего угодно, и поиск по имени
показывал бы всё подряд. Те же грабли уже были в «Сортировке», см. раздел 6.

**Пробел в поле поиска не забирает следующий заказ.** У раздела есть горячая клавиша
«Space» → «Взять следующий»; без `stopPropagation` на поле имя было бы не набрать.

**У старых заказов отметки «кто заполнил» нет и не будет.** `filled_at` проставляется
в момент, когда заказ ВПЕРВЫЕ становится обработанным, и только с тех пор, как появились
колонки (`db/11`). Всё, что заполнили раньше, отметки не получило — задним числом её взять
неоткуда. Владелец на это наткнулся сразу: заказ забит, а поиск пишет «никто».

Поэтому у заказов без отметки имя восстанавливается **из журнала изменений**: берём самую
раннюю запись, где ФИО получателя появилось из пустого, иначе первую правку вообще.
Показываем это отдельной подписью «по журналу правок» и не подменяем ею настоящую отметку:
журнал говорит, кто менял заказ, а не кто сидел и забивал его с бланка. Тот же источник
использует ежедневный отчёт (раздел 6d) — и по той же причине.

Заказ с данными, но без следов в журнале, показывается как «не записано · заполнен до того,
как появился учёт», а не «ждёт заполнения»: писать второе было бы прямым враньём.

**Переключатель периода есть и у менеджера, не только у админа.** Раньше «Сегодня /
Вчера / Неделя / Месяц» стояли только в админской таблице, и менеджер видел исключительно
сегодняшние цифры — посмотреть вчерашние было нечем. Подписи карточек меняются вместе с
периодом («Заполнено мной вчера»), иначе цифра за вчера подписывалась бы как сегодняшняя.

**Почему у сотрудника «0 заказов».** В таблицу «Менеджеры заказов» человек попадает по
двум причинам: он что-то заполнил за период ИЛИ у него прямо сейчас заказ взят или отложен.
Ноль при этом означает второе — работа висит, а завершённого за период нет. Отдельного
списка сотрудников там нет вовсе, строки строятся из самих заказов.

Чаще всего это **забытый отложенный заказ**: отложенный не протухает (в этом и смысл —
менеджер ждёт данных от партнёра), поэтому он может висеть третьи сутки, а со стороны
выглядит как «у сотрудника ноль». С 27.09.2026 в колонке «Сейчас» пишется, сколько он уже
висит, и старше `FILL_HOLD_STALE_H` (12 часов) подсвечивается красным.

Три состояния в выдаче и цвет строки: заполнен (зелёный, видно кто и за сколько секунд),
взят в работу или отложен (жёлтый, видно кем), ждёт заполнения (серый). Захват считается
живым те же `FILL_CLAIM_MIN` минут, что и в очереди, — иначе «держит» показывалось бы
у заказа, который давно вернулся в общий пул.

## 8p. «Помощник по данным»: заказы партнёров по дням (28.09.2026)

Помощник отказался отвечать на «сколько партнёров дают до 5 заказов в день» — и был прав:
в сводке (`aiBuildDataSummary`, `js/09-dashbord.js`) лежали только месячные суммы. 120
заказов за месяц — это и 4 в день у ежедневного партнёра, и 60 в день у того, кто отгрузил
дважды; из одной цифры второе не восстановить.

Добавлены два поля:

- **`Заказы_партнёров_в_день`** — по партнёру и месяцу: в скольких ДНЯХ он отгружал,
  всего, сколько в среднем за такой день, максимум за день. «В среднем» считается **по дням
  с заказами**, а не по всем календарным дням месяца — иначе партнёр, отгружающий раз в
  неделю, выглядел бы «мелким», хотя в свой день привозит полсотни.
- **`Партнёров_по_интенсивности`** — уже подсчитанное распределение по среднему за день.
  Вопрос «сколько партнёров дают до 5 в день» должен решаться просмотром строки, а не
  сложением двухсот чисел в уме: считать ИИ умеет плохо, и ошибку тут не заметить.

**Только последние три месяца.** Разбивка уходит в запрос к модели целиком, и вся история
по всем партнёрам раздула бы его на пустом месте.

Оба поля описаны в `Пояснение` — без этого модель их просто не использует. **Добавляете
новое поле в сводку — обязательно опишите его там же**, включая единицы и способ счёта.

## 8d. «Дашборд» переименован в «Статистику» (26.09.2026)

Ключ модуля остался прежним — `dashboard`. **Переименовывать его нельзя:** по нему хранятся
выданные права в `roles.perms`, и смена ключа отобрала бы доступ у всех ролей разом.
Изменились только подпись в меню и в «Ролях и правах» да иконка (`stats` — столбики
лесенкой со стрелкой вверх).

**Две большие таблицы — «Статистика по дням» и «Заборщики по дням» — сворачиваются и при
входе в раздел всегда свёрнуты.** Они длинные, и из-за них не было видно карточек наверху,
ради которых в раздел и заходят. Состояние живёт в `dashOpen` — в памяти вкладки, а не в
`localStorage`: раскрыли на время, ушли и вернулись — снова свёрнуто.

Сброс делает роутер `render()` по смене вкладки (`_lastTab`), а не сам раздел: внутри него
перерисовка случается от фильтра периода и от Realtime, и там сворачивать нельзя — таблица
закрывалась бы прямо под руками.

## 8t. Уникальность трека, номера заказа и внешнего номера (30.09.2026)

Три уникальных индекса — `db/20`. Ставить их можно только после того, как разобраны уже
существующие двойники: индекс на данных с повторами не создаётся, а падает и перечисляет их.
Блоки 1–3 в файле именно про это.

| Индекс | Что закрывает |
|---|---|
| `orders_track_uniq` | один трек на две посылки: статус и претензия достаются одной, вторая исчезает из отслеживания |
| `orders_code_uniq` | номер уходит в Казпочту как `OrderNum`; на повторный она НЕ выдаёт новый ШПИ, а возвращает прежний |
| `orders_partner_ext_uniq` | задвоение заказа от партнёра по API, в пределах одного партнёра |

**Индексы частичные** (`where … btrim(x) <> ''`): пустой трек не должен мешать другому
пустому, а у заказа без трека его и не должно быть.

**Внешний номер — уникален В ПРЕДЕЛАХ ПАРТНЁРА.** У двух разных партнёров номер «1001» —
это два разных заказа, глобальный запрет сломал бы приём.

**Защита по `external_id` в приёме по API уже была** — но это проверка В КОДЕ функции
(«пришёл тот же — вернуть существующий»). Между проверкой и вставкой есть зазор: два
одновременных запроса проходят проверку оба. Индекс закрывает зазор на уровне базы.

**Отказ базы переводится на русский** — `dbErrText` в `js/01-yadro.js`, карта
`DB_UNIQUE_MSG` по ИМЕНИ индекса. Postgres отвечает «duplicate key value violates unique
constraint "orders_track_uniq"», и по такому тексту человек не поймёт ни что случилось, ни
что делать. **Имена индексов в SQL и в карте должны совпадать** — переименуете в базе,
поправьте карту, иначе вернётся английский текст.

Перевод накрывает ВСЕ пути записи сразу: кабинет партнёра, загрузку из Excel, пул бланков,
приём по API. Отдельная понятная проверка стоит только в карточке заказа (запросом к базе,
не по `S.orders` — там после входа лежат лишь сегодняшние заказы), чтобы человек увидел
номер конфликтующего заказа ещё до сохранения.

## 8u. «Расчёт партнёра»: архив прогонов (30.09.2026)

Прогнали файл с весами — расчёт жил ровно до обновления страницы. Закрыл вкладку, и
свериться с партнёром нечем: ни сколько заказов было, ни по каким ставкам считали сумму,
которую ему выставили. Теперь каждый прогон сам ложится гридом под расчёт — таблица
`calc_partner_runs` (`db/21`).

**Сохраняется САМО, без кнопки.** Партнёр выбран и файл прочитан — значит расчёт состоялся,
и просить за него ещё нажатие незачем: забудут ровно в тот раз, когда понадобится.

**ОДНА строка на «партнёр + загруженный файл».** Поправили столбец с весом или надбавку за
кг — та же строка обновляется. Иначе в архиве осели бы промежуточные, заведомо неверные
попытки (автоопределение столбца ошибается — раздел про `calcPartnerParseFile`), и найти
среди них настоящий расчёт стало бы нельзя. Выбрали файл заново — это НОВЫЙ прогон, прошлый
остаётся как был: `_cpRunIds` и `_cpRunSig` сбрасываются в обработчике выбора файла.

**Отпечаток `_cpRunSig` — защита от повторов, а не украшение.** Сохранение вызывается из
перерисовки, а перерисовок много (Realtime, возврат во вкладку, смена периода). Без
отпечатка каждая писала бы ещё одну копию того же прогона. По той же причине грид рисует
ОТДЕЛЬНАЯ функция `calcPartnerRunsRender()` в свой `#cpRunsBox`: полная перерисовка из
сохранения закрутила бы круг «сохранил → нарисовал → сохранил».

**Хранится РАЗБИВКА ПО КГ, а не сами веса.** Для этой модели она полная: плата зависит
только от округлённого вверх веса, поэтому из разбивки восстанавливаются и итоги, и
выгрузка в Excel. Список из тысяч чисел хранить незачем.

**СТАВКИ — СНИМКОМ** (`base_price`, `base_margin`, `per_kg_margin`, `per_kg_charge`). Их
правят, и надбавка за доп. кг вообще общая на всех: без снимка прошлый прогон, пересчитанный
по карточке, дал бы сумму, отличную от той, что уже ушла партнёру. Та же причина, по которой
снимок берётся у `orders.sales_margin` (раздел 5b). В карточке прогона ставки видны и прямо
подписаны как «на момент расчёта».

**Внешнего ключа на партнёра НЕТ**, вместо него имя снимком. Партнёра из списка расчёта
удаляют кнопкой на том же экране: с `on delete cascade` вся история расчётов по нему исчезла
бы вместе с карточкой, а с `restrict` его нельзя было бы удалить вообще.

**В имени выгруженного файла стоит дата ПРОГОНА, а не сегодняшняя.** Августовский расчёт,
подписанный сегодняшним числом, потом ничего никому не докажет. Выгрузка при этом одна на
два места (`calcPartnerExcel`) — разойдись они, в счёте партнёру и в архивной копии стояли бы
разные столбцы.

**Удаление не воскресает.** При удалении строки ключ из `_cpRunIds` убирается, а отпечаток
НЕ сбрасывается: со сброшенным следующая же перерисовка сочла бы текущий прогон новым и
записала бы удалённое обратно. Удаление — по праву «Калькуляция → Удаление», кнопка иначе не
показывается; снимок строки ложится в корзину, потому что идёт через `dbDelete`.

**Список грузится раз за сеанс**, поэтому в шапке грида есть «🔄 Обновить»: расчёты прогоняют
и коллеги, и без кнопки их прогоны появлялись бы только после перезагрузки страницы.
Показываются последние `CALC_RUNS_LIMIT` (200) — архив растёт, а листают всегда свежее.

**Без `db/21` архива нет, а расчёт работает как раньше.** Таблицу спрашиваем напрямую через
`sb`, а не через `dbList`: тот на отсутствующую таблицу отвечает пустым массивом, и «таблицы
нет» было бы не отличить от «прогонов не было». Не загрузилось — на месте грида стоит
подсказка с именем файла SQL, а сохранение молча не делается (`calcPartnerRuns==null`).

## 8w. История заказа в карточке (02.10.2026)

Под «ИП для Почты» в карточке заказа — три строки: кто завёл заказ, кто его заполнил, кто
принял товар на складе, с датой и временем. Просьба владельца; данные видны и по октябрьским
заказам, задним числом.

**Две отметки из трёх лежат в самом заказе** — `filled_at`/`filled_by_name` (модуль
«Заполнение», db/11) и `sorted_at`/`sorted_by_name` («Сортировка»). Они и показываются как
есть.

**А «кто завёл» НИГДЕ НЕ ХРАНИТСЯ** — колонки такой нет. Поэтому строка догружается из
журнала действий после открытия карточки (`orderHistoryLoad`), и источников у неё три:

| Как создан | Откуда имя | Что в строке |
|---|---|---|
| вручную, карточкой | `activity_log`, `action='create'` с `entity_id` заказа | «Создан: кто · когда» |
| реестром из Excel | запись `action='import'`, СОПОСТАВЛЕННАЯ ПО ВРЕМЕНИ | «Загружен: кто · когда» + имя файла |
| пачкой из заявки | нигде | «Создан … по заявке на забор, пачкой» |

**Сопоставление по времени — это догадка, и она подписана.** Заказы из реестра создаются
пачкой, записи на каждый нет: журнал получает ОДНУ строку на весь файл, уже после вставки.
Поэтому берём запись об импорте в окне от минуты до `created_at` заказа и до пятнадцати
после (`OHIST_IMPORT_BEFORE_MS`/`OHIST_IMPORT_AFTER_MS`) — загрузка сотни заказов занимает
секунды, а в полчаса уже может уложиться соседний файл. В строке печатается имя файла, чтобы
догадку было видно глазами.

**У заказов из реестра в строке «Заполнен» имени нет, и это не потеря.** `filled_at` им
проставляется при создании — ФИО, адрес и телефон пришли готовыми, менеджеру там делать
нечего (раздел 5f). Пишем дату и «данные пришли готовыми в реестре», а не «—»: прочерк
намекал бы на потерянную отметку.

**Заполнение у старых заказов восстанавливается по журналу правок** — тем же правилом, что
в поиске «кто заполнял» (раздел 8c): самая ранняя запись, где ФИО получателя появилось из
пустого. И так же подписано «по журналу правок», потому что журнал говорит, кто менял заказ,
а не кто сидел и забивал его с бланка.

**Запросов максимум два, и только при открытии карточки.** Журнал большой, держать его в
памяти вкладки незачем. Пока ответ не пришёл, в строке стоит «ищем в журнале…», а не
прочерк — иначе на долю секунды показывалось бы «кто — не записано».

## 8v. «Расчёт партнёра»: пачка файлов (30.09.2026)

Реестры приходят за месяц пачкой, и по одному их прогонять — тридцать заходов в одну вкладку.
Поле файла стало `multiple`: выбрали сразу все — каждый посчитался строкой в сводке.

**Один файл — как раньше, несколько — пачкой.** Обработчик смотрит на число выбранных
файлов. Одиночный режим не тронут: там результат сразу и уходит в архив сам.

**Каждый файл считается ОТДЕЛЬНО, в одну сумму они не складываются.** У партнёров разные
ставки, и счёт выставляется по файлу: общая сумма по пачке показана только справкой в
карточках наверху и строкой «Итого».

**Партнёр угадывается по имени файла** (`calcPartnerBatchGuess`), как в загрузке заказов из
Excel: реестры называют по партнёру — «Казпочта 25.09.xls». Из совпавших берётся САМОЕ
ДЛИННОЕ название, иначе «Казпочта» перебивала бы «Казпочта Астана» и счёт ушёл бы по чужим
ставкам. Не угадался — берётся партнёр, выбранный сверху: тридцать файлов ОДНОГО партнёра
тогда разбираются одним выбором, ничего не тыкая по строкам. Поправить можно в самой строке.

**ПАЧКА В АРХИВ САМА НЕ УХОДИТ — и это не забывчивость.** В одиночном режиме партнёра выбрал
человек, поэтому сохранение автоматическое; в пачке его угадала программа по имени файла.
Тридцать записей с чужим партнёром пришлось бы разгребать руками, поэтому сначала таблица на
проверку, потом кнопка «Сохранить в архив (N)».

**Повторное нажатие дублей не делает.** У каждой строки свой `runId` и отпечаток `savedSig`;
кнопка считает только те файлы, которых в архиве нет ИЛИ которые изменились после сохранения
(поправили партнёра, столбец веса, надбавку). Изменённая строка ОБНОВЛЯЕТСЯ, а не добавляется
второй — тот же принцип, что в одиночном режиме.

**Пишем по одной записи, а не одним запросом на тридцать.** Групповой `insert` был бы быстрее,
но одна плохая строка отклонила бы все тридцать, и какая именно — из ответа не видно. Здесь
же виден прогресс («Сохраняю в архив: 7 из 30») и в конце сказано, сколько ушло и сколько не
удалось. Тридцать обращений — это секунды, а не тысяча запросов, из-за которых пачками пишут
межгород и обработчиков (раздел 5, 8n).

**Чтение файлов — по одному, с отдачей кадра браузеру** (`await new Promise(r=>setTimeout(r,0))`
между файлами). Без этого тридцать файлов читаются с наглухо замершим экраном, и это выглядит
как «повисло». Замер: 30 файлов по 500 строк — 157 мс на разбор, 1 мс на отрисовку, 33 МБ
памяти.

**Расчёт по всем файлам делается ОДИН раз на отрисовку** (`calcs` в `calcPartnerBatchHtml`).
Сначала он вызывался внутри каждой строки, и тридцать строк означали тридцать проходов по
весам всех файлов.

**Разбор весов — тот же код, что у одиночного файла**, включая автоопределение столбца и
предупреждение «средний вес N кг — похоже, не тот столбец». Столбец правится в самой строке;
файл, где весов не нашлось вовсе, даёт ошибку в своей строке и не мешает остальным.

**Сведение весов вынесено в `calcPartnerTotals(weights,partner)`** — одна функция на оба
режима. Разойдись они, в счёте партнёру и в сводке по пачке стояли бы разные числа по одному
файлу.

**Свод в Excel — строка на файл** («Файл, Партнёр, Заказов, К оплате, Наша прибыль,
Примечание» + Итого). Ради него пачку и делают: по нему выставляют счета, а не по тридцати
открытым по очереди карточкам.

**Мобильная правка заодно:** выпадающий список ВНУТРИ строки таблицы был 19 px с 13-м шрифтом —
правила раздела 8s ловят только `.field` и `.filters`. Добавлено
`.resp-table td select{font-size:16px;min-height:44px}`: иначе партнёр в строке и мимо пальца,
и с зумом от iOS при касании.

## 8яг. «Партнёры по городам» в Центре контроля (05.10.2026)

Грид: сколько заказов даёт каждый партнёр в каждом городе забора за выбранный месяц —
всего, в среднем в день, максимум за день, курьерских и почтовых. Просьба владельца.

**Месяц считается по дате ЗАБОРА, а при её отсутствии по дате создания** — ровно как в
Калькуляции (`ordersInOrderMonth`). Иначе два экрана про одни и те же заказы показывали бы
разные числа, и выяснять, какое верное, пришлось бы руками (это уже разбирали: раздел 5a,
вопрос «5685 против 5731»).

**«В среднем в день» делится на ДНИ С ЗАКАЗАМИ, а не на календарные дни месяца.** Партнёр,
который возит раз в неделю, иначе выглядел бы мелким, хотя в свой день привозит полсотни —
те же грабли, что в сводке для ИИ-помощника (раздел 8p).

**Город берётся у ЗАКАЗА (`pickup_city_id`), а при пустом — из карточки партнёра.** У
заказов, созданных пачкой из заявки, город часто не проставлен, и без запасного варианта
половина строк была бы «не указан».

**Барахолка по умолчанию НЕ считается** (`mainOrders`), но есть галочка «Считать Барахолку»:
это другая ветка, курьер туда не ездит, и в вопросе «сколько партнёр даёт заказов» её заказы
смешивать нельзя. Галочка нужна, чтобы при желании посмотреть общий объём, не выдумывая
второй экран.

**Число в колонке «Заказов» — ссылка**: открывает разбивку по дням для этой пары
«партнёр + город». Именно она отвечает на «сколько даёт ежедневно», а среднее в таблице —
только для сравнения партнёров между собой.

**Поиск перерисовывает ТОЛЬКО свою панель** (`nfVolRedraw`), а не весь раздел: полный
`render()` уводил бы фокус из поля на каждой букве. Фильтр месяца и галочка — наоборот,
полный `render()`: там фокус терять нечему.

**Нумерация строк сквозная, сверху вниз**, и это одновременно место партнёра по объёму:
сортировка идёт по числу заказов. Номер считается по ВИДИМОМУ списку, а не по партнёру —
сменили фильтр, и нумерация снова начинается с единицы. Тот же номер есть и в выгрузке в
Excel, иначе экран и файл нумеровались бы по-разному.

**Над фильтрами — сводка по тому, что сейчас видно:** партнёров, заказов, курьерских,
почтовых (и «без типа», если такие есть), плюс подпись «месяц · город». Меняется вместе с
фильтрами — ради неё фильтр города в основном и нужен: сразу видно объём города, не считая
строки глазами.

**Партнёров считаем ПО ИМЕНАМ, а не по строкам.** Один партнёр возит из двух городов и даёт
две строки — по строкам партнёров получилось бы больше, чем их есть. Проверено на данных,
где у партнёра два города: строк пять, партнёров четыре.

**Фильтр города забора** (`nfVolCity`) — список собирается ИЗ САМИХ ЗАКАЗОВ выбранного
месяца, а не из справочника: половина городов в заборах не участвует вовсе. Отдельный пункт
«— город не указан —» со значением `-`, потому что пустую строку в `<option value>` не
отличить от «все города», а такие строки спрашивают отдельно — по ним не видно, откуда возят.

**Строка «Итого» считается по ВИДИМЫМ строкам, а не по всему месяцу.** Выбрали город — в
итоге стоит этот город; иначе «Итого» спорило бы с таблицей прямо над ним.

**Показывается максимум `NF_VOL_LIMIT` (300) строк**, остальное — поиском или выгрузкой в
Excel: партнёров 468, а с разбивкой по городам строк кратно больше.

**Пока полная история не подъехала (`S._heavyLoaded`), вместо таблицы «Загружаем историю
заказов…»** — в памяти вкладки сразу после входа только сегодняшние заказы, и месяц
показался бы одним днём.

**Доступ — `isStaff()`.** «Центр контроля» виден и курьерам (право на заказы, карта `fb`),
а объёмы партнёров им ни к чему. Понадобится сузить до администратора — это одно слово.

## 8яд. «Заполнение»: фильтр по городу забора (08.10.2026)

Просьба владельца: «когда менеджер заказов выбирает город, ему падают только заказы
этого города». Полоса «Город забора» наверху раздела, `fillCity` в `js/16-zabivka.js`.

**Это фильтр ВЫДАЧИ, а не вида.** «Взять следующий», пробел и счётчик «свободно» берут
из одного и того же отфильтрованного набора (`fillFree`), поэтому полоса стоит отдельной
строкой наверху, а не прячется среди фильтров: от неё зависит, что человек получит по
кнопке.

**Свои взятые и отложенные заказы фильтр НЕ прячет** — `fillMine`/`fillHeld` считаются по
`fillQueueAll()`, то есть без города. Человек их уже держит; исчезни они с экрана при
смене города, он бы о них забыл, захват висел бы до конца срока, а заказ стоял.

**Чужие захваты в таблице «Менеджеры заказов» тоже без города** (`fillStatsRows`): кто у
кого в работе, от МОЕГО выбора города зависеть не должно.

**Город заказа берём `orderCalcCity()` из Калькуляции**, а не пишем вторую такую функцию:
своё поле `pickup_city_id`, а если пусто — город партнёра. У заказов, созданных пачкой из
заявки, поле бывает пустым, и правило «из какого города заказ» в системе должно быть одно.

**Варианты — из самой очереди, а не из справочника городов** (тот же приём, что в
«Партнёрах по городам» и в фильтре заборщиков «Сортировки»): в заборах участвует десяток
городов из сорока. В скобках — сколько там СВОБОДНЫХ заказов прямо сейчас: цифра отвечает
на вопрос «есть ли там для меня работа». Отдельный пункт «Город не указан» (значение `-`)
показывается, когда такие заказы есть, — иначе при выбранном городе они стали бы невидимы
для всех.

**Выбранный город НЕ сбрасывается, даже когда заказов в нём нет** — в отличие от фильтра
заборщиков в «Сортировке» (раздел 6). Там сброс спасал от пустой таблицы, а здесь сброс
означал бы, что человеку молча начнут падать заказы ЧУЖОГО города. Поэтому он остаётся в
списке с нулём, а экран прямо говорит, почему пусто: «по городу «Алматы» свободных нет ·
1 сейчас у коллег · в других городах свободно 2, снимите фильтр города». Без этой строки
менеджер сидит и ждёт заказов, которых ему и не дадут.

**Хранится в `localStorage`, а не в памяти вкладки:** по городу работают всю смену, и
выставлять его заново после каждой перезагрузки человек просто забудет. Выбор свой у
каждого устройства — у двух менеджеров на одном складе он разный.

**Город есть и в запросе свежих кандидатов** (`fillFreshCandidates`): двести свежайших
строк могли оказаться все чужого города, и выборка вернулась бы пустой при полном складе.
Условие там СТРОГОЕ, по полю заказа, без запасного варианта «город партнёра»: такой заказ
и так лежит в памяти вкладки, то есть достаётся первой попыткой в `fillTakeNext`.

**«Добрать за вчера (N)» тоже считает по городу** — кнопка обещает N заказов и обещать
должна то, что реально упадёт.

**По карточке сотрудника (`profiles.city_id`) фильтр НЕ подставляется.** У кладовщика это
поле ограничивает «Сортировку» (раздел 6), но менеджер заказов часто забивает за все
города сразу, и молча включённый фильтр выглядел бы как пропавшая работа. Выбор только
руками.

Проверено на подставных данных: все города — свободно 5, Астана — 3 (включая заказ без
города, но с партнёром из Астаны), Алматы — 1, «город не указан» — 1; свой алматинский
заказ виден в «У меня в работе» при выбранной Астане; выбранный город остаётся в списке
с нулём; на 375 px список 44 px со шрифтом 16, прокрутки вбок нет.

## 8q. Смена партнёра у списка заказов (30.09.2026)

**Живёт в «Центре контроля» и только у администратора.** Панель «🏷 Сменить партнёра у
списка заказов» → «Открыть». Вставляешь номера списком, выбираешь партнёра, видишь
таблицу «было → станет» и применяешь. Появилась по живой задаче: сорок заказов завели
под «Физ лицо Алматы», а на деле они партнёрские — руками это сорок открытых карточек.

**Сначала кнопка стояла в строке фильтров «Заказов заборов»** — то есть была доступна
любому с правом на редактирование заказов, включая курьеров. Владелец в тот же день
перенёс её в «Центр контроля»: инструмент правит партнёра сразу у десятков заказов, а
партнёр определяет и выручку, и раздел учёта.

**Проверка именно `isAdmin()`, а не сам раздел.** «Центр контроля» виден не только
администратору — доступ к нему привязан к праву на заказы (`notify:'orders'` в карте `fb`),
и оно есть у курьеров. Та же ловушка, что была с корзиной (раздел «Финансы, калькуляция
и корзина»): полагаться на видимость раздела нельзя.

Сама функция `setPartnerBulkModal` осталась в `js/11-zakazy.js`, а вызывается из
`renderNotify` (`js/03`). Порядок подключения этому не мешает: объявления функций
всплывают в своём файле, а вызов происходит из обработчика нажатия, когда загружены все.

**Ищем ЗАПРОСОМ К БАЗЕ по `code`**, а не по `S.orders`: в памяти вкладки после входа лежат
только сегодняшние заказы, а такие списки приносят за неделю. Номера дробим по 100 на
запрос — адрес запроса не резиновый. Повторы в списке отсеиваются, ненайденные номера
перечисляются отдельно.

**Менеджер и обработчик по умолчанию НЕ меняются** — галочка выключена. Они участвуют в
расчёте зарплат, и правка задним числом меняет уже посчитанные деньги за месяц (раздел 5a).
Нужно — включите галочку осознанно.

**Сумма заказа и `sales_margin` не пересчитываются никогда.** Они сняты по тарифу того
партнёра, при котором заказ создавался, и пересчёт задним числом сдвинул бы выручку
закрытого месяца. Если по этим заказам нужен тариф нового партнёра — это отдельная
осознанная правка, а не побочный эффект смены названия.

**Заказы, уже сидящие на этом партнёре, не трогаются**, и на кнопке стоит число, которое
реально изменится («Применить к 2 заказам из 3») — обещать все найденные было бы враньём.

Запись идёт пачками по 100 мимо `dbUpdate` (иначе сотня запросов подряд), а в журнал
попадает одна запись с числом заказов, а не сорок отдельных.

## 8ya. Свайп открывает боковое меню (02.10.2026)

На телефоне меню теперь открывается **движением пальца от левого края вправо**, а закрывается
**движением влево по открытому меню**. Кнопка-бургер работает как раньше.

**Почему именно от края.** Меню выезжает слева, поэтому «вытащить» его естественно вправо.
А главное — горизонтальная прокрутка: таблицы в CRM шире экрана почти в каждом разделе, и
свайп посреди экрана должен листать таблицу, а не выдёргивать меню. Жест принимается только
из полосы `EDGE` (32 px) у левого края, и дополнительно отменяется, если он начался внутри
элемента, который сам прокручивается вбок (`inScroller`).

Пороги: пройти не меньше `DIST` (60 px) по горизонтали и отклониться не больше `SLOP`
(45 px) по вертикали — иначе это обычная прокрутка страницы, а не свайп.

**Слушатели `passive:true`** и ничего не отменяют: жест только читается, прокрутка страницы
при этом не тормозит.

Проверено подставными касаниями на шести случаях: от края вправо — открывается; влево по
открытому — закрывается; из середины экрана, поверх широкой таблицы, вертикальное движение
и короткий тычок — не срабатывает.

## 8яб. «Непривязанные коды» — теперь можно чинить на месте (02.10.2026)

Код KET — единственное, что связывает позицию заказа с товаром на складе (`products.ket_sku`).
Пока код не привязан, заказ **нельзя собрать**: сборка берёт состав из позиций, а они не
знают, что списывать. Поэтому этот экран — узкое место всей связки SPA трафик ↔ Склад.

**Что было:** окно сначала выкачивало ВСЮ историю KET (36 тысяч заказов, 87 тысяч позиций),
потом показывало список кодов и подпись «заведите товар в Складе». Минуту ждёшь, потом
уходишь в другой раздел искать руками, возвращаешься.

**Что стало:**

| Было | Стало |
|---|---|
| полная загрузка истории | один запрос по непривязанным позициям, страницами по 1000 |
| только список кодов | в строке — поле товара и две кнопки |
| «заведите товар в Складе» | **«Привязать»** — добавляет код существующему товару |
| | **«Создать товар»** — заводит новый с этим названием и кодом |
| — | **«📋 Скопировать коды»** — список для письма в KET |

Привязка идёт через `matchInboundItemsForCodes`, то есть **по базе**: подхватываются и старые
заказы, а не только загруженные в эту вкладку (эти грабли описаны у самой функции).

**Позиции «товар выбран, а отметки нет»** считаются отдельным запросом и чинятся кнопкой
«Проставить отметку». Их не видно в списке кодов — привязывать там нечего, товар уже
известен, — но сборка считает такой заказ непривязанным и не даёт его собрать. Молчаливый
тупик: в списке пусто, а заказ не собирается.

**У позиции без кода KET кнопок нет вовсе** — привязывать не к чему, товар ищется именно по
коду. Строка остаётся видимой (заказ всё равно не собрать), но с подписью «вопрос к KET»:
нарисовать кнопку, которая не может сработать, — хуже, чем не рисовать.

**Названия товара в позициях KET нет** — только технический код. Поэтому имя вводит человек,
а не подставляется автоматически; для пачки кодов остаётся прежний путь «Склад → Импорт
тех.названий KET», где вставляют список `код;Название;Менеджер`.

## 8яв. Ракета в шапке (02.10.2026)

Владелец нарисовал её сам и попросил добавить справа в шапке, логотип оставив как есть.

**Нарисована в SVG прямо в `index.html`, а не картинкой:** резкая на любом экране, красится
цветами темы, не грузится отдельным запросом и не требует метки версии.

**Нос — не отдельная фигура, а часть корпуса.** Оранжевая часть нарисована прямоугольником
и обрезана по силуэту корпуса (`clipPath`), поэтому она не может вылезти за край и не даёт
шва. Первые попытки рисовать нос отдельным треугольником давали «рыбу»: нос жил своей жизнью
и не стыковался с корпусом.

**Крылья и пламя нарисованы ДО корпуса** — тогда их основания уходят под него и выглядят
приклеенными, а не наложенными сверху.

Движение — три анимации: лёгкое покачивание, мерцание следа и пульсация пламени. Под
`prefers-reduced-motion` всё останавливается, на телефоне ракета скрыта: в шапке там и так
тесно — бургер, логотип и имя.

## 8y. Копирование номера и правки «Сортировки» (02.10.2026)

**Кнопка «скопировать» рядом с номером заказа** — в гриде «Заказов заборов» и «Барахолки»
(под ID) и в карточке заказа у поля «ID заказа». Номер диктуют партнёру и ищут им в чужих
системах, а выделять его мышью в ячейке таблицы неудобно, на телефоне почти невозможно.

Разметку даёт `copyBtn(текст)`, копирует `copyText()` — обе в `js/01-yadro.js`.

**Слушатель ОДИН на всю страницу и в фазе ПЕРЕХВАТА** (`addEventListener(…, true)`). Кнопка
живёт внутри строки таблицы, у которой свой обработчик, и без остановки всплытия нажатие на
копирование заодно открывало бы карточку заказа. Вешать обработчик на каждую кнопку нельзя:
грид перерисовывается постоянно, их были бы сотни.

**Запасной путь обязателен.** `navigator.clipboard` есть не везде: без https и в старых
браузерах его просто нет, а обещание отклоняется. Тогда копируем через скрытое поле и
`execCommand('copy')` — он работает и там.

**«Печать бланков» в «Сортировке» сворачивается и при входе всегда свёрнута.** Это обычный
`<details>`, поэтому сворачивание работает без обработчиков. Состояние живёт в
`sortPrintOpen` — в памяти вкладки, и **сбрасывает его роутер по смене вкладки**, а не сам
раздел: внутри него перерисовка случается от фото и от Realtime, и там сворачивать нельзя —
панель закрывалась бы прямо под руками. Ровно та же механика, что у таблиц «Статистики»
(раздел 8d).

**Грабли при этой правке:** сброс нельзя ставить МЕЖДУ `if(S.tab==='dashboard'){…}` и
`else if(S.tab==='pickups')…` — это разрывает цепочку `if/else`, и у «Статистики» пропадает
вызов отрисовки. Строка стоит ДО цепочки.

**Фильтр типа доставки в списке «Сортировки»** — рядом с фильтром статуса
(`sortingListDelivery`). Курьерская развозится по городу, почтовая уходит в Казпочту: на
складе это разные стопки, и список удобно сузить до одной.

## 8x. Фильтры «Заказов заборов»: приёмка склада и порядок партнёров (02.10.2026)

**«Не принятые складом»** — новый пункт в фильтре «Заполненность». Показывает заказы с
пустым `sorted_at`, то есть те, по которым склад не отметил приёмку в «Сортировке».

Показываются ВСЕ такие заказы, включая ещё не обработанные (без ФИО и типа доставки).
Кладовщику их пока не предлагают — в «Сортировке» пул только из обработанных (раздел 6), —
но посылка физически не принята, и прятать её из списка «что склад не принял» нельзя.

**Партнёры в «Исключить партнёров» — по алфавиту.** Было «сначала у кого больше заказов»:
порядок менялся от выборки к выборке, и список каждый раз приходилось перечитывать заново, а
ищут там глазами по названию. Сортировка `localeCompare(…,'ru')`.

Остальные списки партнёров (поиск в фильтрах, «Отправитель» в карточке, «Наименование» в
заявке) уже алфавитные — `S.partners` грузится с `order:'name'`. Отдельно их не трогали.

## 8e. Удаление отмеченных заказов (27.09.2026)

Кнопка «Удалить выделенные» — в строке фильтров «Заказов заборов», рядом с «Исключить
партнёров». Такая кнопка была и раньше, но рисовалась в шапке и **только при непустом
выборе** — а галочки ставятся без перерисовки страницы, поэтому появлялась она лишь
случайно, после какого-нибудь другого обновления. Теперь она на месте всегда: без выбора
серая и неактивная, с галочками краснеет и показывает число.

Счётчик обновляет `updateDelSelBtn()` из `updateKetAllChk()` — то есть при каждом
изменении галочек. Без этого число на кнопке отставало бы от выбора.

**Галочка «выбрать все» кнопку не обновляла** (исправлено 28.09.2026). Отметки отдельных
строк доходят до кнопки через `updateKetAllChk` → `updateDelSelBtn`, а обработчик «выбрать
все» наполнял `ketSelected` и проставлял галочки в строках, но `updateDelSelBtn` не звал:
заказы отмечены, а кнопка серая и не нажимается. Кнопка живёт ВНЕ таблицы и о галочках
сама не знает — любой новый путь, меняющий `ketSelected` без перерисовки, обязан дёрнуть
`updateDelSelBtn()`.

Если кнопки нет совсем — это другое: она рисуется только при праве `orders.delete`
(«Роли и права» → «Удаление»).

**Удаляем только через `dbDelete`**, по одному. Он кладёт полный снимок строки в
`deleted_items`, и это единственная страховка: быстрый `delete ... in (...)` был бы
в разы шустрее, но восстанавливать после него нечего.

**Предупреждаем про межгород.** Если среди отмеченных есть заказы из уже созданных
отправок, в подтверждении названо их число: в коробке останется id удалённого заказа,
и стоимость продолжит делиться с его учётом. Не запрещаем — бывает, что удалить нужно
именно такой, — но коробку после этого надо пересобрать.

## 8f. «Заполнение»: почему один заказ доставался двоим (27.09.2026)

Заполняльщики жаловались, что к ним падают одни и те же заказы. Причина оказалась простой
и проверяемой: **захват живёт `FILL_CLAIM_MIN` (10 минут) от нажатия «Взять следующий» и
раньше никак не продлевался.** Норма — минута, но на деле заказ занимает больше: разобрать
почерк на фото, уточнить адрес, позвонить партнёру. На одиннадцатой минуте заказ тихо
возвращался в общую очередь, и тот же самый доставался соседу.

Проверено на живых данных: заказ, взятый 11 минут назад, снова попадал в `fillFree()` —
и чужой, и свой собственный.

**Теперь захват продлевает работа в карточке.** Любое изменение поля вызывает
`fillTouchClaim()`, но не чаще раза в `FILL_TOUCH_MIN` (3 минуты) — на каждую букву
запросов не нужно. Ушёл и не трогает — захват истекает как раньше, и заказ честно
возвращается в очередь: это по-прежнему защита от «взял и забыл».

Продление идёт мимо `dbUpdate`, прямым запросом: это служебная отметка, и в журнале
изменений ей делать нечего — иначе история заказа утонет в записях «продлили захват».

**Заодно отложенный заказ защищён и на стороне базы.** В условие захвата добавлено
`not claim_hold is true` (только когда колонка есть). Локальный список отложенные и так
не предлагал, но он мог устареть: сосед отложил заказ секунду назад, а в памяти вкладки
он ещё «просроченный».

## 8r. «Заполнение»: три починки по жалобам менеджеров (30.09.2026)

**1. «Обновить» у менеджера не работала.** Кнопка рисуется ДВАЖДЫ — в строке периода и
рядом со «Взять следующий», — а id у неё был один. Браузер по id отдаёт только первую,
и нижняя была мёртвой. У администратора она одна, поэтому у него всё работало, и жалоба
звучала загадочно. Теперь у кнопки КЛАСС `fill-reload`, обработчик вешается на все, и
`fillRefresh` блокирует их тоже все. **Рисуете элемент в двух местах — не давайте ему id.**

**2. Захват — 30 минут вместо 10** (`FILL_CLAIM_MIN`). Десяти не хватало: разобрать
почерк на фото, уточнить адрес, дозвониться партнёру.

**Предел ИЗМЕРЕНИЯ времени при этом оставлен прежним — 10 минут**
(`FILL_MEASURE_MAX_MIN`), и это не описка. Раньше это было одно число, и подъём захвата
молча испортил бы «среднее время»: заказ, который делали 25 минут, попал бы в среднее при
норме 60 секунд и утянул бы его в разы. Дольше десяти минут — это не работа, а пауза.

**3. «Свободные заказы разобрали» при 97 свободных на экране.** Настоящая причина —
устаревшая память вкладки: заказы разбирают и заполняют пятеро одновременно, Realtime
может часть изменений не донести (вкладка в фоне, сеть мигнула), и в списке висят заказы,
давно заполненные. Все 20 попыток захвата возвращали ноль строк, и человек видел
«свободных: 97» и тост «разобрали».

Теперь при неудаче система **спрашивает базу заново** (`fillFreshCandidates`) и пробует
её кандидатов, а не отправляет человека «попробовать ещё раз». Заодно освежает `S.orders`,
чтобы счётчики на экране перестали врать. Проверено на подставных данных: две устаревшие
записи не захватились, один запрос к базе, захвачен заказ, о котором вкладка вообще
не знала.

**Кандидаты перемешиваются внутри старейших сорока** (`fillCandidateOrder`). Строгий
«самый старый первым» означает, что все менеджеры дерутся за ОДИН И ТОТ ЖЕ заказ, а
остальные девяносто ждут. Очередь при этом соблюдается — перемешивание только внутри головы
списка.

**4. Часы берём серверные (`nowMs`), а не ноутбука.** `fillCutoff` и запись `claimed_at`
считали по `Date.now()`. Менеджер с часами, убежавшими вперёд, считает ЧУЖИЕ свежие
захваты просроченными и отбирает заказы, над которыми уже работают — это ещё одно
объяснение жалобы «падают одни и те же заказы» от 27.09, помимо короткого захвата.
А его собственный `claimed_at`, записанный вперёд, для остальных не истекает никогда.

## 8j. «Заполнение»: очередь идёт по выбранному периоду (28.09.2026)

В полночь незаполненные заказы вчерашнего дня молча уходили из очереди: выдавались
строго сегодняшние (`fillIsToday`), и «Взять следующий» отвечал «свободных заказов нет»,
хотя работа осталась. Фильтр периода на очередь не влиял вовсе — по нему считалась
только статистика, поэтому нажатие «Вчера» выглядело как «ничего не происходит».
Ровно на это и наткнулись 28.09 в 00:03.

**Теперь период задаёт и очередь** (`fillQueueFrom` + `fillInQueue`): «Вчера» — это
вчера И сегодня, «Неделя» — неделя по сегодня.

**Верхняя граница всегда сегодняшний день, даже когда в фильтре стоит «по вчера».**
Иначе выбранный вечером «Вчера» прятал бы новые заказы, и человек весь день не видел бы
свежей работы — ошибка тише прежней и заметна только к концу смены.

**Кнопка «Добрать за 27.09 (N)»** рядом со «Взять следующий» сдвигает окно на день назад
и подсвечивает «Вчера»: искать нужную вкладку в полночь не приходится. Считается ровно
ОДИН день перед окном (`fillTailCount`), а не всё прошлое: «добрать 400 за месяц» — это
не про работу, а про старые брошенные болванки. Окно очереди подписано и на плашке
«Ждут заполнения», и в строке выдачи («свободных заказов: 12 · с 27.09»).

**Старое ограничение снимать было безопасно** вопреки комментарию, который там стоял
(«вчерашние болванки — это то, что партнёр заявил, но не отдал»): `fillNeedsWork`
требует наличия ФОТО бланка, а у незаявленного заказа фото и не появится.

**«Раздел ещё не включён» в первые секунды — больше нет.** Экран определяет наличие
колонок по первой строке `S.orders`, а пока заказы грузятся, строк нет вообще, и раздел
пугал требованием выполнить SQL — при том что всё давно включено. Теперь, пока история
не подъехала (`S._heavyLoaded`), честно пишем «Загружаем заказы…». Особенно заметно было
сразу после полуночи: быстрый запрос «за сегодня» возвращает ноль строк, и до прихода
полной истории раздел выглядел сломанным.

**Экран говорит, ПОЧЕМУ брать нечего** (`fillWhyEmpty`). Кнопка «Взять следующий» гаснет
по пяти разным причинам — заказ уже у вас, отложен вами, все у коллег, за день нет заказов
с фото, окно очереди не тот день, — а со стороны это всегда выглядит как «кнопка не
работает». Теперь причина написана рядом.

**Данные за прошлые дни дотягиваются сами** (`fillEnsureLoaded`): сразу после входа в
памяти только сегодняшние заказы, вся история подъезжает следом. Сдвинули фильтр —
недостающее грузится; если полная история уже пришла, запрос не делается вовсе.
`fillRefresh` теперь тянет СТРАНИЦАМИ по 1000: за день столько не набирается, а за
месяц — запросто, и список оборвался бы молча, без ошибки.

## 8h. Карточка заказа: убраны три поля (28.09.2026)

По просьбе владельца из карточки убраны **«Комментарий»** и **«Город (почтовая)»**, а
**«Курьер по заказам»** теперь показывается только при курьерской доставке (получил класс

**Следствие, о котором владелец предупреждён:** `city_id` у новых почтовых заказов теперь

## 8s. Мобильная версия: размеры под палец и зум iOS (30.09.2026)

Жалоба владельца была общей — «много где неудобно смотреть и пользоваться». Замер на
375 px показал, что это не отдельные поломки, а размеры во всём:

| Элемент | Было | Стало |
|---|---|---|
| поиск в фильтрах | 33 px / 13 px | 44 / 16 |
| селекты и даты | 35 / 13 | 44 / 16 |
| кнопки фильтров | 35 | 44 |
| кнопки пагинации | **28** / 12 | 44 / 14 |
| кнопки в строке заказа | 31 | 44 |
| поля в карточке | 39 / 14 | 44 / 16 |
| крестик закрытия карточки | 30 | 44 |
| галочка выбора | **13** | 26 (см. ниже) |

**Шрифт 16 px в полях — не «крупнее для красоты».** Safari на iPhone ЗУМИТ страницу при
касании поля со шрифтом меньше 16 px: человек тапает в поиск, вёрстка прыгает, и её надо
отщипывать назад. Это и была главная причина «неудобно пользоваться».

**Норма 44 px** — размер подушечки пальца, ниже него промахи неизбежны. Ставим `min-height`,
а не `height`: адрес или длинное название должны свободно растягивать элемент.

**Условие блока двойное — `(max-width:760px), (pointer:coarse)`.** Второе ловит планшеты и
ноутбуки с тачскрином: ширина большая, а палец тот же. Блок стоит ПОСЛЕДНИМ в файле и этим
перекрывает прежние значения — при правках выше он останется главным, это намеренно.

**Что ещё исправлено тем же заходом:**

- **Пагинация была столбиком** — три этажа кнопок, 110 px экрана и 150 px отступа под ними.
  Вернули в строку: кнопки крупнее, а места занимает меньше.
- **Карточка-модалка**: отступ вокруг 20 → 10 px (на 375 это была десятая часть ширины),
  `90vh` → `92dvh`, а кнопки внизу стали ПРИЛИПШИМИ. До этого в длинной карточке до
  «Сохранить» надо было пролистать весь экран полей, и люди закрывали окно, не сохранив.
- **`100vh` у выдвижного меню → `100dvh`**: в мобильном Safari `vh` считается вместе с
  адресной строкой, и нижние пункты меню уходили под край экрана.
- **Подпись в карточке-строке** занимала 42 % ширины — отдали содержимому, стало 36 %.
- **Сломанное правило в CSS**: у фильтров таблицы «Сотрудники» был потерян селектор,
  декларации висели после закрывающей скобки, и браузер молча выбрасывал оформление полей.

**Осталось сознательно:** галочка выбора 26 px, а не 44. Растянуть хит-зону самого
чекбокса одним CSS нельзя, а переделывать разметку во всех модулях ради шести пикселей
не стоит; ячейка вокруг неё теперь не ниже 44, так что промах по вертикали ловится.

**Проверка:** на 375 px ни одного элемента управления меньше 44 px, ни одного поля со
шрифтом меньше 16, горизонтальной прокрутки нет, за край не вылезает ничего. Десктоп
не изменился — те же 35/29/13, замерено отдельно.

**Детектор вёрстки** (`impeccable detect`) даёт 51 предупреждение «overused-font» на
Fraunces и одно на `transition:width` у боковой панели. Оба оставлены: шрифт — это
сложившийся облик CRM, менять его — не мобильная правка, а смена фирменного стиля;
анимация ширины нужна для схлопывания панели на компьютере, и заменить её на `transform`
без переделки раскладки нельзя.

## 8b. «Роли и права» — матрица квадратами (26.09.2026)

## 8o. Карточка «Физ лицо» не сохранялась (28.09.2026)

У партнёров **«Физ лицо Алматы»** и **«Физ лицо Астана»** адрес, район и телефон — не их
собственные, а того клиента, у которого забрали конкретную посылку (для этого в карточке
заказа есть отдельное поле «Адрес откуда забрали», `fizlico_pickup_address`). В карточке
партнёра держать их нечем: она одна на всех.

А форма требовала их заполнить, и карточка вообще не сохранялась. Следствие оказалось
дороже неудобства: у этих двух партнёров **нельзя было задать обработчика** — форма
упиралась в поля, которых у них не бывает, — и все их заказы уходили без него
(см. 8n). Владелец просил «поставить Ырысалды автоматом», а поставить было нельзя.

Теперь для них (`isFizlicoName`) район, адрес и телефон необязательны: звёздочка у поля
не показывается, под ним подсказка, проверка пропускается. Для всех остальных партнёров
всё как было.

**Имя берётся из ПОЛЯ, а не из сохранённой карточки:** партнёра могли только что
переименовать в физ. лицо или обратно, и проверять надо то, что сохраняется.

Телефон снят вместе с адресом сознательно: у «физ лица» он тоже свой в каждом заказе, а в
карточке партнёра используется только для показа в кабинете партнёра — там пустое значение
уже обрабатывается как «—».

**Обработчик для них задаётся, как у всех, — в карточке партнёра.** В коде имя сотрудника
не зашито и не должно быть: человек уходит в отпуск или увольняется, а карточка меняется
за пять секунд и без выкладки.

## 8n. «Заказов у обработчиков меньше, чем всего» (28.09.2026)

Вопрос владельца: в сводке у обработчиков 14 117 заказов, а за месяц их 14 478. Разница —
заказы, у которых `processor_id` не заполнен вовсе: таблицы считают ТОЛЬКО заказы с
указанным человеком (`if(!o.processor_id)return`), и 361 заказ просто не попадал никуда.

Это не ошибка счёта, а дыра в данных, и она стоит денег: **по таким заказам ставка за
заказ не начисляется никому**. У менеджеров по продажам то же самое — по заказам без
`sales_id` надбавка остаётся прибылью компании.

Поле подставляется из карточки партнёра В МОМЕНТ СОЗДАНИЯ заказа (`js/11-zakazy.js`,
создание пачки из заявки). Пусто оно бывает, когда у партнёра поле не заполнено, когда
заявка не привязана к партнёру (`partner_id` тогда `null`) или когда заказ пришёл из
Excel-реестра с неопознанным партнёром.

**Что теперь видно.** В обеих таблицах сводки добавлена строка «не указан» и строка
«Всего заказов за месяц» — арифметика сходится на экране, а не в уме. Число в строке
«не указан» — ссылка: открывает список таких заказов, сгруппированный ПО ОТПРАВИТЕЛЮ.
Группировка тут важнее перечня: триста строк ни о чём не говорят, а десяток партнёров
сразу показывает, у кого в карточке не заполнено поле.

**Проставить можно прямо из списка.** В окне есть кнопка «Проставить обработчика по
карточкам партнёров (N)» и кнопка в каждой строке. Значение берётся из карточки партнёра,
а сам партнёр — полем заказа, а если пусто, по названию отправителя
(`findPartnerByNameLoose`, как в `salesMarginFor`): у заказов из заявки `partner_id` часто
не заполнен, и по нему одному половина групп осталась бы «партнёром не найден».

В строке сразу видно, чего не хватает: «в карточке не задан» (партнёр найден, поле пустое —
заполните карточку) или «партнёр не найден» (название отправителя ни с кем не совпало).

**Запись идёт пачками по 100 мимо `dbUpdate`** — он делает по два обращения на заказ плюс
запись в журнал на каждое, и на трёхстах заказах это больше тысячи запросов подряд, кнопка
выглядит мёртвой. Те же грабли уже были в разборе межгорода (раздел 5).

**Другого способа проставить обработчика в интерфейсе НЕТ.** В карточке заказа поля
«Обработчик» не существует — осталась только ссылка `$('o_proc')` в
`js/11-zakazy.js`, защищённая проверкой на существование. Второй путь — карточка партнёра:
при смене обработчика/менеджера там обновляются все существующие заказы этого партнёра
(`update ... eq('partner_id', id)` в `js/12-spravochniki.js`), но только те, у кого
`partner_id` заполнен.

## 8m. Тип курьера и роли для не-админа (28.09.2026)

**Тип курьера** (`profiles.courier_kind`: `pickup` — заборщик, `order` — по заказам) живёт
в карточке сотрудника, а НЕ в роли. По нему справочник курьеров решает, куда предлагать
аккаунт для привязки. Роль же названа человеком, и её название — единственное, что связывает
одно с другим. Отсюда `courierKindByRole()`: в названии есть «заборщ» — значит `pickup`.

**Почему заборщик получался «по заказам».** Три места сговорились:
1. в форме создания тип не зависел от выбранной роли — просто первый вариант списка;
2. карточку создаёт Edge Function `create-user`, и поле `courier_kind` она может не
   записывать: в базе остаётся `null`;
3. пустой тип В КАРТОЧКЕ показывался как «Курьер по заказам» — и первое же сохранение
   записывало заборщику чужой тип, после чего он пропадал из своего справочника.

Теперь тип подставляется по названию роли, после создания проверяется и при нужде
дописывается запросом из браузера (`dbUpdate` по найденной карточке), а пустое значение
в карточке больше не показывается как «по заказам».

**Не-админ заводит только заборщиков.** Раньше ему предлагались ВСЕ курьерские роли,
включая «Курьер по заказам». Теперь список — только роли с «заборщ» в названии, а поле
«Тип курьера» ему не показывается вовсе: нечего выбирать — нечего и перепутать. Если такой
роли нет, создание не открывается и прямо говорит, чего не хватает.

**Название роли тут значимо.** Переименуют «Курьер Заборщик» во что-то без «заборщ» —
у не-админа пропадёт возможность создавать, а тип начнёт подставляться как «по заказам».
Это осознанный размен: отдельного признака у ролей нет, а заводить колонку ради двух
значений — лишняя связь через всю систему.

## 8l. Вход без карточки сотрудника давал полные права (28.09.2026)

Найдено при разборе «осиротевших» логинов. `loadMe` читает карточку из `profiles`, а если
строки нет — подставлял запасную `{role:'manager'}`. Это `defaultPerms('staff')`, то есть
**полный доступ к заявкам и заказам, включая удаление**, плюс чтение справочников.

То есть сотрудник, которому удалили карточку, но не удалили учётную запись входа,
продолжал входить и работать как ни в чём не бывало. По выгрузке 28.09.2026 таких записей
было одиннадцать, и одна из них **входила 21.09** — за неделю до проверки.

Теперь при ЯВНОМ отсутствии строки (`PGRST116` — «нет строк») ставится `S.meMissing`,
сессия закрывается и показывается отказ. Проверка стоит в обоих местах: при входе по
паролю и при восстановлении сессии — карточку могли удалить, пока человек сидел со старым
токеном.

**Прочие ошибки чтения под это НЕ попадают** — только «нет строк». Сбой сети или правил
доступа заперли бы снаружи всю компанию разом, а это хуже, чем лишний вход одного
уволенного. Разница видна по коду ошибки, гадать не нужно.

Проверено на трёх случаях: карточка есть — вход; карточки нет — отказ и выход из сессии;
сбой чтения — вход как раньше.

## 8k. «Номер уже занят» при создании сотрудника (28.09.2026)

Логин сотрудника — это телефон, превращённый в адрес `<10 цифр>@jyldam.local`. На повтор
Auth отвечал по-английски прямо в тост: «A user with this email address has already been
registered». Из этого не понять ни чей это номер, ни что делать.

Случая два, и лечатся они по-разному:

| Что случилось | Как видно | Что делать |
|---|---|---|
| Номер у живого сотрудника | он есть в списке «Сотрудники» | найти его, второго с тем же номером не завести |
| Осталась только учётная запись входа | в списке НЕТ, а номер занят | удалить её: Supabase → Authentication → Users → `<номер>@jyldam.local` → Delete |

Второй случай и есть самый злой: снаружи номер выглядит свободным. Остаётся он от
неполного удаления или от **оборвавшегося создания** — запись входа заводится ПЕРВОЙ,
и если карточка после неё не создалась (например, у создающего нет прав на запись в
`profiles`), номер занят, а сотрудника нет.

Поэтому проверка на дубль идёт ТЕПЕРЬ ДО вызова функции (`staffWithPhone`): иначе каждая
попытка оставляла бы за собой ещё одну занятую запись входа. Сравниваем по последним
10 цифрам и телефона, и адреса — телефон у старых карточек записан по-разному.

**Удаление сотрудника и так удаляет учётную запись входа** — `delStaff` зовёт Edge
Function `delete-user` (все четыре функции — `create-user`, `delete-user`, `update-user`,
`set-password` — развёрнуты, в репозитории их исходников нет, они заведены в панели
Supabase). Дыра была в запасном пути: при ошибке спрашивалось «всё равно удалить
карточку?», и согласие оставляло ровно такого «сироту». Теперь карточка в этом случае
НЕ удаляется: лишняя живая карточка — меньшее зло, чем занятый невидимый номер.
Исключение — ответ «не найдено»: записи входа и не было, удалять нечего, карточка
убирается молча.

**Поиск по сотрудникам ищет и цифрами.** Телефон в строке поиска отформатирован
(«+7 (707) 962-80-21»), и набранное подряд «7079628021» его не находило: человек в списке
есть, а поиск отвечает «ничего не найдено» — и выглядит это как «номер свободен, а завести
нельзя». Теперь к текстовому поиску добавлено сравнение по одним цифрам телефона И адреса,
от четырёх знаков.

**В колонке «Логин» больше нет прочерка у тех, у кого пустое поле «Телефон».** Логин-адрес
`<10 цифр>@jyldam.local` — это и есть номер, по которому человек входит; раньше он не
показывался вовсе, и сотрудника нельзя было найти ни глазами, ни поиском.

**Найти уже накопившихся сирот** (в SQL-редакторе Supabase):

```sql
select u.id, u.email, u.created_at
from auth.users u left join public.profiles p on p.id = u.id
where p.id is null order by u.created_at desc;
```

Текст ошибки разбирает `staffPhoneTaken`, а сообщение собирает `staffTakenMessage`:
администратору — с точным путём в Supabase, остальным — «передайте администратору».
То же сообщение показывается при смене телефона в карточке.

## 8i. Меню строки в «Сотрудниках» обрезалось (28.09.2026)

«Сменить пароль» и «Удалить сотрудника» лежат в меню `⋯` внутри строки, а меню было
`position:absolute` внутри `.table-scroll`. У того стоит `overflow-x:auto` — и по правилам
CSS это делает прокручиваемой и ВЕРТИКАЛЬ тоже. Поэтому у последней строки меню просто
срезалось нижним краем таблицы: видна была белая полоска, нажать пункт нельзя.

Заметно только когда строк мало — например список отфильтрован до одного человека. При
полном списке под строкой есть другие, и меню умещается. Так и не замечали полутора недель.

Теперь меню открывается **поверх страницы** (`position:fixed`, координаты от кнопки —
`placeStaffMenu`): вниз, а если внизу не помещается — вверх от кнопки; по горизонтали
прижимается к краю экрана, чтобы не уезжало на телефоне. Закрывается щелчком мимо,
прокруткой и сменой размера окна — фиксированное меню иначе осталось бы висеть на
прежнем месте экрана. Слушатели вешаются ОДИН раз (`bindStaffMenuClose`): `renderStaff`
вызывается на каждую букву в поиске, и они бы копились.

**Та же ловушка ждёт любое выпадающее меню внутри таблицы.** `.table-scroll` есть почти
у каждой; `overflow:hidden`/`auto` у предка обрежет что угодно абсолютное. Делаете
выпадающий список в строке — сразу `fixed` с координатами от кнопки.

## 8g. «Unauthorized» от Edge-функций (27.09.2026)

Функции проверяют вход по токену сессии, а он живёт около часа. У вкладки, открытой со
вчера или пережившей сон ноутбука, обновление могло не случиться — и на кнопку «Получить
трек» прилетало сухое «Unauthorized», из которого человеку ничего не понятно.

Все вызовы функций от имени сотрудника идут теперь через **`callEdge(name, payload)`**
(`js/01-yadro.js`): при ответе 401 он один раз обновляет сессию и повторяет запрос, а если
и это не помогло — возвращает «Сессия истекла — обновите страницу и войдите заново».

Через него проходят `kazpost-get-barcode` (по одному и пачкой), `set-password`,
`update-user`, `kelesu-sync-history`. **Новые вызовы функций делайте через него**, а не
копированием `fetch` с заголовком: иначе снова получите «Unauthorized» без объяснения.

**Сообщение больше не подменяет настоящую причину.** Сначала я свёл любой 401 к «сессия
истекла» — и получил ровно то, чего добивался избежать: человек обновляет страницу, видит
тот же текст и не знает, что делать. Теперь в сообщении стоит ответ сервера как есть:
«Доступ не принят (401): …». По нему сразу видно, чей это отказ — наш (`Unauthorized: …`)
или платформы (`Invalid JWT`, `Missing authorization header`).

**Токен проверяется ПРЯМЫМ запросом к `/auth/v1/user`, а не через `supabase.auth.getUser(jwt)`.**
Через библиотеку получили «Auth session missing!»: переданный токен она проигнорировала и
пошла искать сохранённую сессию, которой в Edge-функции нет и быть не может. Прямой запрос
от поведения библиотеки не зависит, и в отказ попадает настоящая причина от Auth
(«invalid claim: missing sub claim», код 401), а не наша догадка.

**Вход в `kazpost-get-barcode` проверяется СЕРВИСНЫМ ключом, а не анонимным.** Раньше
создавался клиент на `SUPABASE_ANON_KEY` и вызывался `getUser()` без аргументов. Ключ этот
подставляет платформа, мы им не управляем: стоит Supabase его переименовать или перестать
подставлять — клиент соберётся с пустым ключом, и функция начнёт отвечать «Unauthorized»
всем подряд, хотя в коде ничего не менялось. Сервисный ключ задаём мы сами (он и так нужен
для записи), а `getUser(jwt)` с ним проверяет токен ровно так же.

Текст отказа теперь называет причину: «Unauthorized: JWT expired» против «Unauthorized:
запрос пришёл без токена входа» — раньше оба случая выглядели одинаково.

Если проблема осталась и после этого — проверьте «Verify JWT» у функции и что секрет
`SERVICE_ROLE_KEY` на месте.

## 9. Что делать, если что-то не работает после деплоя

1. Проверить консоль браузера (веб-инспектор → Консоль) на ошибки JS.
2. Если ошибка вида `Cannot access 'X' before initialization` — значит, какая-то
   переменная/константа используется РАНЬШЕ своего объявления в файле (JS temporal dead zone) —
   искать, где объявлена константа, и либо переместить объявление выше, либо не ссылаться на неё в
   коде, который выполняется немедленно при загрузке (вне функций).
3. Если что-то визуально не отображается, а в HTML (через инспектор → Copy outerHTML) видно, что
   данные там есть — значит, дело в CSS, не в генерации разметки. Проверить `getComputedStyle()`
   конкретного элемента через консоль (`display`, `visibility`, `opacity`) — вероятно, что-то
   пересекается с общим правилом для другой таблицы (см. про `.resp-table` и класс `open` выше).
4. Если действие (сохранение/удаление) как будто срабатывает, но результат не сохраняется после
   обновления страницы — проверить RLS-политики в Supabase для соответствующей таблицы
   (`select * from pg_policies where tablename='...'`) — возможно, отсутствует политика на нужную
   операцию.

## 10. Практические детали работы с репозиторием

Обнаружено при работе, в исходный документ не входило:

- `index.html` в репозитории хранится с **CRLF** переводами строк, а копия, скачанная с GitHub,
  приходит с LF. Если скопировать скачанный файл поверх репозиторного, git покажет изменение

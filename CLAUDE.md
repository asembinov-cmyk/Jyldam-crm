# Jyldam Logistics CRM — контекст проекта для разработки

Сводка всего, что нужно знать о проекте, прежде чем вносить изменения в код. Написана после
длительной сессии разработки — чтобы новый исполнитель (человек или ИИ) не наступал на те же
грабли повторно.

## 1. О компании и бизнесе

**Jyldam Logistics** — курьерская и логистическая компания, работает по Казахстану (в первую
очередь Астана и Алматы, плюс региональные города).

Компания тесно связана / фактически является частью **ТОО «QP Service»** — эта же организация
оказывает услуги фулфилмента для продавцов маркетплейсов (в первую очередь Wildberries): приём
товара от продавцов, хранение, маркировка, упаковка и доставка на склад маркетплейса.

Есть партнёрская компания **KET Logistic** — с ней есть интеграция (заказы можно отправлять в KET
прямо из CRM).

### Бизнес-модель в двух словах

1. **Партнёры** (магазины/продавцы) создают **заявки на забор** — «у меня N заказов, заберите».
   Заявка привязана к конкретному партнёру и городу.
2. Из заявки автоматически создаются N **заказов** (пустые «болванки» — без ФИО, адреса и т.д.) —
   их нужно наполнить данными.
3. **Менеджеры заказов («забивальщики»)** открывают заявку, фотографируют накладные/бланки на
   каждый заказ, вносят ФИО получателя, адрес, телефон, тип доставки (курьерская или почтовая —
   это принципиально разные ветки логики дальше).
4. Дальше заказ либо:
   - **Курьерская доставка** — развозится курьером внутри города, ИЛИ уезжает межгородним рейсом
     в другой город (см. раздел 5).
   - **Почтовая доставка** — отправляется через Казпочту (см. раздел 7).
5. Параллельно на складе **кладовщики** сортируют физические посылки по городам — для этого есть
   отдельный модуль «Сортировка» (раздел 6), который позволяет начинать сортировку сразу, не
   дожидаясь, пока все заказы в заявке будут «забиты».

## 3. Структура базы данных (основные таблицы)

- **`orders`** — заказы. Самая крупная и важная таблица (десятки тысяч строк, продолжает расти).
  Ключевые поля:
  - `code` — человекочитаемый номер заказа
  - `client`, `phone`, `address` — данные получателя
  - `delivery_id` — тип доставки (ссылка на `delivery_types`) — **обязательное** поле, без него
    заказ не считается «обработанным»
  - `courier_city_id` — город назначения ДЛЯ КУРЬЕРСКОЙ доставки
  - `city_id` — город назначения ДЛЯ ПОЧТОВОЙ доставки (**это два разных поля!** какое из них
    смотреть — зависит от `delivery_id`)
  - `pickup_city_id` — город, где посылку физически ЗАБРАЛИ (склад/партнёр) — это **НЕ** то же
    самое, что город назначения!
  - `pickup_id` — ссылка на заявку на забор, из которой создан заказ
  - `intercity_shipment_id`, `intercity_cost` — привязка к межгородней отправке (раздел 5)
  - `sorted_at`, `sorted_by_name` — отметка склада (модуль «Сортировка», раздел 6)
  - `track` — трек-номер (Казпочта или другой перевозчик)
  - `fizlico_pickup_address` — отдельный адрес забора, только для партнёров типа «Физ лицо
    Алматы/Астана» — не показывается в общем гриде, только в самой карточке заказа (этот столбец
    специально убирали из таблицы)
- **`pickups`** — заявки на забор от партнёров
- **`partners`** — партнёры/магазины (`tariff_post`, `tariff_courier` — тарифы)
- **`profiles`** — сотрудники CRM. У сотрудника может быть заполнено поле `city_id` — если
  заполнено, то в модуле «Сортировка» он видит только заказы своего города (раздел 6). У админа
  это поле обычно пустое → видит все города.
- **`shipments`** — межгородние отправки (раздел 5). Поля: `ship_date`, `warehouse_id`,
  `dest_city_id`, `box_cost` (стоимость всей отправки), `per_order` (стоимость на 1 заказ,
  `box_cost` делённая на кол-во заказов, округлённая), `order_ids` (jsonb-массив id заказов).
- **`deleted_items`** — «корзина». Перед любым `DELETE` из основной таблицы сначала сохраняется
  полный снимок строки сюда (функция `dbDelete` в коде) — на случай восстановления. Хранится
  30 дней. Смотреть в разделе CRM «Центр контроля» → «Корзина».
- **`delivery_types`** — справочник типов доставки. В нём могут быть лишние/старые записи — в
  форме заказа список специально отфильтрован регуляркой `/курьер|почт/i`, чтобы показывать только
  два актуальных варианта.
- **`courier_cities`** — отдельный, более узкий справочник городов именно для курьерской доставки
  (используется в межгороде и в форме заказа для поля «Город (курьерская)»). Это **НЕ** то же
  самое, что общий справочник `cities`! Если город не появляется в выпадающем списке межгорода —
  сначала проверить, есть ли он вообще в `courier_cities` (был случай с городом Капчагай — просто
  отсутствовал в справочнике).

### RLS (Row Level Security) — ОЧЕНЬ ВАЖНО, тут уже были проблемы

На таблицах `orders` и `pickups` в какой-то момент накопилось множество дублирующихся, избыточных
RLS-политик (по 9–11 штук на таблицу, некоторые — буквально копии друг друга). Это создавало
реальную нагрузку на Postgres при каждом запросе (каждая политика проверяется на каждой строке) и
приводило к таймаутам при загрузке большого объёма заказов.

Решение, которое уже применено: политики упрощены до 3 штук на таблицу — `orders_select`,
`orders_insert`, `orders_update` (аналогично для `pickups`) — каждая просто `using (true)` /
`with check (true)`, то есть разрешено всё (реальных ограничений по ролям в этой системе
фактически не было и раньше, просто было много избыточных копий одного и того же правила).

**ГРАБЛИ, на которые уже наступали:** при этом упрощении забыли политику на `DELETE` — из-за этого
удаление заказов молча не работало несколько часов (заказ «удалялся», но на самом деле нет — RLS
блокировал, PostgREST не считал это ошибкой на клиенте). Это добавлено отдельно:

```sql
create policy "orders_delete" on public.orders for delete using (true);
create policy "pickups_delete" on public.pickups for delete using (true);
```

Если в будущем снова будете трогать RLS у какой-то таблицы — **всегда проверяйте, что есть все
4 операции** (select/insert/update/delete), а не только 3.

### Закрытие анонимного доступа (18.09.2026) — текущее состояние

Описанное выше упрощение до `using (true)` имело побочный эффект: правила были выданы роли
`public`, а не `authenticated`. Роль `public` в Postgres включает анонимов — то есть таблицы были
открыты по анонимному ключу из `index.html` **без входа в систему**. Ключ этот публичен по
определению (статический фронтенд, спрятать его невозможно), и защищать данные должен был именно RLS.

Проверено практикой: запрос без авторизации отдавал `orders` целиком — 26 267 строк с ФИО,
телефонами и адресами получателей. Так же были открыты `pickups`, `deleted_items` (корзина с
полными копиями удалённых заказов), `wh_reservations`, на чтение — `partners` и справочники
(`cities`, `courier_cities`, `delivery_types`, `districts`, `statuses`, `order_statuses`).
У `calc_partners`, `calc_global_settings` и `kelesu_messages` не было ни одного правила вообще.

**Что сделано:** все эти правила переписаны с `public` на `to authenticated`, анонимные `SELECT`
сняты, на трёх таблицах без правил включён RLS с доступом для вошедших. Для сотрудников ничего не
изменилось — доступ у них по-прежнему полный. Заодно убраны дубли правил у `inbound_*` и `partners`
(по два одинаковых на таблицу — та самая лишняя нагрузка из предыдущего раздела).

Проверка после правки: тот же анонимный запрос к `orders`, `cities`, `deleted_items` и
`kelesu_messages` возвращает 0 строк.

**Как это выглядит при проверке:** PostgREST отвечает `HTTP 200` с пустым результатом, а НЕ ошибкой
доступа. Поэтому «закрыто» и «таблица пустая» снаружи выглядят одинаково — сверяйтесь со счётчиком
(`Prefer: count=exact`), а не с кодом ответа.

**Ловушка с именами правил:** правило на `deleted_items` называлось `allow all for authenticated`,
но выдано было роли `public`. Название врало, и в интерфейсе Supabase это выглядит нормально.
При проверке смотрите колонку `roles` в `pg_policies`, а не имя правила.

Готовые SQL для этой правки лежат локально в `db/` (папка в `.gitignore` — файлы
намеренно не выкладываются в публичный репозиторий).

### Повышение прав через profiles (19.09.2026)

Edge Function `set-password` проверяет права **правильно**: читает роль вызывающего из `profiles`
и пропускает либо администратора, либо обладателя `users.edit` — и то лишь для смены пароля
курьеру. Дыра была не в функции, а в том, на что она опирается: `profiles` и `roles` стояли с
правилом `ALL / to authenticated / true / true`, то есть **любой вошедший мог переписать любую
карточку, включая свою**.

Цепочка: курьер входит под своим аккаунтом → прямым запросом ставит себе `role = 'admin'` →
вызывает `set-password` → функция честно читает его карточку, видит «admin» → меняет пароль
администратору. Причём шаг 2 сам по себе уже открывает весь интерфейс: проверки `can()`/`canMod()`
в браузере читают ту же роль.

**Что сделано:** чтение обеих таблиц оставлено всем вошедшим (нужно при каждом входе, чтобы
вычислить собственные права), запись ограничена по образцу интерфейса — `roles` только админу,
`profiles` админу целиком, а обладателю `users.edit` только карточки курьеров и только с условием,
что курьером она и останется (`using` проверяет строку до правки, `with check` — после).

**Почему понадобились функции `jyldam_is_admin()` и прочие:** правило на `profiles`, которое само
читает `profiles`, уходит в бесконечную рекурсию. Функции объявлены `security definer` и читают
таблицы в обход правил. Если будете писать похожие политики — делайте так же.

**Попутно замечено:** в интерфейсе раздел «Роли и права» НЕ закрыт на администратора — проверки
`isAdmin()` стоят по всему разделу сотрудников, но не там. То есть менеджер с правом «Сотрудники»
мог открыть роль и выдать себе тип «Админ». Со стороны базы это теперь закрыто, но саму кнопку
в интерфейсе стоит тоже закрыть.

### Финансы, калькуляция и корзина (19–20.09.2026)

**Финансы и калькуляция** (`finance_*`, `calc_*`, 11 таблиц) закрыты по правам роли: правило
вызывает `jyldam_can(модуль, действие)`, а та читает `roles.perms` — те самые права, что
выставлены в разделе «Роли и права». Ничего отдельно настраивать не нужно: выдали роли доступ
к «Финансам» в интерфейсе — он появился и в базе. Администратору доступно всё всегда.

**Корзина** (`deleted_items`) — здесь правило намеренно НЕсимметричное, не «упрощайте» его:

| Операция | Кому | Почему |
|---|---|---|
| SELECT / UPDATE / DELETE | только админ | там полные снимки удалённых заказов с ФИО, телефонами, адресами |
| INSERT | любому вошедшему | снимок кладёт `dbDelete` при ЛЮБОМ удалении от ЛЮБОГО сотрудника |

Если закрыть и INSERT, ломается страховка, причём молча: `dbDelete` оборачивает запись снимка
в `try/catch` и при неудаче всё равно удаляет запись. Менеджер удалил заказ → снимок не
сохранился → восстанавливать нечего → никто не заметил.

Логику интерфейса здесь повторять было нельзя: доступ к «Центру контроля» в нём привязан
к праву на заказы (`fb` карта, `notify:'orders'`), а оно есть у курьеров — корзина осталась бы
открытой. Решение владельца от 20.09.2026: смотрит только администратор.

### Отложено: построчные правила для заказов

Курьер по-прежнему получает из базы ВСЕ заказы, а «только свои» отбирает браузер:
`S.orders.filter(o => myOrderCourierIds().includes(o.order_courier_id))`. То есть чужие ФИО,
телефоны и адреса уже лежат у него в памяти телефона.

Правило в базе выглядело бы так: курьеру отдавать только заказы, где `order_courier_id` ведёт
на его карточку в `order_couriers` (там `account_id` = аккаунт входа); персоналу — всё.

**Главная опасность — скорость.** `orders` читается при каждом входе каждого сотрудника, и
правило проверяется на каждой строке. Наивный подзапрос в `order_couriers` для каждой из
26 тысяч строк — это ровно тот сценарий, из-за которого уже были таймауты (см. выше). Делать
через `stable`-функцию, которая один раз возвращает список «моих карточек», и сравнение
`order_courier_id = any(...)`, плюс проверить индекс на `order_courier_id`.

Работа отложена владельцем 20.09.2026. Открытый вопрос, без которого не начинать: **что именно
курьер вправе менять в своём заказе** — сейчас у него право «редактирование заказов» целиком,
то есть формально и сумму, и тариф, и назначение другому курьеру.

**Что остаётся открытым:** любой вошедший сотрудник по-прежнему может прямым запросом прочитать
`finance_entries`, `calc_*` (ставки и нормативы), всю клиентскую базу в `orders` и корзину
`deleted_items`, а также изменить или удалить любой заказ. Проверки прав на эти модули живут
только в браузере. Это отдельная, бо́льшая задача: построчные правила (курьер видит только свои
заказы) и разделение доступа к финансам.

### Производительность / таймауты при загрузке

При росте `orders` до ~25 000+ строк начались таймауты при загрузке списка на клиенте. Причины
были две, обе уже решены:

1. Функция `dbList()` раньше запускала слишком много параллельных запросов страниц одновременно
   (по числу страниц, без ограничения) — браузер физически не может держать больше ~6 одновременных
   соединений к одному хосту, остальные вставали в очередь и не укладывались в таймаут.
   Решение: `dbList()` теперь грузит страницы пачками по 6 (`CONCURRENCY=6`), с таймаутом на
   страницу 30 секунд.
2. У проекта Supabase на маленьком тарифе (Micro/Small compute) закончился Disk IO burst budget —
   реальное дисковое троттлинг на инфраструктурном уровне, не имеющее отношения к коду. Тариф был
   повышен (Large, потом вернули на Medium после того, как выяснилось, что дело было в основном в
   пункте 1 выше). Если увидите таймауты снова — сначала проверьте Supabase → Settings →
   Infrastructure → есть ли предупреждение «Disk IO budget is being consumed» — и учтите, что
   размер ДИСКА (не только compute) тоже можно увеличить отдельно (лимит: не чаще 4 раз в 24 часа).

**Это обычные скрипты, а НЕ модули.** Никаких `import`/`export`. Все 604 глобальных имени
(434 функции + 170 переменных) по-прежнему общие, файлы выполняются строго в порядке подключения
в `index.html`. Для браузера пятнадцать файлов подряд — ровно то же, что один склеенный.
Резали механически, ни одной строки кода не меняли.

**Порядок подключения менять нельзя.** Файлы ссылаются друг на друга по именам, и если, например,
`11-zakazy.js` подключить раньше `01-yadro.js`, получите `Cannot access 'X' before initialization`
(раздел 9, пункт 2). Новый файл добавляйте в `index.html` на его место по порядку.

**Грабли, на которые наступили при нарезке:** совпадение склеенного текста с оригиналом ещё НЕ
означает, что нарезка корректна. Каждый `<script>` браузер разбирает отдельно, поэтому граница не
может проходить внутри функции или блока — иначе файл невалиден сам по себе. С первого раза так
сломались 7 файлов из 15 при полностью совпавшей склейке. Проверять надо и то, и другое:
склейку — на идентичность оригиналу, каждый файл — на разбор по отдельности.

**Метки версий обязательны.** Подключения выглядят как `js/11-zakazy.js?v=d953c90e` — это отпечаток
содержимого. Без его обновления браузеры будут отдавать пользователям старую версию из кеша.
После любой правки в `js/` или `css/`, перед коммитом:

```
python3 tools/refresh-versions.py
```

Скрипт заодно ругается, если файл лежит на диске, но забыт в `index.html`.

**У самого `index.html` метки нет и быть не может** — его адрес фиксирован. GitHub Pages отдаёт его
с `cache-control: max-age=600`, то есть до 10 минут после деплоя браузер вправе показывать старую
копию, даже не спрашивая сервер. Проверено на практике: сразу после деплоя браузер отдал старый
`index.html` из кеша (передано 0 байт) со ссылкой на старую версию CSS, хотя сервер уже отдавал
новую. Обычное обновление страницы не помогает — нужен `Cmd+Shift+R` (Windows: `Ctrl+F5`) или
подождать до 10 минут. Учитывайте это, когда проверяете деплой: «не применилось» чаще означает
«кеш», а не «сломалось».

### Как устроен сам код

- Навигация — по функциям `render...()` (например
  `renderOrders()`, `renderPartnersPage()`, `renderSorting()`) — каждая отвечает за один раздел меню.
- Общий объект состояния `S` (глобальный) держит всё загруженное из базы: `S.orders`, `S.pickups`,
  `S.cities`, `S.courier_cities`, `S.me` (текущий пользователь) и т.д.
- `render()` — главный роутер, вызывается при переключении вкладки. Внутри — `if(S.tab==='...')render...()`.
  **Важно:** если добавляете новый раздел с плавающей панелью пагинации внизу (см. `.orders-pager`
  в CSS) — не забудьте добавить вызов её функции очистки (`removeXxxPager()`) в самое начало
  `render()`, иначе панель «уезжает» вместе со скроллом на других вкладках при переключении (были
  похожие баги — плавающая панель от «Сортировки» не убиралась при переходе в «Историю изменений»).
- `dbList`, `dbInsert`, `dbUpdate`, `dbDelete` — общие обёртки над Supabase клиентом (`sb`), с
  логированием действий в `activity_log` и (для delete) бэкапом в `deleted_items`.
- **Realtime уже подключён глобально** (`sb.channel('jyldam-live')`, подписка на `orders`,
  `pickups`, `inbound_orders`) — любое изменение в базе (от кого угодно) автоматически прилетает
  всем открытым сессиям и обновляет `S.orders` и текущий экран (`scheduleRtRender`). Не нужно
  вручную дёргать перезагрузку данных после сохранения — но полезно знать, что экран обновляется
  САМ, даже без вашего участия, если кто-то другой что-то поменял.
- `.resp-table` — общий CSS-класс адаптивных таблиц (на мобильном превращаются в карточки через
  `data-label` атрибуты). **Исправлено 20.09.2026:** раньше правило
  `.resp-table tr:not(.open) td{display:none}` действовало на ВСЕ такие таблицы, хотя раскрытие
  строки по клику есть ровно в двух — «Заказы» и «Заявки на забор». Любая другая таблица на
  мобильном превращалась в пустые полоски: ячейки скрывались, а показывались лишь те, чьи
  подписи перечислены в правиле («ID», «Статус», «Город»…), а у чужих таблиц таких подписей нет.
  Так ломались «История изменений» и «Непривязанные заказы»; раньше это же ловили в «Сортировке»
  и лечили добавлением `open` каждой строке — лечение симптома, а не причины.

  Теперь правила сворачивания привязаны к отдельному классу **`.resp-collapse`**, он стоит только
  на таблицах заказов и заявок. **Обычной таблице ничего добавлять не нужно** — она по умолчанию
  показывает все ячейки. Делаете таблицу со сворачиванием — ставьте `resp-collapse` рядом с
  `resp-table`.

## 5. Модуль «Отправки межгород» (Intercity)

Курьерские заказы, которые нужно физически перевезти между городами (например, забрали в Астане,
а получатель — в Алматы), объединяются в **отправки** (коробки/грузы) с общей стоимостью перевозки,
которая потом делится на все заказы в коробке.

### Особые правила маршрутизации (зашиты в константы в коде)

- `INTERCITY_ALMATY_ALLOWED_CITIES` — со склада Алматы отправка идёт напрямую только в эти
  5 городов: Астана, Шымкент, Тараз, Кызылорда, Талдыкорган. Все остальные города для склада Алматы
  не должны появляться в выборе вообще (едут транзитом через Астану).
- `INTERCITY_VIA_ASTANA_CITIES` — список городов (Усть-Каменогорск, Семей, Костанай, Павлодар,
  Петропавловск, Караганда, Кокшетау, Сатпаев, Жезказган, Актобе, Уральск, Актау, Атырау), в
  которые со склада Астана заказы едут, ПОДТЯГИВАЯ по пути заказы, забранные в Алматы днём раньше
  (транзит через Астану). Логика вычисления «вчерашней» даты забора — в `ordersForIntercity()`.
- `INTERCITY_LIMITED_SCHEDULE_CITIES` — города с ограниченным расписанием отправки (Тараз,
  Костанай, Петропавловск) — не каждый день, поэтому в отправку «подтягиваются» также заказы,
  забранные в предыдущие дни-«доноры» (`intercityRollupDates()`).
- **Талдыкорган** — отдельный особый случай: для целей склада/сортировки (не для межгородней
  логики выше!) считается «своим» для Алматы — заказы, забранные в Талдыкоргане, физически привозят
  на склад Алматы (там нет отдельного склада). См. функцию `sortingCityId()` в разделе 6.
- Список городов в выпадающем меню при создании отправки строится динамически функцией
  `destCitiesForDate(date, whId)` — показывает город только если для него реально нашлись
  неотправленные заказы (`ordersForIntercity()`) на выбранную дату. Если ожидаемый город не
  появляется — сначала проверить, что он вообще есть в `courier_cities`, и есть ли реально
  подходящие заказы.

### Расчёт стоимости на 1 заказ

`per_order = Math.round(box_cost / кол-во заказов)` — округление может создавать небольшую
погрешность на уровне отправки (сумма всех `per_order` не всегда равна точно `box_cost`), но это
признанная, некритичная погрешность (порядка единиц тенге на отправку), **не стоит переделывать без
явного запроса**.

### Связь с «Калькуляцией» (раздел финансов)

Итоговая сумма межгорода в сводке Калькуляции считается **по дате самой отправки** (`ship_date` у
`shipments`), а НЕ по дате забора заказа (`pickup_date` у `orders`) — специально сделано так, чтобы
сходилось с суммой, которую показывает сам модуль «Отправки межгород». Причина расхождения, которая
уже была найдена и исправлена: из-за «дня-донора» (см. выше) заказ может быть забран в одном
календарном месяце, а сама отправка уйти уже в следующем — раньше это создавало разницу в сотни
тысяч тенге между двумя экранами. Реализация — переменные `freightByShipDate` / `freightByOrderDate`
/ `freightAdjust` в функции `renderCalcSummary()`.

Раздел непривязанных заказов (модалка «Показать непривязанные») показывает только заказы текущего
месяца — старые (прошлых месяцев) не показываются, они больше не актуальны для повседневной работы.

## 6. Модуль «Сортировка»

### Зачем он нужен

Раньше склад ждал, пока все менеджеры («забивальщики») закончат вносить данные по всей заявке, и
только потом получал единый «реестр» (Excel-выгрузку) для сортировки посылок по городам. Это
значит, что сортировка не начиналась, хотя часть заказов уже была готова. Модуль «Сортировка»
позволяет сразу, по мере готовности каждого отдельного заказа, определить, в какой город его класть.

### Как это работает

1. Кладовщик фотографирует физическую накладную на посылке (на них нет штрих-кода — только
   рукописный/печатный текст: ФИО, адрес, телефон).
   - Фото сжимается на телефоне перед отправкой (canvas, до 1400px по длинной стороне, JPEG
     качество 0.75) — это специально сделано для скорости: полноразмерное фото с телефона
     (несколько МБ) сильно замедляло и отправку, и саму работу ИИ. Функция `resizeImageForAI()`.
2. ИИ (`callAI`, модель `claude-sonnet-5`) распознаёт с фото ФИО/адрес/телефон, возвращает строгий JSON.
3. Система ищет совпадение среди сегодняшних, уже обработанных, ещё не отсортированных заказов
   (`findSortMatches()`) — сравнивает по телефону (самый надёжный признак, вес 100), ФИО
   (полное/частичное совпадение слов) и частично по адресу. Если совпадений несколько — выбирается
   с максимальным «весом», остальные предлагаются как альтернативы при «Это не тот заказ».
4. Если совпадение найдено — крупно показывается город назначения (`orderDestCityId()` — берёт
   `courier_city_id` или `city_id` в зависимости от типа доставки) + тип доставки + ФИО/адрес для сверки.
5. Кладовщик подтверждает («✅ Принял») — заказу выставляется `sorted_at` + `sorted_by_name`.
   Отсортированные заказы больше не попадают в поиск.
6. Если авто-поиск не сработал — ручной поиск по ФИО/телефону/номеру среди необработанных заказов
   (`renderSortManualPick()`).

### «Обработан» ли заказ — важное понятие

`orderIsProcessed(o)` = у заказа заполнено ФИО получателя И определён тип доставки (`delivery_id`).
Пока это не так — заказ существует (создан по заявке), но данные ещё не внесены, и показывать его
кладовщику рано (тип доставки, а с ним и город, может ещё измениться в процессе заполнения).
Необработанные заказы исключены из пула поиска в «Сортировке» — если совпадение не найдено, но
необработанные заказы за этот день/город есть, кладовщику показывается подсказка «⏳ возможно,
заказ ещё не обработан», а не просто «не найден».

Из-за этого понятия в основной форме заказа (`orderModal`) поле «Тип доставки» обязательно для
сохранения (без него не даст сохранить — проверка `if(!val('o_delivery'))...return false`), и
список вариантов в нём специально ограничен только «курьерская»/«почтовая» (регулярка
`/курьер|почт/i` по названию из справочника `delivery_types`, у которого могли быть лишние старые записи).

### Привязка кладовщика к городу — по городу ЗАБОРА, не назначения!

Это принципиально отличается от логики курьера (у курьера — привязка к конкретным заказам через
`my_order_courier_ids()`, это НЕ трогали и не меняли).

У кладовщика в его карточке сотрудника (`profiles.city_id`) можно указать город — тогда в
«Сортировке» он видит только заказы, которые **забрали** в этом городе (`o.pickup_city_id`), а НЕ
те, что едут в этот город. Логика: кладовщик работает на конкретном физическом складе (например,
склад Алматы), и на этот склад привозят посылки, забранные в Алматы (и в Талдыкоргане — см. особый
случай) — а его задача — определить, в КАКОЙ ГОРОД каждая из этих посылок должна дальше уехать
(это и есть сортировка).

Функция `sortingCityId(o)` — как раз про это: возвращает `pickup_city_id` заказа, с одним особым
случаем — если это Талдыкорган, приравнивает к городу Алматы (потому что там нет отдельного склада,
все посылки физически идут через склад Алматы). Если у сотрудника `city_id` не заполнен (обычно у
админа) — фильтра нет, видно все города сразу — плюс для админа/общего доступа показывается
разбивка по городам сверху (сколько заказов/принято в каждом городе отдельно).

### UI-детали модуля (на будущее, если будете его расширять)

- Наверху — плашки статистики: Заказов [за день] / Принято / Осталось, плюс вторая строка:

- По клику на строку — можно вручную переключить статус принят/не принят (с подтверждением через

- Пагинация на компьютере — такая же плавающая панель, как везде в CRM (`.orders-pager`, выбор
  кол-ва на странице, кнопки листания). На мобильном — «Показать ещё» (батчами).

  `MODULES` и в карте `fb` внутри `canMod()`) — по умолчанию виден только админу, пока явно не
  выдано разрешение роли.

## 6a. Модуль «Заказы партнёров» (KET) — особенности загрузки

Самые большие таблицы в базе: `inbound_orders` (36 тыс. строк, 47 МБ) и `inbound_order_items`
(87 тыс. строк, 21 МБ). Поэтому модуль грузится лениво и постранично, и с ним связаны три вещи,
которые легко сломать.

**`S.inbound_orders` — признак «модуль ещё не открывали».** Модуль проверяет именно
`if(!S.inbound_orders)`, чтобы понять, нужна ли первая загрузка. Поэтому никакой другой код не
должен создавать этот массив «про запас». Так уже ломалось: обработчик Realtime делал
`if(!S[key])S[key]=[]`, и один заказ, прилетевший от KET до открытия модуля, делал массив
непустым — первая загрузка не срабатывала, и вместо списка показывалась пара случайных строк.
Исправлено 18.09.2026: для `inbound_orders` обработчик выходит, если массива ещё нет.

**Обновления от KET не должны перерисовывать чужие модули.** Данные KET видны только в своём
модуле — ни счётчика в меню, ни на дашборде у них нет. Поток заказов от KET может идти почти
непрерывно, и раньше он перерисовывал текущий экран каждые 4 секунды, какой бы модуль ни был
открыт: список дёргался, прокрутка сбрасывалась. Теперь перерисовка планируется только при
`S.tab==='ket_orders'`; в памяти данные обновляются всегда.

**Режим «вся история» залипает — помните об этом.** В `loadInbound` параметр `full` по умолчанию
наследуется от прошлого вызова (`_inboundFullHistory`). Стоит один раз применить фильтр — он
грузит всё, — и дальше любой вызов `loadInbound()` без явного `full` снова тянет всю историю.
Так фоновое обновление раз в 3 минуты заново качало 36 тысяч заказов со всеми позициями каждый
раз, когда пользователь возвращался в модуль. Исправлено 18.09.2026: фоновое обновление для
`ket_orders` больше не трогает данные вообще, а обновляет только счётчики (три запроса `head:true`,
ноль строк) — строки и так приходят через Realtime. Если добавляете новый вызов `loadInbound`,
**указывайте `full` явно**.

**Фильтрация идёт в базе, а не в браузере (с 20.09.2026).** Раньше любой фильтр включал полную
загрузку: 36 тыс. заказов и 87 тыс. позиций ради полусотни строк на экране. Теперь всё, что
выражается запросом, считает база: даты, статусы (`send_status`, `status_kz`, `call_status`),
тип доставки (курьерская — `index is null`, почтовая — заполнен), общий поиск по
`external_id`/`client`/`phone` и фильтры по колонкам из карты `INB_SERVER_COL`.

Что запросом НЕ выразить — партнёр (вычисляется через состав заказа), склад, звонки,
переведённые на русский статусы — по-прежнему требует полной загрузки: `inboundNeedsFullLoad()`
решает это честно, лучше подождать, чем показать неполный список. **Добавляете новый фильтр по
колонке — либо внесите поле в `INB_SERVER_COL`, либо он автоматически потянет полную загрузку.**

Замер на заглушке (поиск по номеру заказа): было 147 запросов и 108 381 строка, стало 5 запросов
и 100 строк. Фильтр по партнёру остался на полной загрузке — это и проверялось отдельно.

Тонкость с поиском по телефону: строка запроса режется по пробелам и запятым (чтобы можно было
вставить сразу много номеров заказов), поэтому `+7 701 234 56 78` распадается на куски. Отдельно
добавляется поиск по цифрам всей строки целиком — иначе телефон не находился бы вовсе.

**Позиции грузятся пачками параллельно.** `loadInbound({full:true})` тянет позиции запросами по
500 id. Раньше это был последовательный цикл с `await` внутри — на 36 тысячах заказов 73 запроса
строго один за другим, десятки секунд. Теперь пачки идут по 6 одновременно (как в `dbList`).
Полная загрузка включается при первом же вводе в любой фильтр — имейте в виду, она тяжёлая.

## 6b. Отправка заказов в KET — трек-номер

Документация KET: https://ketkz.com/api/doc.txt. У них **всего два метода**:
`send_order.php` (создать заказ) и `get_orders.php` (прочитать заказы). **Метода обновления
не существует** — это главное ограничение, из которого следует всё остальное.

**Трек-номер (штрихкод) отправляется ДВУМЯ полями сразу — `kz_code` И `barcode`.**
Не убирайте ни одно из них без проверки на живом заказе. По документации это узнать нельзя:
среди полей ОТПРАВКИ там нет ни `barcode`, ни `kz_code` (последний описан только как поле
ОТВЕТА `get_orders`: «kz_code - трекинг код - когда заказ идёт почтой»).

Что показали проверки на живых заказах (20–21.09.2026), по порядку:

| Что отправляли | Колонка Barcode в KET |
|---|---|
| только `kz_code` | пусто |
| `kz_code` + `barcode` | **заполнена** |
| только `barcode` | пусто (проверено дважды) |

То есть работает именно пара. Почему — неизвестно, и выяснять это можно только живыми
отправками: метода обновления у KET нет, каждая проверка — новый заказ у них в системе.

**Грабли, на которые уже наступили.** После удачного теста с двумя полями `kz_code` убрали,
решив, что сработал `barcode`. Тест этого не показывал: уходили оба поля, и какое из них
сработало, из него не следовало. Трек перестал доходить, и заметили это не сразу — заказы
уходили к KET без трека, а дослать его нечем. Вывод общий: **не удаляйте поле на основании
теста, в котором оно не проверялось отдельно.**

Прежде чем винить KET, проверяли свою сторону целиком — и правильно делали:
`orderToKet()` кладёт поле, `callKet()` шлёт объект в нашу функцию `ket-proxy`, а та собирает
`data` как `{...order, secret}`, то есть **передаёт все поля насквозь и ничего не фильтрует**.
Значит поле действительно доходило до KET.

Отправляем при ЛЮБОМ типе доставки, если `track` заполнен. Условия «только почтовые» быть не
должно — курьерский заказ с треком тогда уходит без него.

**Метода обновления у KET нет** (всего два: `send_order.php` и `get_orders.php`), поэтому трек
уходит только в момент создания заказа. Отправили раньше, чем получили трек у Казпочты —
дослать нечем. Отправку это НЕ блокирует (решение владельца): заказ уходит без трека, а
`ketSendWarnNoTrack` лишь предупреждает. Не превращайте предупреждение обратно в вопрос.

**Следствие отсутствия метода обновления:** трек уходит только в момент отправки. Если заказ
отправили в KET до получения трека у Казпочты — дослать нечем, только пересоздавать заказ.
Поэтому порядок действий важен: **сначала получить трек, потом отправлять в KET.**

**Вес заказа уходит в поле `actual_weight`**, в килограммах, ровно тем числом, что стоит в
карточке заказа. Имя поля дал KET 21.09.2026 (по их приёмке 75747498), в документации его нет.
Отправляем ТОЛЬКО когда вес заполнен: выдумывать его нельзя, метода обновления у KET нет, и
неверный вес останется у них навсегда. Этим же закрыта просьба «по Астане можно не делать» —
там заказы не взвешивают, поле пустое, и ничего не уходит само. Понадобится слать вес и по
Астане — достаточно начать его проставлять в заказах, код менять не нужно.

**Отправку это НЕ блокирует и блокировать не должно** (решение владельца от 20.09.2026):
заказ без трека уходит в KET как обычно, просто без полей трека. Пользователю показывается
уведомление `ketSendWarnNoTrack` — при массовой отправке в тексте подтверждения, при
одиночной тостом после успешной отправки. Если будете это трогать — не превращайте
уведомление обратно в вопрос, который мешает отправить заказ.

**Что видно при отправке.** `sendOrderToKet` пишет в консоль браузера то, что уходит
(`KET → отправляем`), и ответ KET (`KET ← ответ`), а в сообщении об успехе прямо говорит:
«трек AP… передан». Без этого «у KET колонка Barcode пустая» невозможно отличить от
«мы его и не передавали» — именно на этом и потеряли время.

**Как проверить, что трек реально доехал:** отправить почтовый заказ с треком, затем открыть
«Заказы партнёров» и посмотреть колонку «Трек номер» (это и есть `kz_code` из ответа KET).
Если там пусто — значит `send_order.php` поле не принимает, и надо запрашивать у KET отдельный
способ передачи; наша сторона при этом сделана верно.

## 6c. Бланк Казпочты — данные отправителя в настройках

Данные отправителя (от кого, откуда, телефон поддержки, индекс, договор, код платежа) были
**впечатаны в сам PDF-шаблон**: сменить ИП или номер договора можно было только пересобрав файл.
С 20.09.2026 они хранятся в таблице `mail_label_settings` и правятся в CRM:
**Настройки → «Бланк Казпочты»**.

**Два файла шаблона, не перепутайте:**

| Файл | Что это |
|---|---|
| `assets/mail-label-blank.pdf` | чистый бланк, из него печатаем |
| `assets/mail-label-template.pdf` | исходный, с впечатанными данными — оставлен как образец «как было» |

Чистый получен из исходного удалением шести надписей. Технически: их содержимое лежало
**отдельным слоем** — последний поток PDF, который сначала рисует саму форму (`/TPL1 Do`), а
потом кладёт текст поверх. В этом потоке у шести блоков `BT x y Td [...]TJ ET` содержимое
заменено на пустое, **дополненное пробелами до прежней длины** — чтобы не сдвинулись байтовые
смещения и не сломался xref. Размер файла совпадает с исходным до байта.

**Почему нельзя было просто закрасить белым:** казахские подписи правой колонки стоят
вплотную — «сумма наложенного платежа» на 9 пунктов выше строки «Откуда». Прямоугольник,
закрывающий адрес целиком, срезал бы им низ букв.

Координаты (базовая линия, отсчёт сверху, страница 842×595): от кого 96/156, откуда 96/190,
поддержка 96/204, индекс 196/220, договор 65/351, КОД ПЛАТЕЖА 264/126 и число 480/126.

**Данные берутся по ИП, выбранному в заказе.** Так же устроено у KET: там «Настройки
отправителей» — список ИП, и при выборе ИП данные бланка меняются. У нас выбор уже был:
в карточке ПОЧТОВОГО заказа поле «ИП для Почты» (`orders.post_ip_id`), просто бланк его не
использовал. Теперь `mailLabelCfgFor(order, common)` берёт поля выбранного ИП из справочника
`post_ips`, а чего у ИП не задано — подставляет из общих настроек. «От кого» складывается
как «приставка + название ИП» (`ТОО QP Service` + `ИП Жадыра`), как в KET.

Поля у ИП: `label_prefix`, `from_addr`, `support`, `index_code`, `contract`, `payment_code`.
Пустое поле означает «взять общее» — заполнять нужно только то, что у этого ИП своё.

**Номер ШПИ и штрих-код.** Печатаются в правой колонке: номер над подписью «№ ШПИ»,
штрих-код под штамп-квадратом — там же, где их ставит бланк, который печатает KET.
Координаты сняты из самого шаблона через pdf.js, а не подобраны на глаз: подпись «№ ШПИ»
стоит на 511/219, подписи штампа — на 273 и 283.

Код рисуется настоящим Code128 (библиотека JsBarcode, она уже подключена в index.html и
используется для кодов заказов), вставляется в PDF картинкой PNG и кэшируется по номеру —
в одной печати бывают десятки бланков. Проверено чтением обратно: сгенерированный PDF
рендерится и распознаётся сканером как исходный номер. Самодельные «полоски по цифрам»
для этого не годятся — такой рисунок не читается.

Если трека у заказа нет, номер и код просто не печатаются, бланк выходит как раньше.

**Суммы и индекс получателя.** Обе денежные строки бланка — «сумма объявленной ценности» и
«сумма наложенного платежа» — показывают ОДНУ И ТУ ЖЕ сумму заказа прописью:
«1 500 (одна тысяча пятьсот тенге 00 тиын)». Считает `amountForLabel`; склонения проверены
на 1500/2000/5000/21 («одна тысяча», «две тысячи», «пять тысяч», «двадцать один»).
Индекс внизу справа — это индекс ПОЛУЧАТЕЛЯ из карточки заказа (`orders.index`), не путать
с индексом отправителя вверху (он из настроек).

**У файлов в `assets/` тоже есть метка версии.** Шаблон грузится через `fetch` из кода, а не
тегом, и сначала метки не было — правка шаблона не доезжала, браузер отдавал старую копию
из кеша. Поймано на живом примере: в бланке оказались ОБЕ строки, старая «0 (ноль тенге)»
и новая сумма. `tools/refresh-versions.py` теперь проставляет версии и для `assets/`,
но правит файлы `js/` уже после того, как посчитал их отпечатки — **после правки шаблона
скрипт нужно прогнать дважды**, пока не скажет «менять нечего».

**Значения по умолчанию продублированы в коде** (`MAIL_LABEL_DEFAULTS`) — ровно те, что были
на старом бланке. Если таблицы нет или она недоступна, бланк печатается как раньше, а не пустым.

## 6d. Ежедневный отчёт в Телеграм

Бот «JYLDAM Logistics» присылает сводку по работе за день. Считает и отправляет Edge Function
`daily-report`, расписание — в планировщике базы (`pg_cron` + `pg_net`), SQL лежит в
`db/9-ТЕЛЕГРАМ-ежедневный-отчёт.sql`.

**Два отчёта:** вечерний (23:00 по Астане — итоги дня) и утренний (9:00 — что мешает работать:
без типа доставки, почтовые без веса, без трека, без индекса). Тело запроса выбирает какой:
`{"kind":"evening"}` или `{"kind":"morning"}`; утренний не обязателен.

**Что в вечернем:** заявок на забор; заказов всего и в разрезе курьерских/почтовых; по городам
забора; сколько принял склад (по городам, Талдыкорган относится к Алматы — как в «Сортировке»);
сколько заказов правили менеджеры и кто именно; проблемы; выручка, расходы и прибыль за день.

**«Кто правил заказы» берётся из `activity_log`, а не из `processor_id`.** Поле `processor_id`
подставляется от партнёра автоматически при создании заказа и не говорит, кто сел и переписал
бланк. В журнале же запись появляется только если поля реально изменились (`dbUpdate` пишет лог
при непустом `buildChanges`). Один заказ могли править несколько раз — считаются заказы, а не
строки журнала.

**Заказ без типа доставки — не почтовый.** `delivery_id` пустой означает «ещё не заполнен»;
если отнести такие к почтовым, счётчик «почтовых без веса» раздувается пустышками. В отчёте
они отдельной строкой «без типа доставки» — это ровно те, которых не видит склад (раздел 6).

**«Не отправлено в KET» не считаем.** Отправка в KET — ручное решение по каждому заказу,
обязанности отправлять нет, поэтому такой счётчик был бы шумом. Вместо него: сколько ушло и
сколько из них ушло БЕЗ трека — вот это настоящая потеря, метода обновления у KET нет
(раздел 6b), дослать трек нечем.

**Проверка Казпочты идёт номером УЖЕ ВЫДАННОГО заказа.** Функция берёт почтовый заказ
сегодняшнего дня, у которого уже есть трек, и повторяет запрос с его `OrderNum`: Казпочта
отвечает кодом 20012 и прежним ШПИ, нового номера не тратит. **Не подставляйте свой номер
вроде `PING`** — первый же такой запрос израсходует настоящий ШПИ, а номер навсегда займётся
и потом столкнётся с реальным заказом (`genOrderCode()` выдаёт 7 цифр). Если за день нет ни
одного почтового заказа с треком, проверка просто пропускается.

**Если отчёт не собрался, приходит сообщение об ошибке.** Молчание в 23:00 легко принять за
«день без происшествий», поэтому сбор обёрнут в `try/catch`: текст ошибки уходит тем же
сообщением, а функция отвечает `500`, чтобы сбой был виден и в `cron.job_run_details`.

**ПРИБЫЛЬ СЧИТАЕТСЯ В ДВУХ МЕСТАХ — это единственное такое место в системе.** Формула в
функции (`orderFinance`) — построчная копия `calcOrder()` из `js/07-kalkulyaciya.js` вместе с
наследованием нормативов (`calc_settings` → предыдущий месяц → строка без периода), городскими
и персональными ставками, снимком `orders.calc` и правилом «оплачено отправителем». **Меняете
статьи расходов в CRM — поправьте и здесь**, иначе отчёт начнёт тихо расходиться с экраном
«Калькуляция». Совпадение проверялось прогоном обеих версий на одних данных.

Одно расхождение сознательное: в месячной сводке Калькуляции межгород пересчитывается по дате
ОТПРАВКИ (`freightByShipDate`, раздел 5), а в дневном отчёте берётся `intercity_cost` самого
заказа. Для одного дня пересчёт по отправкам смысла не имеет.

**Список полей заказа сверяется с базой на лету.** Функция сначала читает одну строку
`orders` целиком, смотрит набор колонок и запрашивает только те, что реально есть.
Так вышло не от хорошей жизни: запрос несуществующей колонки роняет ВЕСЬ отчёт, хотя без
неё считается всё остальное. Отсутствующие перечисляются в сообщении строкой «нет полей в
базе», чтобы потеря была видна, а не тиха.

**В базе нет `orders.ket_id` и `orders.calc`, хотя код CRM пишет в обе** (обнаружено
22.09.2026 как раз этим отчётом). Следствия разные: `calc` — это снимок расчёта по заказу,
без него Калькуляция просто всегда считает по текущим нормативам; а вот `ket_id` — отметка
«отправлен в KET», и она не сохраняется, то есть галочка «KET ✓» пропадает после
обновления страницы и заказ можно отправить в KET повторно, не заметив. Отчёт берёт
отправки в KET из `activity_log` (`action='ket'`) — там запись есть.

**Передать конкретный день:** `{"kind":"evening","date":"2026-09-21"}`. Нужно, чтобы
проверить отчёт на настоящих числах, не дожидаясь вечера. Неразобранная дата молча
откатывается на сегодня. Планировщик `date` не передаёт.

**В сообщение уходят ТОЛЬКО ЦИФРЫ** — ни ФИО, ни телефонов, ни адресов. Телеграм чужой
сервис, клиентской базе там не место. Понадобится список — он остаётся в CRM.

### Бот отвечает на команды (22.09.2026)

Телеграм при каждом сообщении дёргает **ту же функцию** `daily-report` — отдельной не
заводили. Команды: `/report`, `/report вчера`, `/report 21.09`, `/problems`, `/help`.
Дата разбирается `parseDayFromText` — понимает «21.09», «21.09.2026», «2026-09-21»,
«вчера», «позавчера», «сегодня».

**Два входа в одну функцию, и путать их нельзя.** Планировщик приходит с заголовком
`x-report-key` и секретом `REPORT_KEY`. Телеграм — с заголовком
`x-telegram-bot-api-secret-token` и секретом `TELEGRAM_WEBHOOK_SECRET`, который задаётся
один раз в `setWebhook`. Проверка вебхука идёт ПЕРВОЙ, `REPORT_KEY` для неё не нужен.

**Отвечаем сразу, работу доделываем в фоне.** Отчёт собирается ~10 секунд, а Телеграм,
не дождавшись ответа, шлёт то же сообщение снова — и отчёт приходит дважды. Поэтому
`200` отдаётся немедленно, а сбор уходит в `EdgeRuntime.waitUntil` (или просто без
`await`, если его нет). Плюс повтор отсекается по `update_id`.

**Накопившаяся очередь.** Пока вебхук не настроен, Телеграм хранит сообщения около суток
и вываливает их все разом при включении. Поэтому в `setWebhook` стоит
`drop_pending_updates: true`. Именно это и выглядело как «бот пишет по два раза».

**Вебхук включается запросом к самой функции** (`{"action":"setwebhook"}`), а не вручную
через `api.telegram.org`. Причина: вручную токен бота стоит прямо в адресе, и на любой
другой токен — например отозванный через `/revoke` — Телеграм отвечает глухим
`404 Not Found`, по которому не догадаться, в чём дело. Мы на это потратили полчаса.
У функции токен уже в секретах. Есть ещё `webhookinfo` и `deletewebhook`.

**Если меняете токен через `/revoke`, сразу замените и секрет `TELEGRAM_BOT_TOKEN`** —
иначе молча перестают приходить и отчёты, и ответы бота.

**Бота может найти посторонний.** Функция отвечает только в чат из `TELEGRAM_CHAT_ID`,
остальным молча ничего — но обязательно с кодом `200`, иначе Телеграм будет слать то же
сообщение снова.

**Защита.** У функции выключен «Verify JWT» (её зовёт планировщик, а не вошедший сотрудник),
поэтому вместо входа стоит собственный ключ `REPORT_KEY`: без заголовка `x-report-key`
функция не отвечает никому. Ключ лежит в секретах и в тексте задания планировщика.

**Часовой пояс — важно.** `pg_cron` считает по Гринвичу, а Казахстан круглый год UTC+5 и
часы не переводит. Поэтому 23:00 по Астане это `0 18 * * *`, а 9:00 — `0 4 * * *`. Границы
самого дня функция тоже считает по местному времени (`localDayBounds`), иначе вечерний отчёт
захватывал бы кусок вчерашнего дня — та же ловушка, что была с `localToday()` в CRM.

**Грабли при настройке — на них ушёл почти час.**

`net.http_post` возвращает НОМЕР ЗАПРОСА, а не результат. Ответ приходит позже и лежит в
`net._http_response`; смотреть надо по этому номеру (или `order by id desc limit 3`), иначе
кажется, что всё прошло. Коды: 404 — функция не выложена, 403 — ключ не совпал с секретом
`REPORT_KEY`, 500 «REPORT_KEY не задан» — секрет не создан.

`timeout_milliseconds := 60000` обязателен. По умолчанию `pg_net` ждёт 5 секунд, а отчёт
собирается дольше. Причём функция при этом ДОРАБАТЫВАЕТ и отчёт присылает — просто в
`net._http_response` остаётся «Timeout of 5000 ms reached», и выглядит это как провал.

Редактор SQL в Supabase выполняет ВСЁ содержимое окна, а показывает результат только
последнего запроса. Файл `db/9`, прогнанный целиком, создаёт задания с текстом-заглушкой
`СЮДА-КЛЮЧ` вместо ключа — они молча получают 403 в 23:00. Выполнять по одному блоку:
выделить мышкой и Run. Проверка в блоке 4 показывает колонку `ключ_не_подставлен`.

Три значения, которые легко перепутать: токен бота (`123:AA…`) → секрет `TELEGRAM_BOT_TOKEN`;
идентификатор чата (`812929478`) → `TELEGRAM_CHAT_ID`; придуманный нами ключ → секрет
`REPORT_KEY` И заголовок `x-report-key`. К Телеграму последний отношения не имеет.

**Деньги.** Ни Телеграм, ни планировщик отдельно не стоят: бот бесплатен, `pg_cron` и
`pg_net` входят в тариф Supabase.

## 7. Интеграция с Казпочтой (SOAP API)

Курьер получает трек-номер для почтовых заказов через кнопку «📮 Получить трек» — вызывает Edge
Function `kazpost-get-barcode`, которая обращается к SOAP-сервису Казпочты (`GetAddrLetter`, боевой
URL `http://rates.kazpost.kz/postratesprod/endpoints`).

### Два контура у Казпочты — и разные диапазоны номеров (21.09.2026)

На одном сервере `rates.kazpost.kz` у Казпочты **два адреса сервиса**, и они выдают номера из
РАЗНЫХ диапазонов. Один и тот же запрос, тот же ключ, тот же номер заказа:

| Адрес | Ответ |
|---|---|
| `…:80/postratesprod/endpoints` | `AP081985585KZ` |
| `…:80/postratesws/endpoints` | `QS000000014KZ` |

**Этим и объяснялась вся история с префиксом QS**, на которую ушло несколько дней. Перебирали
`ProductCode` (P103/P145/P109/P126A), `MailCtg`, `SendMethod`, `EnvelopeSize`, формат `OrderNum`,
формат телефона — ни одно из этого не было причиной. Казпочта успела «привязать QS к ключу», и
это было правдой: просто на другом контуре.

Как нашли: программист Казпочты прислал скриншот SoapUI со своим запросом — в адресной строке
стоял `postratesws`, а у нас в коде был `postratesprod`. Отправили ИХ ЖЕ запрос на оба адреса и
получили разные префиксы.

**Адрес теперь в секрете `KAZPOST_ENDPOINT`** (Supabase → Edge Functions → Secrets), чтобы
переключать контур за минуту без правки кода. Значение по умолчанию, если секрет не задан, —
`http://rates.kazpost.kz:80/postratesws/endpoints` (тот, что даёт QS). Вернуться на прежний:
задать секрет со значением `http://rates.kazpost.kz:80/postratesprod/endpoints`.

**Полезное следствие, пригодится при отладке.** Если отправить запрос с тем же `OrderNum`, что
уже использовался, Казпочта НЕ выдаёт новый номер: возвращает код `20012` и ранее выданный ШПИ.
Значит повторный запрос с известным номером заказа — бесплатный способ посмотреть, что этот
контур выдал в прошлый раз, не тратя номер из диапазона.

**И отсюда же риск, про который стоит помнить.** Номер заказа у нас — случайное семизначное
число (`genOrderCode`), а уникальность проверяется только среди заказов, загруженных в браузер.
Сразу после входа там лежат лишь сегодняшние. При 26 тысячах заказов в диапазоне 9 миллионов
совпадения статистически ожидаемы. Если два заказа получат один номер, второй не получит своего
ШПИ — Казпочта молча вернёт чужой, и у двух посылок будет один трек. Проверить:
`select code, count(*) from public.orders group by code having count(*) > 1;`

Важные детали, если снова будете трогать эту интеграцию:

- `ProductCode=P103` («Посылка РК», стандарт) — рабочая, проверенная комбинация, даёт трек-номера с
  префиксом AP. Пробовали разные другие коды (P145 → EW, P109, P126A → не сработали вовсе) в
  попытке получить префикс QS — не вышло. Причина: диапазон QS выделяется Казпочтой заранее, вручную,
  под конкретный номер договора/ключ, и никак не подбирается через параметры запроса. Это
  подтвердилось и с чужой, отдельной системой — та же проблема с тем же ключом и договором. Ждём
  ответа от техподдержки Казпочты по этому вопросу.
- `MailCtg` выбирается автоматически по каждому заказу (не хардкодится в секретах) — если у заказа
  есть сумма к оплате (`order_sum`), используется категория 4 («с объявленной ценностью и наложенным
  платежом» — покрывает и страховку, и наложенный платёж одновременно) с реальной суммой в полях
  `DeclaredValue`/`CashOnDelivery`; если суммы нет — категория 3 («Обыкновенная»).
- `SndrCtg=2` (юрлицо) — добавили после того, как обнаружили это поле в ДРУГОЙ, отдельной панели
  (`admin.jyldam-logistics.kz`), где были более полные настройки.
- Все секреты (Key, DEA_NUMBER, БИН и т.д.) читаются с `.trim()` — раньше случайный пробел в конце
  значения секрета (например, `"P109 "`) приводил к непонятной внутренней ошибке базы Казпочты
  (ORA-06512) без внятного сообщения.

## 8. Прочие известные особенности и грабли

- **Вес заказа — всегда три знака после запятой.** Кладовщик списывает с весов и отбрасывает
  хвостовые нули: набирает «1,3» вместо «1,300», «0,97» вместо «0,970». Число от этого не
  меняется, но в списке рядом стоят «1,3», «0,97» и «2» — глазами не сравнить и не понять,
  записано ли до грамма. Везде показываем через **`fmtWeight(w)`** (js/01-yadro.js), читаем из
  полей через **`parseWeight(v)`**: он принимает и запятую, и точку и округляет до грамма.
  Поля ввода веса — `type="text"` с `inputmode="decimal"`, а НЕ `type="number"`: у числового
  поля запятая считается ошибкой ввода, значение молча становится пустым, и вес терялся.
  Формат не исправляет уже введённые неверные числа: 1,031 так и останется 1,031.

- **Сумма заказа: два поля, одно правило.** В базе исторически `order_sum` (то, что человек
  вводит в карточке) и `cost` (его копия). Сохранение давно пишет оба одинаково, но у старых
  заказов `order_sum` бывает пустым, а `cost` заполнен. Раньше это разъезжалось на экране:
  карточка и Калькуляция читали `order_sum`, а грид «Стоимость», плашка «Сумма доставки» и
  выгрузка Excel — `cost`; один заказ показывал разные числа, а в Калькуляцию заказы с пустым
  `order_sum` попадали с нулевой выручкой. Теперь везде **`orderSum(o)`** (js/01-yadro.js):
  берёт `order_sum`, а если он пуст — `cost`. **Новые места с деньгами по заказу делайте через
  него**, а не читайте поля напрямую.

- **Даты и часовые пояса:** используется `localToday()` — специальная функция для получения ТЕКУЩЕЙ
  ЛОКАЛЬНОЙ даты, корректно работающая независимо от часового пояса браузера (компенсирует
  `getTimezoneOffset()`). НЕ использовать голый `new Date().toISOString().slice(0,10)` для
  «сегодня» — это UTC, может отличаться от локальной даты на несколько часов ближе к границе суток.
- **Загрузка фото пачкой** (в карточке заявки на забор) — сопоставляет фото «по порядку» только с
  заказами, у которых ещё нет ни одного фото (защита от случайной перезаписи). Если фото больше,
  чем пустых заказов — лишние остаются нераспределёнными (есть тост-уведомление об этом, но легко
  упустить из внимания). Для быстрого поиска, каким заказам не хватило фото — есть кнопка-фильтр
  «🔍 Без фото (N)» в той же карточке.
- **Кнопка «Сохранить»** в карточке заявки на забор продублирована наверху (рядом с «Загрузить фото
  пачкой» / «Создать ещё заказ»), чтобы не листать длинную ленту заказов до самого низа — нижняя
  (стандартная) кнопка скрыта через CSS, но обе вызывают одну и ту же логику сохранения/проверки.
- **Партнёры типа «Физ лицо Алматы/Астана»** — особый тип партнёра (проверка
  `isFizlicoName()`/`isFizlicoPartner()`, сравнение без учёта разных видов кавычек). Для таких
  партнёров в карточке заказа появляется отдельное поле «Адрес откуда забрали (физ. лицо)»
  (`fizlico_pickup_address`), которое специально НЕ выводится в общую таблицу заказов (только
  внутри карточки).
- **Новый норматив в «Калькуляции» — это ещё и колонка в базе.** Каждое поле из `CALC_FIELDS`
  сохраняется в ОДНОИМЁННУЮ колонку таблицы `calc_settings` (`saveCalcSettings` собирает строку
  по `data-calcnorm`). Добавили поле только в код — при сохранении вылетит
  «Could not find the 'X' column of 'calc_settings' in the schema cache», причём **не сохранится
  ничего**: ни новое поле, ни остальные значения, которые правили на этом экране. Ровно так
  вышло 20.09.2026 с `fund_smm` и `fund_other` — я заявил, что SQL не нужен, и ошибся.
  Добавляете поле — сразу добавляйте колонку (`db/7-ДОБАВИТЬ-расходы-в-калькуляцию.sql` как
  образец) и проверяйте сохранение, а не только отрисовку.

## 9. Что делать, если что-то не работает после деплоя

1. Проверить консоль браузера (веб-инспектор → Консоль) на ошибки JS.
2. Если ошибка вида `Cannot access 'X' before initialization` — значит, какая-то
   переменная/константа используется РАНЬШЕ своего объявления в файле (JS temporal dead zone) —
   искать, где объявлена константа, и либо переместить объявление выше, либо не ссылаться на неё в
   коде, который выполняется немедленно при загрузке (вне функций).
3. Если что-то визуально не отображается, а в HTML (через инспектор → Copy outerHTML) видно, что
   данные там есть — значит, дело в CSS, не в генерации разметки. Проверить `getComputedStyle()`
   конкретного элемента через консоль (`display`, `visibility`, `opacity`) — вероятно, что-то
   пересекается с общим правилом для другой таблицы (см. про `.resp-table` и класс `open` выше).
4. Если действие (сохранение/удаление) как будто срабатывает, но результат не сохраняется после
   обновления страницы — проверить RLS-политики в Supabase для соответствующей таблицы
   (`select * from pg_policies where tablename='...'`) — возможно, отсутствует политика на нужную
   операцию.

## 10. Практические детали работы с репозиторием

Обнаружено при работе, в исходный документ не входило:

- `index.html` в репозитории хранится с **CRLF** переводами строк, а копия, скачанная с GitHub,
  приходит с LF. Если скопировать скачанный файл поверх репозиторного, git покажет изменение
  **всех** строк вместо реальной правки. Редактировать нужно файл из репозитория, сохраняя его
  переводы строк.
- Не редактировать копию в `~/Downloads`: она уже один раз была перезаписана новой загрузкой и
  молча потеряла применённую правку. Рабочая копия — клон репозитория.
- `gh` установлен в `/opt/homebrew/bin/gh`, но не всегда есть в `PATH` — вызывать по полному пути.
- Проверить, что деплой реально доехал:
  `gh api repos/asembinov-cmyk/Jyldam-crm/pages/builds/latest --jq '.status + " " + .commit[0:7]'`
